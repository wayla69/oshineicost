1 ภาพรวมสถาปัตยกรรม

หลักการออกแบบสามข้อกำหนดทุกอย่างที่ตามมา: (1) ข้อมูลรีวิวอยู่ที่แดชบอร์ดบน Fly ที่เดียว เพราะฐานข้อมูลยอดขายถูก push ทับจากเครื่อง sync ทุกวัน ตารางรีวิวจึงต้องอยู่ในรายการ "เก็บข้ามการสลับฐานข้อมูล" (2) credential ของทุกแพลตฟอร์มอยู่บนเครื่อง sync ในไฟล์เดียว (สำรองพร้อม secrets อื่น) ตัวดึงจึงรันบนเครื่องนั้นแล้วโพสต์เข้าเว็บ ไม่ใช่รันบน Fly (3) ทุก connector คุยกับเครือข่ายผ่านฟังก์ชัน http() ที่ฉีดเข้าไปได้ ทำให้เทสต์ทั้งหมดรันบน fake โดยไม่แตะ API จริง

3 โครงสร้างข้อมูล

customer_feedback (หนึ่งแถว = หนึ่งเสียง)

คอลัมน์ความหมาย
id, fingerprint UNIQUEตัวตนของแถว: sha1(source#external_id) เมื่อแพลตฟอร์มให้ id (คงที่แม้ผู้เขียนแก้ข้อความ) ไม่งั้น sha1(branch|date|text)
kindreview บนลิสติ้ง/เพจของร้าน · comment ใต้โพสต์/วิดีโอของร้าน · mention ที่อื่นบนอินเทอร์เน็ต (ไม่มีดาว ไม่เข้าคิวตอบ)
source, external_id, external_ref, url, locationแหล่ง, id ฝั่งแพลตฟอร์ม (มี prefix เช่น comment: post: tweet:), ที่อยู่สำหรับโพสต์คำตอบ (Google resource name / ig_user/comment / video/comment), ลิงก์ต้นทาง, ชื่อลิสติ้ง/เพจ/แคปชัน
branch_id, branch_nameจับคู่จากชื่อ (ตรง → มีชื่อสาขาอยู่ในชื่อลิสติ้ง → ตรวจจับจากข้อความสำหรับ mention) ถ้าไม่พบ เก็บชื่อดิบไว้และรายงาน unmatched
rated_at, rating, text, author_hashวันตามเวลาไทย, ดาว (ถ้ามี), ข้อความ (ว่างได้สำหรับรีวิวให้ดาวอย่างเดียว), แฮชของผู้เขียน — ไม่เก็บชื่อ (PDPA)
sentiment, score, themes, menus, analysed_byผลวิเคราะห์ (pos/neg/neu, −1..1, JSON list, JSON list) และเครื่องมือที่ใช้ (claude / lexicon)
reply_text, replied_atคำตอบที่มีอยู่จริงบนแพลตฟอร์ม (ดึงมาหรือส่งแล้ว)
reply_draft, reply_status, reply_requested_at/by, reply_errorคิวตอบ: pending → sent | failed (พร้อมเหตุผล) หรือ manual (แพลตฟอร์มไม่ให้โพสต์ผ่าน API)
uploaded_at/by, updated_atร่องรอยการนำเข้า/อัปเดต

ตารางประกอบ

feedback_sync_log
ผลการดึงแต่ละรอบต่อแหล่ง: since, fetched, inserted, updated, unchanged, status, message — การ์ดแหล่งข้อมูลอ่านจากที่นี่ และ since อัตโนมัติคำนวณจาก "สำเร็จครั้งล่าสุด"
feedback_webhook_events
เหตุการณ์ที่ Meta ส่งเข้ามา (platform, object_id, field, payload) รอตัวดึงมาอ่านเนื้อหาแล้วทำเครื่องหมาย processed (เก็บล่าสุด 5,000 รายการ)

ทั้งสามตารางถูกสร้าง/เพิ่มคอลัมน์อัตโนมัติเมื่อถูกเรียกครั้งแรก (_ensure() ใช้ CREATE IF NOT EXISTS + ALTER TABLE ADD COLUMN เมื่อขาด) จึงย้ายไปฐานข้อมูลใหม่ได้โดยไม่ต้องรัน migration แยก

5 สัญญาของ connector และรูปแบบแถว

6 ระยะเวลาย้อนหลังสูงสุดของแต่ละแหล่ง

กติกากลาง: รอบแรกของแต่ละแหล่งดึงย้อนหลังเท่าที่แพลตฟอร์มให้ (ตาราง) รอบถัดไปดึงตั้งแต่ "สำเร็จครั้งล่าสุด − 2 วัน" ทุกวัน 09:00 หรือสั่งด้วยมือด้วย --since all / --since YYYY-MM-DD ได้ตลอด

7 รีวิวเชิงวิศวกรรม: จุดแข็ง ความเสี่ยง ข้อสมมติ

ที่ทำได้ดี

  • Idempotent ทุกทาง — fingerprint ทำให้อัปโหลดซ้ำ/ดึงซ้ำไม่สร้างแถวซ้ำ แถวที่ไม่เปลี่ยนไม่เสียค่าวิเคราะห์ แถวที่แก้ไขวิเคราะห์ใหม่ คำตอบที่มาจากแพลตฟอร์มปิดคิวเอง
  • ล้มดังไม่ล้มเงียบ — ทุกแหล่งบันทึกผลต่อรอบ (สำเร็จ/ล้มเหลว+เหตุผล) คิวตอบที่ส่งไม่ได้ขึ้น "ส่งไม่สำเร็จ" พร้อมเหตุผลบนรีวิวนั้น เครื่องที่ไม่ได้ตั้งค่าไม่ทำให้อะไรค้างเงียบ
  • ทดสอบได้โดยไม่แตะ API จริง — http() ฉีดได้ 43 เทสต์ครอบคลุม paging, since, การหมุน token, การตอบ, webhook signature; gate เขียวก่อน merge ทุก PR
  • ปลอดภัยพอสมควร — webhook ตรวจ HMAC และ fail-closed, จำกัดขนาด body, ตัวรับเปิดสาธารณะเฉพาะ path เดียว; ข้อมูลส่วนบุคคลเก็บเป็นแฮช; secrets อยู่ไฟล์เดียวที่สำรองอยู่แล้ว
  • ต่อขยายถูก — แพลตฟอร์มใหม่ = ไฟล์เดียว + หนึ่งบรรทัดทะเบียน (พิสูจน์แล้ว 5 ครั้งในวันเดียว)

ความเสี่ยงและข้อสมมติ (เรียงตามผลกระทบ)

  1. แก้แล้ว ตาราง customer_feedback ไม่อยู่ในรายการเก็บข้ามการ push ฐานข้อมูล → รีวิวที่อัปโหลดจะหายทุก 10:00 พบระหว่างทำงานและแก้ใน PR #127 (มีเทสต์กันถอยหลัง) — บทเรียน: ตารางใหม่ใดที่เขียนบน Fly ต้องเข้า _PRESERVED_* เสมอ
  2. กลาง TikTok: ชื่อ endpoint/ฟิลด์อิงเอกสาร Business Account API v1.3 จากความจำ ยังไม่ได้ทดสอบกับแอปจริง (ต้องรอ TikTok อนุมัติ) ค่าคงที่ทั้งหมดรวมไว้ต้นไฟล์ ปรับที่เดียว และ parser อ่านฟิลด์แบบยืดหยุ่น
  3. กลาง Google: การอนุมัติ Business Profile API ใช้เวลา 1–2 สัปดาห์; แอป OAuth ที่อยู่สถานะ Testing มี refresh token อายุ 7 วัน ต้องกด Publish (อยู่ในคู่มือ §7) — ระหว่างรอใช้ Takeout
  4. กลาง คุณภาพการวิเคราะห์: พจนานุกรมไทยจับประชด/บริบทซับซ้อนไม่ได้ ตั้ง ANTHROPIC_API_KEY บน Fly เมื่อไรก็ได้ (โค้ดพร้อม, ค่าใช้จ่ายรีวิวหลักพันไม่ถึง ฿50) — จนกว่าจะตั้ง ให้อ่านตัวเลข neg% อย่างระวัง
  5. กลาง Meta webhook: ต้องตั้ง Fly secrets 2 ตัว + สมัครรับเหตุการณ์; แอปโหมด Development ได้เหตุการณ์เฉพาะบัญชีที่มีบทบาทในแอป (ครอบคลุมบัญชีร้าน) และ Meta ไม่ส่งย้อนหลัง
  6. ต่ำ Takeout: สมมติโครงสร้าง location-*/reviews.json + data.json parser ทนต่อการเบี่ยงเบน (อ่านทุก reviews*.json, ชื่อจาก data.json หรือชื่อโฟลเดอร์)
  7. ต่ำ การตรวจจับสาขาจากข้อความ: ใช้ชื่อสาขาที่ยาวที่สุดที่ปรากฏ; ชื่อซ้ำซ้อน (โคราช1/โคราช2) ไม่ถูกจับ และชื่อจังหวัดในบริบทอื่นอาจจับผิด — แก้ด้วยมือได้ (ลบ/อัปโหลดใหม่) และไม่กระทบรีวิวที่มีสาขาชัดเจน
  8. ต่ำ X: ทีม Basic เสียเงินและเห็นแค่ 7 วัน; ระบบไม่ตอบทวีต (ต้อง user-context OAuth)
  9. ออกแบบ การตอบเป็นแบบ asynchronous (รอบ 09:00 หรือสั่ง replies ด้วยมือ) เพราะ credential อยู่บนเครื่อง sync ไม่ใช่บนเว็บ ถ้าต้องการ "ส่งทันที" จากปุ่ม ต้องย้าย token ขึ้น Fly secrets และเพิ่ม endpoint ส่งตรง
  10. ประสิทธิภาพ summary คำนวณใน Python เหนือทุกแถวในช่วง — สบายถึงระดับแสนแถว; เกินนั้นค่อยย้าย aggregation ลง SQL

8 คู่มือยกไปใช้ในแอปอื่น

ระบบพึ่งพาแอปแม่แค่ 5 จุด ที่เหลือคัดลอกได้ตรง ๆ (Python 3.12 stdlib + FastAPI; openpyxl เฉพาะการอ่าน XLSX)

จุดที่ผูกกับ Oshineiในโค้ดต้องแทนด้วยอะไรในแอปปลายทาง
การเชื่อมต่อฐานข้อมูลfrom core import get_dbcontext manager ที่คืน SQLite connection ที่มี row_factory = sqlite3.Row (หรือ adapter ของ DB อื่น — SQL ในไฟล์เป็น SQLite มาตรฐาน ใช้ upsert แบบ INSERT OR IGNORE + UPDATE)
สิทธิ์เขียนrequire_write_token ใน dependencies ของ endpoint ที่แก้ข้อมูลdependency ของแอปปลายทาง (token/JWT/session)
รายชื่อสาขาSELECT branch_id, name FROM branches ใน _branches()ตารางสาขา/ร้านค้าของแอปปลายทาง (ใช้จับคู่ชื่อและตรวจจับจากข้อความ)
รายชื่อเมนูSELECT description FROM skus ใน _menu_names()รายการสินค้า/เมนูของแอปปลายทาง (ใช้จับ "เมนูที่ถูกพูดถึง") หรือส่ง list ว่างถ้าไม่มี
login + write token ของตัวดึงApiSink ใน fetch_feedback.py (อ่าน .seed_tokens.txt, .refresh_login.txt)วิธี auth ของ API ปลายทาง — เปลี่ยนเฉพาะ _do_login() และ header

  3. สร้างหน้าจอตาม API ข้อ 4: การ์ดแหล่งข้อมูล (/sources), ปุ่มกรอง kind, KPI/หัวข้อ/เมนู/สาขา (/summary), รายการ (/items), แผงตอบ (/reply-draft → /reply) — js/11-feedback.js ใช้เป็นตัวอย่างการต่อ
