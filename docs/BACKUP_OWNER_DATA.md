# สำรองข้อมูลของเจ้าของระบบ (owner-data) ออกนอกเซิร์ฟเวอร์ทุกคืน

> เครื่องมือ: `scripts/backup_owner_tables.py` · ตัวรัน: `Backup Owner Data.bat` · ตัวติดตั้ง: `scripts/Setup Backup.bat`
> ฝั่งเซิร์ฟเวอร์: `GET /api/_admin/backup/owner-data.sqlite` และ `.json` (`backend/main.py`, `core.export_owner_data`)
> ทดสอบ: `backend/test_admin_backup.py`

## ทำไมต้องมี

ข้อมูลยอดขายสร้างใหม่ได้จาก MSSQL ทุกวัน แต่ข้อมูลที่พนักงานพิมพ์หรือนำเข้า **บนเว็บไซต์โดยตรง** ไม่มีที่อื่นเก็บไว้ ได้แก่ บัญชีผู้ใช้ สูตรและราคาของ BoM Center ใบสั่งซื้อ ผลตรวจนับ ผลกระทบยอด เสียงลูกค้า รายการตรวจ และค่าตั้งค่า
ข้อมูลเหล่านี้อยู่ในดิสก์ของเครื่อง Fly เพียงชุดเดียว หากดิสก์เสียหรือถูกเขียนทับ จะกู้คืนไม่ได้ จึงต้องมีสำเนาที่อยู่นอกเซิร์ฟเวอร์ทุกคืน

## สิ่งที่สำรอง

ไฟล์ SQLite หนึ่งไฟล์ ภายในมี **เฉพาะตารางที่ระบบเปลี่ยนฐานข้อมูลประจำวัน (data swap) ต้องนำข้ามไปด้วย** พร้อมโครงสร้างตาราง ดัชนี และข้อมูลครบทุกแถว
รายชื่อตารางอ่านจากตัวแปรเดียวกับที่การเปลี่ยนฐานข้อมูลใช้ (`core._PRESERVED_EXACT`, `core._PRESERVED_PREFIXES`) จึงไม่มีรายชื่อชุดที่สองให้ลืมแก้ เมื่อมีตาราง `bc_*` หรือ `recon*` ใหม่ ตารางนั้นถูกสำรองเองโดยไม่ต้องแก้อะไร

- ตัวอย่าง: `app_user`, `app_settings`, `push_subscription`, `bc_*` (สูตร ราคา ใบสั่งซื้อ ผลตรวจนับ), `recon*`, `feedback*`, `customer_feedback`, `checklist*`, `cost_override`, `stock_count`, `requisition_line`, `ingredient_order_*`
- แถวที่พนักงานแก้ด้วยมือในตาราง `ingredient_order_unit` (ขนาดแพ็ค) ถูกรวมด้วย เพราะเป็นข้อมูลที่ระบบ swap ต้องรักษาเช่นกัน (`core._MERGED_ROWS`)

**ไม่ได้สำรองไว้ในไฟล์นี้**

- ข้อมูลยอดขายและตารางที่คำนวณใหม่ (`sales_*`, `skus`, `menu_fact_*`, `bcd_*` ฯลฯ) — สร้างใหม่ได้จากการ sync MSSQL
- ไฟล์แนบของระบบกระทบยอด (สลิป ใบเสร็จ) — สำรองโดย `Backup DB.bat` ผ่าน `pull_fly_attachments.py`
- ไฟล์ลับในเครื่อง (`backend/.env`, `.seed_tokens.txt`) — `Backup DB.bat` สำเนาไว้ใน `Oshinei Backups\secrets`

งานนี้ **เสริม** `Backup DB.bat` (สำเนาฐานข้อมูลเต็มและไฟล์ `fly_state_*.ndjson.gz` เวลา 07:30) ไม่ได้แทนที่ จุดต่างคือไฟล์นี้เป็น SQLite ที่เปิดอ่านได้ทันทีพร้อมโครงสร้างตารางจริง ใช้ตรวจและกู้คืนได้ง่ายกว่า และรันแยกเวลา 02:30 จึงไม่ติดกับความล้มเหลวของงานสำรองฐานข้อมูลเต็ม

## ข้อควรระวังด้านความปลอดภัย

ไฟล์มี **รหัสผ่านที่เข้ารหัสแล้ว (hash) ของผู้ใช้ทุกคน** (`app_user`) และข้อมูลภายในของบริษัท
- ปลายทางเปิดได้ด้วย **admin token ของเจ้าของเท่านั้น** (บรรทัดที่ขึ้นต้นด้วย `admin:` หรือ token ที่ไม่มีชื่อกำกับ ใน `OSHINEI_SEED_TOKEN`) token รายบุคคลที่พนักงานพิมพ์ในปุ่ม "รหัส" ใช้ไม่ได้ และการเข้าสู่ระบบด้วยบทบาทใดก็ตามก็เปิดไม่ได้
- หากไม่มี token หรือ token ผิด ระบบตอบ 403 เสมอ (ไม่เปิดโดยปริยายแม้ยังไม่ได้ตั้ง token)
- token ส่งทาง header `X-Seed-Token` เท่านั้น ไม่อยู่ใน URL และสคริปต์ไม่พิมพ์ token ลงหน้าจอหรือไฟล์บันทึก
- ที่เก็บไฟล์ตั้งต้นคือ `%USERPROFILE%\Oshinei_backups` ซึ่ง **ไม่ซิงก์ขึ้น OneDrive** หากต้องการสำเนานอกเครื่องอีกชั้น ให้คัดลอกโฟลเดอร์นี้ไปยังที่เก็บที่เข้ารหัสเอง

## ติดตั้งบนเครื่องเจ้าของ (ครั้งเดียว)

ก่อนเริ่ม: ต้องมี admin token ใน `backend\.seed_tokens.txt` (ไฟล์ที่ sync ใช้อยู่แล้ว) หรือใน `backend\.env` เป็นบรรทัด `OSHINEI_SEED_TOKEN=...` หรือในตัวแปรสภาพแวดล้อม `OSHINEI_SEED_TOKEN`

1. ดับเบิลคลิก `scripts\Setup Backup.bat` หรือรันคำสั่งเดียวนี้จากโฟลเดอร์โปรเจกต์

   ```
   powershell -NoProfile -ExecutionPolicy Bypass -File scripts\register_owner_backup.ps1
   ```

2. ตัวติดตั้งสร้างงาน **Oshinei Owner Data Backup** ใน Task Scheduler รันทุกวันเวลา 02:30 (ถ้าเครื่องปิดอยู่ จะรันเมื่อเปิดเครื่องครั้งถัดไป) และ `Setup Backup.bat` รันสำรองหนึ่งครั้งทันที (`--once`) เพื่อให้เห็นผล
3. ตรวจบรรทัดสุดท้ายของ `%USERPROFILE%\Oshinei_backups\backup.log` ต้องเป็น `OK`
4. ถอนงานออก: `scripts\Setup Backup.bat -Remove`

ชื่องานขึ้นต้นด้วย `Oshinei` จึงอยู่ในการเฝ้าของ task watchdog อยู่แล้ว หากงานล้มเหลว พลาดรอบ หรือค้าง จะแจ้งบนหน้าแรกของผู้ดูแล (ไม่ได้เพิ่มเข้ารายการที่ watchdog สั่งรันซ้ำให้อัตโนมัติ เพราะรายการนั้นเจ้าของอนุมัติทีละงาน)

## วิธีทำงานและบันทึกผล

ทุกคืนสคริปต์ทำตามลำดับ

1. ดาวน์โหลดไฟล์ `oshinei_owner_data_YYYYMMDD_HHMM.sqlite` ไปไว้ที่ `--out` (ค่าตั้งต้น `%USERPROFILE%\Oshinei_backups`) ผ่านไฟล์ชั่วคราว
2. ตรวจไฟล์: เปิดได้ · `PRAGMA integrity_check` ได้ `ok` · จำนวนแถวของทุกตารางตรงกับที่เซิร์ฟเวอร์แจ้งมากับไฟล์นี้ · เทียบกับ endpoint `.json` อีกครั้ง (ตารางต้องครบ และแถวต้องไม่หายเกิน 10% — แถวที่เปลี่ยนระหว่างดาวน์โหลดเป็นเรื่องปกติของระบบที่ใช้งานอยู่)
3. ผ่านทุกข้อจึงเปลี่ยนชื่อเป็นไฟล์จริง และลบไฟล์เก่าเกิน `--keep` (ค่าตั้งต้น 30 ไฟล์) หากไม่ผ่าน ไฟล์ถูกเก็บเป็น `owner_data.rejected` เพื่อตรวจสาเหตุ และ **ไม่ลบไฟล์เก่าเลย**
4. เขียนหนึ่งบรรทัดลง `backup.log` เช่น

   ```
   2026-10-10 02:30:07 | OK | file=oshinei_owner_data_20261010_0230.sqlite | bytes=2695168 | tables=79 | rows=11724
   2026-10-10 02:30:07 | FAIL | reason=download: HTTP 403 from the live app (the admin token was refused)
   ```

5. จบด้วยรหัสออก 0 เมื่อสำเร็จ · 1 เมื่อล้มเหลว · 2 เมื่อไม่พบ token

บันทึกละเอียดของงานที่ตั้งเวลาอยู่ที่ `backend\logs\backup_owner_data.log`

คำสั่งเสริม (รันจากโฟลเดอร์โปรเจกต์)

| คำสั่ง | ใช้ทำอะไร |
|---|---|
| `py -3.12 scripts\backup_owner_tables.py --dry-run` | ถามเซิร์ฟเวอร์ว่าจะส่งตารางใดบ้าง กี่แถว ไม่ดาวน์โหลดไฟล์ |
| `py -3.12 scripts\backup_owner_tables.py --base http://127.0.0.1:8045 --out D:\tmp\bk` | ทดสอบกับเซิร์ฟเวอร์ในเครื่อง |
| `py -3.12 scripts\backup_owner_tables.py --keep 60` | เก็บ 60 ไฟล์แทน 30 |
| `py -3.12 scripts\backup_owner_tables.py --restore-check <ไฟล์>` | ตรวจว่าไฟล์สำรองอ่านได้ทุกตาราง |

## ตรวจว่าสำรองใช้ได้จริง (ทำเดือนละครั้ง)

```
py -3.12 scripts\backup_owner_tables.py --restore-check "%USERPROFILE%\Oshinei_backups\oshinei_owner_data_YYYYMMDD_HHMM.sqlite"
```

คำสั่งนี้คัดลอกไฟล์ไปไว้ในโฟลเดอร์ชั่วคราว เปิดแบบอ่านอย่างเดียว รัน `integrity_check` และอ่านทุกตาราง ผลที่ต้องได้คือบรรทัด `RESTORE CHECK: PASS` ไฟล์ต้นฉบับไม่ถูกแก้ไข

## กู้คืน

ห้ามกู้คืนลงฐานข้อมูลที่ใช้งานจริงโดยตรง ให้ทำในสำเนาก่อนเสมอ

1. **ตรวจไฟล์** ด้วย `--restore-check` ตามข้างต้น
2. **ลองในสำเนา** ทำสำเนาฐานข้อมูล `backend\oshinei.db` เป็นไฟล์ใหม่ เช่น `scratch.db` แล้วนำตารางจากไฟล์สำรองใส่ด้วยฟังก์ชันเดียวกับที่การเปลี่ยนฐานข้อมูลใช้ (ฟังก์ชันนี้ลบแล้วสร้างตารางใหม่พร้อมดัชนีตามไฟล์ต้นทาง)

   ```
   cd backend
   py -3.12 -c "import core; core._carry_forward_preserved(r'%USERPROFILE%\Oshinei_backups\oshinei_owner_data_YYYYMMDD_HHMM.sqlite', r'scratch.db')"
   ```

   จากนั้นเปิด `scratch.db` ตรวจจำนวนแถวของตารางที่ต้องการเทียบกับไฟล์สำรอง
3. **กู้บางตาราง** ถ้าเสียหายเฉพาะบางตาราง ให้คัดลอกเฉพาะตารางนั้นจากสำเนาที่ตรวจแล้ว (`ATTACH` ฐานข้อมูลแล้ว `INSERT ... SELECT`) ไม่ต้องแทนทั้งชุด
4. **กู้ทั้งชุดขึ้นเว็บไซต์** ถ้าตารางบนเว็บไซต์หายทั้งหมด ให้ใช้ `scratch.db` ที่ตรวจแล้วเป็นฐานข้อมูลที่ส่งขึ้น Fly ตามขั้นตอนส่งฐานข้อมูลปกติ (`Push Invisible.bat`) ระบบ swap จะรักษาตารางเหล่านี้ไว้ตามกติกาเดิม ควรแจ้งผู้พัฒนาก่อนทำขั้นตอนนี้ เพราะต้องหยุดการ sync ชั่วคราวและตรวจจำนวนแถวหลังกู้ทุกครั้ง

ทางเลือกสำหรับกู้ตารางเดียวจากไฟล์ `fly_state_*.ndjson.gz` ของ `Backup DB.bat` ยังใช้ได้เหมือนเดิม (`backend\pull_fly_state.py restore`)

## แก้ปัญหา

| อาการใน `backup.log` | สาเหตุและวิธีแก้ |
|---|---|
| `FAIL ... no admin token` | ไม่พบ token ตรวจ `backend\.seed_tokens.txt` หรือ `OSHINEI_SEED_TOKEN` |
| `HTTP 403 ... token was refused` | token ไม่ใช่ของ admin (หรือถูกเปลี่ยนแล้ว ดู `docs/TOKEN_ROTATION.md`) ให้ใช้บรรทัด `admin` ใน `backend\.seed_tokens.txt` |
| `HTTP 429` | เซิร์ฟเวอร์กำลังสร้างไฟล์สำรองอยู่ ลองใหม่ภายในหนึ่งนาที |
| `download: ... timed out` | เครือข่ายหรือแอปตอบช้า ลองรันซ้ำด้วย `Backup Owner Data.bat` |
| `FAIL ... file has N rows, the server declared M` | ไฟล์ที่ได้ไม่ครบ ไฟล์ถูกเก็บเป็น `owner_data.rejected` ให้รันใหม่ ถ้าซ้ำให้แจ้งผู้พัฒนา |
| ไม่มีบรรทัดใหม่ในวันนั้น | เครื่อง PC ปิดอยู่หรืองานไม่ทำงาน ดูแจ้งเตือนของ task watchdog และสถานะงานใน Task Scheduler |
