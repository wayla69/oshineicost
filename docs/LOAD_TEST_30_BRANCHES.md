# ทดสอบภาระงาน 30 สาขา ณ เวลาตัดรอบ (PR-G)

วันที่ทดสอบ: 2026-10-09 · ผู้ทดสอบ: Claude · ขอบเขต: เซิร์ฟเวอร์ทดสอบในเครื่อง (ไม่แตะระบบจริงบน Fly)

## 1. สรุป

- **ผลสรุป: ระบบปัจจุบันรองรับ 30 สาขาที่กดส่งพร้อมกันในช่วงตัดรอบไม่ได้** แต่รองรับได้เมื่อสาขากระจายเวลากดส่งออกไปอย่างน้อย 30 วินาที
- พบข้อผิดพลาดจริง 1 จุด: `POST /api/bom-center/order/save` ที่ส่ง `counts` มาด้วย ตอบ 500 `database is locked` เมื่อมีหลายสาขาบันทึกพร้อมกัน (หัวข้อ 5)
- ไม่พบ timeout ฝั่งผู้ใช้ และไม่พบข้อผิดพลาดนอกจาก `database is locked` ขั้นตอนดำเนินการของคลัง การรับสินค้า หน้างาน และการตรวจนับสิ้นเดือนไม่มีข้อผิดพลาดในทุกการทดสอบ
- ยังไม่เสนอให้เปลี่ยนขนาดเครื่อง Fly (หัวข้อ 7)

## 2. วิธีทดสอบ

### เครื่องมือ

- `scripts/load_branches.py` ใช้ `requests` และ thread pool ไม่ใช้เบราว์เซอร์ ยอมรับเฉพาะ `--base` ที่เป็นเครื่องเดียวกัน (127.0.0.1 หรือ localhost) หากระบุที่อยู่อื่นสคริปต์จะหยุดทันที
- `scripts/load_branches_setup.py` เตรียมฐานข้อมูลสำเนาสำหรับทดสอบ

### ลำดับที่ทดสอบในแต่ละรอบ

1. ทุกสาขาเข้าสู่ระบบพร้อมกัน แล้วเริ่มพร้อมกันด้วย barrier
2. แต่ละสาขา: หน้างาน (`GET /todo`) → เปิดแผน (`GET /order/plan`) → เลือกรอบส่ง (`GET /order/plan?round=&delivery=`) → บันทึกร่างพร้อมยอดนับ (`POST /order/save` มี `counts`) → อ่านแผนใหม่ → ส่งใบสั่งซื้อ (`POST /order/save` มี `submit`) ทุกรายการที่สั่งมียอดนับ
3. คลัง 1 บัญชี ดำเนินการทีละใบ (`POST /hub/process/{id}`)
4. ทุกสาขารับสินค้าพร้อมกัน (`POST /order/{id}/receive`) รับขาด 1 รายการ เหตุผล `short` พร้อมยืนยัน
5. ทุกสาขาเปิดใบนับสิ้นเดือนและบันทึกร่าง (`GET /stock/sheet`, `POST /stock/count`)
6. ตลอดการทดสอบ ผู้บริหาร 1 บัญชีเรียก `GET /api/reports/management` วนทุก 2 วินาที โดยเปลี่ยนสาขาและช่วงเวลาทุกครั้งเพื่อไม่ให้ถูกตอบจากแคช และเรียก `GET /api/home/brief`

### สภาพแวดล้อม

- ฐานข้อมูล: สำเนาขนาดเท่าระบบจริง (ประมาณ 1.28 GB) คัดลอกด้วย sqlite backup API ไปไว้ในโฟลเดอร์ scratchpad ไม่อยู่ในที่เก็บโค้ด และคืนค่าจากไฟล์ตั้งต้นก่อนทุกการทดสอบ
- สาขา: สาขาจริงที่เปิดอยู่ 28 สาขา และสาขาทดสอบ 32 สาขา (รหัส 901 ขึ้นไป ชื่อ `สาขาทดสอบ 01` ...) แต่ละสาขาทดสอบคัดลอกยอดขายของสาขาจริงและปฏิทินส่งของของสาขาอุดรธานี เพื่อให้แผนสั่งซื้อมีรายการจริง (ประมาณ 85–93 รายการ สั่งจริงประมาณ 45 รายการต่อใบ)
- บัญชี: `load_b01` ถึง `load_b60` บทบาทสาขา ผูกกับสาขาตามลำดับรหัส
- เซิร์ฟเวอร์: `OSHINEI_NO_SWAP=1 OSHINEI_AUTH=1 OSHINEI_HEAVY_CONCURRENCY=1` โดย `uvicorn main:app --workers 1` (กระบวนการเดียวเหมือนระบบจริง)
- เครื่องทดสอบ: Intel Core i9-13980HX (24 คอร์) RAM 32 GB

### คำสั่ง

```
py -3.12 scripts/load_branches_setup.py --db <scratch.db> --total 60
py -3.12 scripts/load_branches.py --base http://127.0.0.1:8040 --branches 30 --rounds 3 --heavy 1 \
    --create-accounts --month-end --server-log <server.err.log> --out result30.json
```

หมายเหตุ: แถวผล `4xx = 1` ที่พบทุกครั้งมาจากข้อมูลสำเนา สาขาอุดรธานีมีใบสั่งซื้อรอบ 1 ส่ง 2026-10-14 ที่รับสินค้าแล้วอยู่ก่อนแล้ว จึงบันทึกซ้ำไม่ได้ ไม่ใช่ข้อบกพร่องของระบบ

## 5. ข้อบกพร่องที่พบ

- คำขอ: `POST /api/bom-center/order/save` ที่มี `counts` (บันทึกร่างพร้อมยอดนับ) จากหลายสาขาในเวลาใกล้กัน
- ผลที่ผู้ใช้เห็น: 500 `Internal Server Error` (ข้อความไม่บอกสาเหตุ)
- บรรทัดในบันทึกเซิร์ฟเวอร์: `sqlite3.OperationalError: database is locked` ที่ `backend/bom_center/stock.py:202` (`INSERT INTO bc_stock_count` ในฟังก์ชัน `save` ถูกเรียกจาก `orders.save_flow` ที่ `orders.py:597`) พบรองลงมาที่ `stock.py:199`, `orders.py:249` และ `orders.py:267`
- สาเหตุ: `orders.save_flow` เขียนยอดนับ (เริ่มธุรกรรมเขียนของ SQLite) แล้วจึงเรียก `plan()` ซึ่งใช้ CPU หนักและ `orders.save()` ก่อนที่ `_write()` จะ commit ล็อกเขียนจึงค้างตลอดช่วงคำนวณ ซึ่งในกระบวนการเดียวที่ใช้ CPU เต็ม (GIL) ใช้เวลาหลายวินาที สาขาถัดไปรอ `busy_timeout` 5000 ms แล้วล้มเหลว
- หลักฐานสนับสนุน: ล็อกหายเมื่อกระจายเวลา 30 วินาทีขึ้นไป (เวลาแผน p50 เหลือ 0.1–0.2 วินาที) และลดลงมากเมื่อยืนยันร่างยอดนับก่อนคำนวณแผน

ไม่ได้แก้โค้ดแอปใน PR นี้

## 6. การแก้ไขที่วางแผน

สาเหตุของล็อกคือ `orders.save_flow` เขียนยอดนับก่อนเรียก `plan()` ที่ใช้ CPU หนัก ซึ่งจะแก้ใน PR-J1 (แผนที่อนุมัติแล้ว) ดังนี้

1. เอาการเขียนยอดนับนี้ออก เพราะใบสรุปตัดเบิกรายวันจะมาแทนการนับก่อนสั่ง
2. คำนวณแผนก่อนมีการเขียนใด ๆ แล้วจึงเปิดธุรกรรมเขียนสั้น ๆ ครั้งเดียว
3. แคช `forecast.usage_history` อายุ 600 วินาที เพื่อลด CPU ต่อการคำนวณแผน

หลัง PR-J1 จะทดสอบซ้ำด้วยสคริปต์นี้ และนำตัวเลขมาต่อท้ายเอกสารนี้

## 7. ข้อเสนอ

1. **คงขนาดเครื่อง `shared-cpu-2x` / 2 GB ไว้ก่อน** เซิร์ฟเวอร์เป็นกระบวนการเดียว คอขวดคือ CPU ของกระบวนการนั้น (GIL) การเพิ่มเป็น `shared-cpu-4x` / 4 GB จึงไม่แก้ปัญหานี้ ควรประเมินใหม่หลังทดสอบซ้ำจาก PR-J1
2. คง `OSHINEI_HEAVY_CONCURRENCY=1` การเพิ่มเป็น 2 ไม่ช่วย
3. แก้ที่โค้ดตามหัวข้อ 6 ก่อน (ผลที่คาดหวัง: ไม่มีล็อกที่ 30 สาขา)
4. มาตรการชั่วคราวหากต้องใช้ก่อน PR-J1: เพิ่ม `busy_timeout` เป็น 30000 ms (ทดสอบแล้วไม่มีข้อผิดพลาดที่ 30 สาขา แต่การบันทึกร่างช้าลงถึง p95 ประมาณ 18 วินาที) และขอให้สาขากระจายเวลาส่งใบสั่งซื้อ ไม่กดพร้อมกันในนาทีสุดท้ายก่อน 13:15
5. ให้ผู้บริหารเปิดรายงานหนักนอกช่วงตัดรอบ ขณะมีการบันทึกพร้อมกัน รายงานหนักช้าลงจาก 0.57 วินาทีเป็น p95 ประมาณ 23 วินาที

## 8. ข้อควรระวังในการเทียบกับเครื่องจริง

เครื่องทดสอบเป็นแล็ปท็อป 24 คอร์ ส่วน Fly ใช้ `shared-cpu-2x` ซึ่งแต่ละคอร์ช้ากว่าและใช้ร่วมกับแอปกระทบยอด (recon) บนเครื่องเดียวกัน เวลาคำนวณแผนบน Fly จึงน่าจะนานกว่านี้ ทำให้ล็อกเขียนถูกถือนานขึ้น จุดที่เริ่มมีข้อผิดพลาด (ประมาณ 10–15 สาขา) บน Fly จึงน่าจะต่ำกว่าที่วัดได้ ตัวเลขในเอกสารนี้ใช้เปรียบเทียบก่อนและหลังการแก้ไขได้ แต่ไม่ควรใช้เป็นค่าสัมบูรณ์ของระบบจริง ควรทดสอบซ้ำบนเครื่องที่ขนาดเทียบเท่าก่อนขยายเป็น 30 สาขา
