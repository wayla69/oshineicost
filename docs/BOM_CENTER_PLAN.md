## 0. บทสรุปผู้บริหาร

**ปัญหา** วันนี้ "ต้นทุนวัตถุดิบ" ของ Oshinei อยู่ 3 ที่ที่ไม่คุยกัน: (1) ไฟล์ Excel ของทีมครัว/analyst (Cost-RW 82 MB, 21 sheet, สูตรผูกกับ *ชื่อเมนู* ไม่ใช่รหัส POS, ราคาฝังอยู่ทุกบรรทัด, มี error cell 102 จุด) (2) ฐานข้อมูลแอป ซึ่งรับต้นทุนมาจาก **6 แหล่งไฟล์ซ้อนกันตามลำดับความสำคัญ** (`cost_sources.apply_all`) และยังให้ "ต้นทุนเหมา" (`sku_cost`) ชนะสูตร (BoM) เสมอ (3) การคำนวณรายเดือนด้วยมือ (ไฟล์ *Cal ต้นทุน Grandmenu* — ต้นทุน % ต่อ Tier ของอุดร) ซึ่งแอปคำนวณได้อยู่แล้วแต่ไม่มีใครเชื่อตัวเลขพอจะเลิกทำมือ ผลคือ ปรับราคาวัตถุดิบทีต้องแก้ 3,859 บรรทัด, ไม่มีประวัติราคารายเดือน, ไม่มีขั้น "ตรวจก่อนปล่อย", และแผนสั่งวัตถุดิบ "ตาบอด" เรื่องสต๊อกคงเหลือ

**สิ่งที่จะสร้าง** ศูนย์คำนวณ BoM หนึ่งเดียว (**BoM Calculation Center**) ที่ทุกฟังก์ชันในแอปเรียกใช้ — ต้นทุนเมนู, COGS/GP, ต้นทุนต่อ Tier, แผนสั่งวัตถุดิบ, ผลต่างการใช้จริง — บนหลัก **"สูตรเก็บแค่ปริมาณ · ราคาแยกเป็นรายเดือน (ราคาซื้อจริงถัวเฉลี่ยจากบัญชี) · ทุกการเปลี่ยนแปลงเป็นเวอร์ชันที่ตรวจก่อนปล่อย"** และ **Forecast Engine** ที่รู้จักรอบสั่ง (อังคาร/พุธ + ศุกร์/เสาร์, แซลมอนสด pre-order ล่วงหน้า 1 สัปดาห์), lead time, ขนาดแพ็ค และ (Phase 2) สต๊อกต้น/ปลายงวดของสาขา

**แบ่ง 2 เฟส**

### 2.2 จุดที่ต้องรื้อ (เหตุผลที่ "ซ่อม" ไม่พอ)

1. **ต้นทุนเหมาชนะสูตร** — `sku_cost ≠ 0` บังสูตรไว้ ทำให้สูตรที่ครัวแก้ "ไม่มีผล" โดยไม่มีใครเห็น (เคยกัดมาแล้ว: B0040 หอยเชลล์)
2. **ราคาฝังในบรรทัดสูตร** — 3,859 บรรทัดต้องเขียนใหม่ทุกครั้งที่ราคาเปลี่ยน; ไม่มีประวัติว่าเดือนไหนราคาเท่าไร
3. **6 แหล่งไฟล์ซ้อนกัน** — การตอบคำถาม "เมนูนี้ต้นทุนมาจากไหน" ต้องไล่ลำดับไฟล์ 6 ชั้น + provenance
4. **ไม่มี master วัตถุดิบใน DB** — DATAP อยู่ใน CSV/`ingredient_order_unit` บางส่วน; yield/loss %, ซัพพลายเออร์, ชนิด (ดิบ/กึ่งสำเร็จ/วัสดุสิ้นเปลือง) ไม่มีที่อยู่
5. **ไม่มีเวอร์ชัน/ไม่มีด่านตรวจ** — การแก้ใด ๆ มีผลทันทีกับทุกรายงานย้อนหลังทั้งประวัติ
6. **สูตรกึ่งสำเร็จไม่ระเบิดต่อ** — CK/HK/DK เป็นใบปลายทาง → แผนสั่งซื้อวัตถุดิบดิบขาด (§8)
7. **รหัสคลัง ≠ รหัสสูตร** — แก้ด้วยคอลัมน์ `recipe_codes` ใน CSV ใบคลังบังคับสั่ง + `RECIPE_CODE_TO_STOCK` ในโค้ด → ต้องเป็นตาราง alias ที่ผู้ใช้แก้ได้
8. **Tier เป็นแค่ป้าย** — ไม่มีกฎ "สูงกินต่ำได้" ในข้อมูล ทำให้ต้นทุน/Tier ต้องไปอาศัย fact ต่อบิลเท่านั้น (ถูกแต่ช้าและทำบน PC)
9. **แผนสั่งซื้อไม่รู้สต๊อก/รอบ/lead time** — เป็น "พยากรณ์การใช้" ไม่ใช่ "ยอดที่ควรสั่ง" (ตัวเองก็เตือนไว้ทุกหน้า)
10. **ตารางที่ผู้ใช้กรอกถูก DB swap ลบ** เป็นบั๊กซ้ำซาก (#209) — การออกแบบใหม่ต้องประกาศตั้งแต่ต้นว่าตารางไหนเป็นของ "เว็บ" ตารางไหนเป็นของ "PC"

## 3. หลักการออกแบบ

1. **หนึ่ง engine หนึ่งคำตอบ** — ทุกตัวเลขต้นทุนในแอปมาจาก BoM Calculation Center ผ่าน API เดียวกัน (COGS, GP, ต้นทุน/Tier, แผนสั่ง, ผลต่าง) — สอดคล้องกับงาน "one answer per question" ที่ทำไว้
2. **สูตรเก็บปริมาณ ราคาแยกรายเดือน** — `recipe_line(qty, unit)` × `ingredient_price(month)` คำนวณตอนเรียก; เปลี่ยนราคา = เพิ่ม 1 แถวต่อวัตถุดิบต่อเดือน; ราคาที่ใช้ = **ราคาซื้อจริงถัวเฉลี่ยถ่วงน้ำหนักจากบัญชี** ของเดือนล่าสุดที่ปิด (§10-1) ไม่ใช่ราคาตามใบเสนอ
3. **ทุกอย่างเป็นเวอร์ชัน และต้องตรวจก่อนปล่อย** — draft → review → released (มีผล YYYY-MM) → ผู้บริโภคอ่านเฉพาะ released; ย้อนกลับได้
4. **Tier เป็นข้อมูล ไม่ใช่ sheet** — เมนูมี `min_tier`; ลูกค้า Tier T กินเมนูที่ `min_tier ≤ T`; sheet ต่อ Tier เป็นแค่ *มุมมอง*
5. **หน่วยครัว ไม่ใช่หน่วยบัญชี** — ผู้ใช้กรอก "15 กรัม × 3 แท่ง", "1/24 แผ่น", "1 สูตร = 15,225 ml" ระบบแปลงเอง (Material Converter)
6. **Template = รูปที่ครัวใช้อยู่** — นำเข้า/ส่งออกในรูป Cost-RW ได้ (parser `prep_grand_menu_bom.py` อ่านรูปนี้อยู่แล้ว) บวกรูปแบน (CSV) สำหรับงาน bulk
7. **ตัวเลขเดิมต้องไม่กระโดดเงียบ ๆ** — Release v0 = ระบบเดิม; parity report ต่อสาขา/เมนู/Tier คือใบตรวจก่อน cut-over
8. **ของที่คนกรอกบนเว็บเป็นของเว็บ** — ตารางใหม่ทุกตารางใช้ prefix `bc_` และอยู่ใน `_PRESERVED_PREFIXES` ตั้งแต่วันแรก (ปิดบั๊กคลาส #209 เชิงโครงสร้าง)

### 5.2 UX — "ใช้งานง่าย" แปลเป็นอะไรบ้าง

- **หนึ่งหน้าหนึ่งคำถาม** (ตามกฎ nav ปัจจุบัน): *วัตถุดิบ* · *สูตรตาม Tier* · *ราคาเดือนนี้* · *ปล่อยเวอร์ชัน* · *แผนสั่ง* — เป็น cluster ใหม่ "**BoM Center**" แทน cluster จัดซื้อเดิม (3 แท็บเดิมย้ายเข้ามา ไม่ซ่อน ตามกฎ no-kill)
- **หน่วยครัวตลอดสาย**: กรอก "3 แท่ง" ระบบโชว์ "= 45 กรัม = ฿6.75"; ไม่บังคับใครคิดเป็นกรัม
- **ต้นทุนขึ้นทันที** ตอนพิมพ์ (คำนวณฝั่ง client จากราคาเดือนที่โหลดไว้ แล้วยืนยันกับ API)
- **สัญญาณไฟ 3 สี** ต่อเมนู/บรรทัด: เขียว (ครบ) · เหลือง (เตือน เช่น ฿0 ตั้งใจ, ราคาเก่ากว่า 2 เดือน) · แดง (บล็อก: ไม่มีราคา, หน่วยแปลงไม่ได้, รหัสไม่รู้จัก)
- **วางจาก Excel**: วางช่วง 3 คอลัมน์ (รหัส/ปริมาณ/หน่วย) ลงสูตรได้ตรง ๆ — ลดงานพิมพ์ซ้ำของครัว
- **Template ที่ครัวคุ้น**: export รูป Cost-RW ต่อ Tier เพื่อให้ครัวแก้ใน Excel ตามเดิมแล้วส่งกลับ (ระบบจะ diff ให้)
- **ภาษา**: ไทยเป็นหลัก ตามธีมปัจจุบัน (ฟอนต์/โทเค็นสี/กลุ่มสี ตาม `docs/ui-kit`)

### 5.3 กฎ Tier ในข้อมูล

- เมนูมี `min_tier` จาก sheet ที่มันปรากฏครั้งแรก (459 → 34 เมนู, 629 → +40, 789 → +59, 999 → +46, 1,299 → +15)
- "ตะกร้าของ Tier T" = เมนูทั้งหมดที่ `min_tier ≤ T` → ใช้ทั้งในมุมมองสูตร, ต้นทุน/Tier แบบคาดการณ์ (`tier_basket` × สัดส่วนการกินจาก fact) และตรวจความผิดปกติ ("ลูกค้า 459 กินเมนู 999" = POS/พนักงานผิดพลาด → รายงานให้ Ops)
- โปรโมชัน (เช่น 399 "4 จ่าย 3") **ดูตามราคา** — ผูกกับ Tier ฐานในตารางราคาที่ `rules.py` มีอยู่ (ยืนยัน §10-4)

### 5.5 Forecast v1 (ส่วนที่ทำใน Phase 1 — ยังไม่หักสต๊อก)

ดูรายละเอียดอัลกอริทึม §6 — ใน Phase 1 ส่งมอบ: ปฏิทินรอบสั่งต่อสาขา, cover period, lead time, แซลมอน pre-order, safety stock ตามความผันผวน (แทน buffer คงที่ 10 %), ระเบิดถึงวัตถุดิบดิบผ่านสูตรกึ่งสำเร็จ, ปัดแพ็ค/MOQ, หน้าจอ "แนะนำยอดสั่งรอบถัดไป" ต่อสาขา (ยังระบุชัดว่า *ยังไม่หักของในตู้*)

### 5.6 การย้ายข้อมูลและ parity (หัวใจความปลอดภัย)

1. **Release v0** = รัน `cost_sources.apply_all` ครั้งสุดท้าย แล้ว snapshot `sku_effective_cost` + `bom_ingredients` + `sku_cost` + overrides เข้า `bc_*` ด้วยสคริปต์ dry-run/backup ตามธรรมเนียม (`--apply` + `.pre_bc_*` backup)
2. **ทดสอบ parity v0**: COGS เดือน ก.ย. 69 รายสาขา จาก engine ใหม่ (อ่าน v0) = engine เดิม **เท่ากันทุกบาท**; golden tests ผ่านครบ → จึงเปิดให้ engine อ่านจาก `bcd_cost_cache`
3. **Release v1 draft** = นำเข้า Cost-RW (BF) + ราคาซื้อจริงถัวเฉลี่ยของเดือนล่าสุดที่บัญชีปิด (DATAP 2569-07 เก็บเป็นราคาอ้างอิงและใช้ tie-out กับ sheet) + mapping 28 ชื่อ (สูตรกึ่งสำเร็จไว้ Phase 1.5 ตาม §10-8)
4. **รายงาน v0→v1**: ต้นทุน/เมนู (194), COGS รายสาขา/เดือน, %/Tier, ความครอบคลุมจาน — คือสิ่งที่ analyst ตรวจ (น่าจะพบ: เมนูที่ v0 ใช้ต้นทุนเหมาเก่า, ทุเรียน ฿68 ที่ v1 ไม่มีถ้า sheet ไม่มี ฯลฯ) → แก้ใน draft จนยอมรับ → analyst ปล่อย v1 ภายใน 25 ธ.ค. 69 มีผล 2027-01 (ราคาซื้อจริงถัวเฉลี่ย พ.ย. 69 ตามกฎความล่าช้า §5.1-3) → management ตรวจ/รับทราบ
5. **Cut-over**: หลัง v1 ปล่อย ทุกรายงานอ่าน v1 สำหรับเดือนที่มีผลเป็นต้นไป; **ประวัติเดือนก่อนยังอ่าน v0** (ตารางเวอร์ชันมี `effective_month` — นี่คือสิ่งที่ระบบเดิมทำไม่ได้)

- **หน่วยในรายงานบัญชีสะกดหลายแบบ** (KG., Gal, แกลอน, PK, แพ็ค,ห่อ, BOT) — ตัวแปลงรวมเป็นชื่อเดียวต่อชนิดหน่วย กฎหน่วย 1 ข้อจึงครอบคลุมทุกการสะกด
- **"แพ็ค" ในบัญชีไม่ใช่แพ็คในทะเบียนเสมอ** — กุ้ง PK = 1 กก. แต่ทะเบียน (DATAP) เป็นลัง 10 กก.; ข้าว แพ็ค = 5 กก. ไม่ใช่กระสอบ 25 กก. ถ้าเชื่อตรง ๆ ราคาต่อกรัมผิด 5–10 เท่าโดยไม่มีใครเห็น → ระบบปฏิเสธการแปลงผ่านแพ็คที่ทำให้ราคาห่างราคาล่าสุดเกิน 2.5 เท่า และเสนอกฎหน่วยที่ถูก (51 ข้อ, 45 ข้อสม่ำเสมอ) ให้ analyst ติ๊กรับทีเดียว
- **รหัสที่บัญชีจ่ายแต่สูตรไม่รู้จัก** (เช่น ทุเรียน FV00043 ฿2.9M/เดือน) — เพิ่มเข้าทะเบียนได้อัตโนมัติพร้อมหน่วยฐานที่เดาจากหน่วยที่ซื้อ ติดหมายเหตุให้ตรวจ; การโยง FV00043 ↔ EST-DURIAN ของสูตรทำใน S2
- งานข้อมูลที่เหลือของ analyst: 11 รายการไม่มีหน่วยฐาน · 89 รายการดิบไม่มีขนาดบรรจุ · 6 กฎแพ็คที่ค่าไม่สม่ำเสมอ

### 5.8 Phase 1.5 — สูตรกึ่งสำเร็จ (2 สัปดาห์ ต่อจาก S5 · §10-8)

ครัวมีสูตรกึ่งสำเร็จอยู่แล้ว (รูปแบบ `BoM_Semi`: "1 สูตร = 15,225 ml" + วัตถุดิบ 1–15 รายการ) เจ้าของให้ทำเป็นเฟสถัดไปโดยวางโครงไว้ก่อน

- **งาน**: นำเข้า `BoM_Semi` ฉบับปัจจุบันเข้า `bc_prep_recipe*` (yield ต่อ batch, หน่วย batch) → ต้นทุนต่อหน่วยฐานของ CK/HK/DK คำนวณจากวัตถุดิบดิบ × ราคาซื้อจริง → `explode()` ลงถึงดิบ → ด่านตรวจข้อ 10 เปลี่ยนจาก "เตือน" เป็น "บล็อก" → แผนสั่ง/forecast อ่านวัตถุดิบดิบที่อยู่ในของกึ่งสำเร็จ
- **เกณฑ์ตรวจรับ**: ต้นทุน CK-001/CK-013 ที่คำนวณจากสูตร ต่างจากราคาซื้อ/อ้างอิงของมัน ≤ 5 % (มากกว่า = ครัวตรวจ yield); แผนสั่งแสดงแซลมอน/ซอส/ข้าวที่อยู่ข้างในของกึ่งสำเร็จ และผลรวมความต้องการแซลมอนดิบเพิ่มขึ้นจาก Phase 1 อย่างอธิบายได้
- **ทำไมต้องก่อน Phase 2**: ยอดสั่งแนะนำที่สาขาจะเห็นต้องรวมวัตถุดิบดิบในของกึ่งสำเร็จ ไม่อย่างนั้นสาขาจะเห็นว่าระบบ "สั่งแซลมอนน้อยไป" ตั้งแต่วันแรกและเลิกเชื่อ

## 6. Forecast Engine — รายละเอียด

### 6.1 อินพุต
- ยอดขายรายวันต่อสาขาต่อเมนู (`sales_sku_daily`) ย้อน 8–12 สัปดาห์ · ปฏิทินวันหยุด/เทศกาล (`demand_calendar` เดิม + season factor ที่มีอยู่) · สูตร release ปัจจุบัน (+ สูตรกึ่งสำเร็จและ yield ตั้งแต่ Phase 1.5) · ปฏิทินรอบสั่ง 2 รอบต่อสาขาที่ฝ่ายขายเติม (รอบ 1 อังคาร/พุธ, รอบ 2 ศุกร์/เสาร์, วันแซลมอน — §10-7) · lead time/MOQ/แพ็คต่อวัตถุดิบ · ราคาซื้อจริงถัวเฉลี่ยเดือนล่าสุด (คิดมูลค่าออเดอร์) · (Phase 2) สต๊อกนับล่าสุด + ของที่สั่งแล้วยังไม่ถึง

### 6.2 ขั้นคำนวณ (ต่อสาขา × วัตถุดิบ × รอบสั่ง)

1. **พยากรณ์จานต่อวัน** ต่อเมนู: baseline แบบ *weekday-fair* (ค่าเฉลี่ยวันเดียวกันของสัปดาห์ 4–6 สัปดาห์ล่าสุด — หลักเดียวกับ MTD baseline ที่ใช้ในรายงาน) × แนวโน้ม (2 สัปดาห์ล่าสุด ÷ 2 สัปดาห์ก่อน, จำกัด 0.7–1.3) × season/event factor (ของเดิม)
   - ทางเลือกที่ทนกว่าเมื่อลูกค้าผันผวน: *อัตราต่อหัว* (จาน/คน รายวันของสัปดาห์) × *พยากรณ์จำนวนลูกค้า* (มีอยู่ใน `buffet_forecast`) — เลือกวิธีที่ MAPE ย้อนหลังต่ำกว่าต่อสาขา (auto-select)
2. **ระเบิดสูตร**: จาน × ปริมาณ/เสิร์ฟ → หน่วยฐาน; ของกึ่งสำเร็จระเบิดต่อถึงดิบ; หาร yield (1 − loss %) → ปริมาณ *ซื้อ*
3. **Cover period** จากปฏิทิน: สั่งอังคาร → ส่งพุธ/พฤหัส → ต้องพอถึงของรอบศุกร์/เสาร์มาถึง; รอบศุกร์คลุมสุดสัปดาห์+ต้นสัปดาห์ (หนักกว่า) → cover days ต่างกันต่อรอบ; **แซลมอนสด**: รอบสัปดาห์เดียว, สั่งล่วงหน้า 7 วัน → horizon = วันส่งถึง +7 วัน
4. **Safety stock** = ค่าควอนไทล์ของการใช้รายวันในอดีต × √(cover days) ตามระดับบริการต่อชั้นวัตถุดิบ (A โปรตีน 95 %, B 90 %, C 85 %) — แทน buffer คงที่ 10 %; ปรับอัตโนมัติจากความแม่นย้อนหลัง (ต่อยอด `/api/ingredients/order-accuracy` ที่มี)
5. **ยอดแนะนำ** = (พยากรณ์ช่วง cover + safety) − สต๊อกคงเหลือ (Phase 2) − ของค้างส่ง → ปัดขึ้นเป็นแพ็ค → MOQ → ไม่ติดลบ; แสดง "หน่วยสั่ง (= หน่วยฐาน)" และมูลค่า
6. **บันทึก run** (`bc_forecast_run`) เป็น snapshot ที่ compliance อ้างอิง (หลักเดียวกับ issue เดิม: ตัดสินสาขาด้วยตัวเลขที่แช่แข็ง ไม่ใช่ตัวเลขที่คำนวณใหม่ทีหลัง)

### 6.3 เอาต์พุต
- หน้า "แนะนำยอดสั่งรอบถัดไป" ต่อสาขา: ตารางวัตถุดิบ (เรียงตามมูลค่า), ยอดแนะนำ/แพ็ค/฿, เหตุผลสั้น (พยากรณ์ X + กันเหนียว Y − คงเหลือ Z), ธงบังคับสั่ง/นำเข้า/แซลมอน; Excel ต่อสาขา; จดหมายสั่ง (ของเดิม) อ่านจาก run
- **ความแม่น**: MAPE ต่อวัตถุดิบ/ชั้น/สาขา ทุกสัปดาห์ (เทียบกับการใช้ตามทฤษฎีใน Phase 1, กับการใช้จริงใน Phase 2) → หน้าจอ + ปรับ safety อัตโนมัติ

## 7. Phase 2 — สาขา (10 สัปดาห์ + pilot 4 สัปดาห์)

### 7.1 ขอบเขตตามความต้องการ

| ข้อ | ความต้องการ | สิ่งที่ส่งมอบ | เกณฑ์ตรวจรับ |
|---|---|---|---|
| 1 | ใส่ beginning stock | หน้า "นับสต๊อก" มือถือ: รายการตามโซนเก็บ (แช่แข็ง/แช่เย็น/แห้ง) ในหน่วยครัว, ค่าครั้งก่อนแสดงจาง, รูปแนบ (ไม่บังคับ), ต้นงวดครั้งแรกเท่านั้น — รอบถัดไป **ปลายงวดเดิม = ต้นงวดใหม่อัตโนมัติ** | นับครบรายการบังคับ (A-class) ≤ 20 นาที; ไม่ต้องกรอกต้นงวดซ้ำ |
| 2 | แจ้งการใช้ตาม BoM | หน้า "การใช้ตามสูตร" ต่อช่วงนับ: ยอดขาย × สูตร (release เดือนนั้น) ต่อวัตถุดิบ, แยกเมนูต้นทาง (drill) | ตรงกับ `bcd_demand_day` รวมช่วง; มีลิงก์ไปเมนู |
| 3 | ใส่ ending stock ก่อนสั่ง | ปุ่ม "นับก่อนสั่ง" ในหน้าสั่งของ → บันทึก `kind='end'` ประทับเวลา; ไม่นับ = สั่งได้แต่ติดป้าย "ไม่หักสต๊อก" (ไม่ปิดกั้น — ตามกฎ no-kill/adoption) | ทุกออเดอร์บันทึกว่ามี/ไม่มีการนับ |
| 4 | เทียบ actual vs BoM | ผลต่าง = (ต้น + รับเข้า − ปลาย) − ทฤษฎี; รายวัตถุดิบ/รอบ/สาขา; % และ ฿; เกณฑ์ตามชั้น (A ±5 %, B ±10 %, C ±20 %); รหัสเหตุผลที่สาขากรอก (ของเสีย/หมดอายุ/ชิม-พนักงาน/ตักเกิน/โอนสาขา/นับผิด/อื่น) | ผลต่างคำนวณได้เมื่อมีนับปลาย+ต้น+รับเข้าครบ; ไม่ครบ → แสดง "ไม่สมบูรณ์" ไม่เดา |
| 5 | รายงานวิเคราะห์ให้ Ops ตรวจต่อ | หน้า "ผลต่างการใช้" (Ops): สาขา × วัตถุดิบ heatmap, Top gap ฿, แนวโน้ม 8 รอบ, แยก "ยังไม่มีเหตุผล", ส่งออก Excel/พิมพ์ A4 (รูปแบบจดหมายเดิม) | Ops เลือกสาขา/ช่วง แล้วได้รายการตรวจ ≤ 10 บรรทัด/สาขา เรียงตาม ฿ |
| 6 | แนะนำยอดสั่ง ตามรอบ 2 ครั้ง/สัปดาห์ + แซลมอนรายสัปดาห์ | Forecast Engine §6 เต็มรูป (หักสต๊อก/ค้างส่ง); **ตารางรอบสั่งต่อสาขาที่ฝ่ายขายเติมเอง** (รอบ 1 เลือกอังคาร/พุธ, รอบ 2 เลือกศุกร์/เสาร์, วันสั่งแซลมอน, วันส่งถึง) — หน้า "ตั้งค่ารอบสั่ง" เป็นตารางสาขา × รอบ แก้ได้ทันที มีผลรอบถัดไป (§10-7); แจ้งเตือน "วันนี้วันสั่ง" | ยอดแนะนำพร้อมก่อน 10:00 ของวันสั่งตามตารางของสาขานั้น; แซลมอนแสดงรอบส่งถึงล่วงหน้า 7 วัน |
| 7 | หน้าสาขาสั่งของ ยอดแนะนำเป็นตัวตั้ง ยืนยัน/แก้ได้ | หน้า "สั่งของรอบนี้": ยอดแนะนำ (ล็อกเป็นค่าตั้ง), ช่องแก้, ถ้าเบี่ยง > เกณฑ์ต้องเลือกเหตุผล, สรุป ฿, ส่ง (status submitted) → **เข้าคิวของส่วนกลาง Sales Support** ซึ่งเป็นผู้ดำเนินการต่อ (§10-6, §7.5) | สั่ง 48 รายการบังคับได้ใน ≤ 5 นาที บนมือถือ; ทุกการแก้มีเหตุผล; ส่งแล้วสาขาเห็นสถานะ "ส่วนกลางรับแล้ว / ดำเนินการแล้ว" |
| 8 | Ops ตรวจว่าสาขาสั่งตามควร | หน้า "Compliance การสั่ง": แนะนำ vs ยืนยัน (สาขา) vs ดำเนินการ (Sales Support) vs รับจริง ต่อรอบ/สาขา; สถานะ ok/under/over/not_ordered/not_submitted; จดหมายเตือน (ของเดิมย้ายมาอ่าน `bc_order`) | รายงานพร้อมทันทีหลังสาขาส่ง; ไม่ต้องกรอก actual มือถ้าสาขาใช้หน้าสั่ง |
| 9 | สรุปผลต่างรายเดือน | รายงานเดือน: ผลต่าง ฿/% ต่อสาขา, ต่อชั้นวัตถุดิบ, เหตุผล Top 5, ปรับปรุงจากเดือนก่อน, เทียบ "เบิกจริง" (requisition) ถ้ามี; ลงใน Management Report เป็น § ใหม่ | ออกอัตโนมัติวันที่ 2 ของเดือน (หลัง sync ปิดเดือน) |

### 7.2 หน้าจอสาขา (มือถือก่อน · 375 px ตามแนว mobile deep summary)

1. **หน้าแรกสาขา**: วันนี้ต้องทำอะไร (นับ? สั่ง? แซลมอน?), ผลต่างรอบล่าสุด 3 บรรทัด
2. **นับสต๊อก**: โซน → รายการ → ตัวเลขใหญ่ + หน่วยครัว + ปุ่ม ±; ค้างไว้ได้ (draft) ; ส่ง
3. **สั่งของ**: ตาราง 3 คอลัมน์ (ชื่อ · แนะนำ · สั่ง) + เหตุผลเมื่อเบี่ยง; แท็บ "แซลมอนสด"
4. **ผลต่างของฉัน**: 10 รายการ gap มากสุด + กรอกเหตุผล

### 7.3 Pilot และการขยาย
- **Pilot 4 สาขา 4 สัปดาห์: อุบลราชธานี · อุดรธานี · ขอนแก่น · ระยอง** (เจ้าของเลือก §10-11; อุดรมีไฟล์ Cal ต้นทุนเป็นฐานเทียบอยู่แล้ว, ระยองเคยมีบรรทัด POS ผิดปกติ qty 1e9 จึงเหมาะทดสอบ guard, ขอนแก่นมี branch report เดิมไว้เทียบ) → ปรับหน่วยครัว/เกณฑ์/เหตุผล → ขยายทุกสาขา master → franchise
- เกณฑ์ผ่าน pilot: นับครบ ≥ 90 % ของรอบ, เวลานับ ≤ 20 นาที, ผลต่างมีเหตุผล ≥ 80 %, MAPE A-class ≤ 15 %

### 7.5 ส่วนกลาง — Sales Support (§10-6)

สาขาไม่ส่งออเดอร์ให้ซัพพลายเออร์เอง ทุกออเดอร์ที่สาขายืนยันเข้าคิวของทีม Sales Support ส่วนกลาง ซึ่งเป็นผู้ดำเนินการต่อ

- **หน้า "คิวออเดอร์"**: ออเดอร์ที่ status = submitted ทุกสาขา จัดกลุ่มตามรอบ/วันส่ง; เปิดดูรายสาขา (แนะนำ vs สาขายืนยัน vs เหตุผล); แก้ปริมาณที่จะดำเนินการได้พร้อมเหตุผล (เช่น ของขาด ส่งเท่าที่มี); กด "ดำเนินการแล้ว" → status processed, บันทึก `processed_by/processed_at/po_ref`
- **รวมออเดอร์**: มุมมอง "ต่อซัพพลายเออร์ × วันส่ง" และ "ต่อสาขา" → ส่งออก Excel/ใบสั่งซื้อ (รูปแบบที่ Sales Support ใช้อยู่วันนี้ให้ส่งตัวอย่างใน S0) ; API ไปซัพพลายเออร์เป็นงานภายหลัง
- **สถานะกลับไปสาขา**: สาขาเห็น "ส่วนกลางรับแล้ว / ดำเนินการแล้ว / ส่งแล้ว" ในหน้าสั่งของ และยืนยันรับของเป็นขั้นสุดท้าย (received)
- **เกณฑ์การให้บริการ**: ออเดอร์ที่ส่งก่อน 10:00 ของวันสั่ง ถูกดำเนินการภายใน 14:00 วันเดียวกัน; รายงาน SLA ต่อรอบ
- **สิทธิ์**: module `scm.orders` (role ใหม่ `salessupport` หรือเพิ่มให้ role ที่มีอยู่ — ตัดสินใน S6)
- **ผลต่อ compliance**: Ops เทียบ 4 ค่า (แนะนำ · สาขายืนยัน · ส่วนกลางดำเนินการ · สาขารับจริง) จึงแยกได้ว่าผลต่างเกิดที่สาขา ส่วนกลาง หรือการส่ง

| S6 | **ราคาซื้อจริงต่างกันระหว่างสาขา/ภูมิภาค** | เมื่อ BoM ใช้ราคาซื้อจริงถัวเฉลี่ย (§10-1) สาขาที่ซื้อแพงจะ "ซ่อน" อยู่ในค่าเฉลี่ย; ของสดซื้อท้องถิ่นเคยพบจ่ายเหนือ median ฿134 k ใน 2 เดือน | M4 เก็บราคาซื้อจริง *ต่อสาขา* ด้วย (`bc_ingredient_price_branch`): ค่าเฉลี่ยเครือข่ายใช้คิด BoM, ค่าต่อสาขาใช้รายงาน "ราคาต่างกันระหว่างสาขา" (สาขา vs ค่ากลาง ±%) |
| S7 | **รวมออเดอร์สาขาเป็น PO ส่วนกลาง** | สาขายืนยันแล้วใครส่งต่อ? วันนี้เป็น LINE/Excel | `bc_order` → รวมเป็นไฟล์ PO ต่อซัพพลายเออร์/ต่อวันส่ง (Phase 2 S9) ; API ซัพพลายเออร์ภายหลัง |
| S8 | **มาตรฐาน yield ต่อปลา** (sheet Yield-Salmon เดิม) | yield ที่ใช้ใน DATAP (แซลมอน 40 %) ควรมาจากการวัดจริงเป็นรอบ ไม่ใช่ค่าคงที่ | M1 `loss_pct` มีประวัติ + หน้าบันทึกผล yield test |
| S9 | **KPI ของ SCM**: service level (สั่งแล้วได้ครบตรงเวลา), forecast MAPE, cover days, PPV | ไม่มีตัวชี้วัดฝั่งจัดซื้อในแอปเลย | หน้า "SCM Scorecard" (S9) |
| S10 | **ของเสีย/ทิ้ง (waste log)** แยกจากผลต่าง | ผลต่างบอกแค่ "หาย" ไม่บอก "ทิ้งเพราะอะไร" | รหัสเหตุผลใน §7 + บันทึก waste รายวันแบบง่าย (ทางเลือก) |

## 11. KPI · ความเสี่ยง · ข้อห้าม

### 11.1 KPI ความสำเร็จ

| ตัวชี้วัด | เป้า | วัดจาก |
|---|---|---|
| จานที่ขายและมีสูตรใน release ปัจจุบัน | ≥ 98 % | `coverage(month)` (นิยามเดียวกับ `rules.needs_cost_sql`) |
| เวลาปรับราคาวัตถุดิบทั้งเดือน | ≤ 1 วันทำงาน | timestamp import → released |
| เวลาตรวจ/ปล่อยเวอร์ชัน | ≤ 3 วัน | draft → released |
| ต้นทุน % ต่อ Tier อัตโนมัติ | วันที่ 1 ของเดือน; ต่างจากไฟล์มือ ≤ 1 pp | เทียบ Cal ต้นทุน 2 เดือน |
| MAPE forecast วัตถุดิบ A-class | ≤ 15 % | `bc_forecast_run` vs การใช้ |
| ผลต่างที่มีเหตุผล | ≥ 80 % ของ ฿ gap | `bc_variance` |
| Compliance การสั่ง | ≥ 90 % รายการ ok | `bc_order` |
| เวลานับสต๊อกต่อรอบ (A-class) | ≤ 20 นาที | timestamps นับ |

### 11.2 ความเสี่ยงและการป้องกัน

| ความเสี่ยง | ป้องกัน |
|---|---|
| ตัวเลข COGS ทุกรายงานเปลี่ยนตอน cut-over | Release v0 + regression 4 รายงาน + รายงาน v0→v1 ที่ analyst ลงชื่อและ management รับทราบ; ประวัติเดือนก่อนอ่าน v0 |
| ราคาซื้อจริงจากบัญชีมาช้า (บัญชีปิดเดือนหลังวันที่ 25) หรือเดือนนั้นไม่มีการซื้อบางรหัส | กฎ "เดือนล่าสุดที่ปิด" + ราคาล่าสุดที่มี + ธงอายุราคา + แก้มือรายรหัสพร้อมเหตุผล; เดือนที่ปิดทันใช้ทันที |
| ราคาถัวเฉลี่ยกลบความต่างระหว่างสาขา | เก็บค่าต่อสาขาคู่กัน (`bc_ingredient_price_branch`) + รายงานราคาต่างกันระหว่างสาขา (§8-S6) |

| สาขาไม่นับ/นับมั่ว | ไม่บังคับแต่ติดป้าย; KPI การใช้งาน; blind count; pilot ก่อน |
| ประสิทธิภาพ (650 k แถวรายวัน × สูตร) | `bcd_demand_day` incremental; cache เดิม; heavy cap |
| ขอบเขตบาน (AL, ของหวาน, เครื่องดื่ม, คลังกลาง) | ประตูเฟสชัด; AL = 2 สัปดาห์หลัง P1; คลังกลางเป็นรายงานไม่ใช่ WMS |

### 11.3 ข้อห้ามและการกู้คืน (ตามธรรมเนียมแผนในโปรเจกต์นี้)

- **ห้าม** ลบ/เปลี่ยนชื่อตารางเดิมใน Phase 1; **ห้าม** แก้ `rules.cogs_expr` ให้ตัวเลขเดิมเปลี่ยนโดยไม่มี parity report; **ห้าม** deploy นอก `deploy-clean.sh`; **ห้าม** ทำงานบน branch ค้างในโฟลเดอร์ที่ scheduler ใช้ (ใช้ worktree)
- ทุกสคริปต์ย้ายข้อมูล: dry-run ค่าเริ่มต้น, `--apply` สำรอง `.pre_bc_*` ก่อน, idempotent
- กู้คืน: `bc_release` ย้อนเป็นเวอร์ชันก่อนได้ 1 คลิก (engine rebuild `sku_effective_cost` จาก cache ของเวอร์ชันนั้น); ฐานข้อมูลตาม `Backup DB.bat`/fly_state รายคืน

## ภาคผนวก B — อภิธานศัพท์

- **Release / เวอร์ชัน** — ชุดสูตร+ราคาที่ตรวจแล้ว มีเดือนที่มีผล; ทุกรายงานอ้างอิงเวอร์ชันของเดือนนั้น
- **หน่วยฐาน** — กรัม/มิลลิลิตร/ชิ้น ที่สูตรนับ; **หน่วยรับ** — แพ็ค/ถุง/กก. ที่ซื้อ; **หน่วยครัว** — แท่ง/แผ่น/ถ้วย ที่คนครัวพูด
- **Yield / loss %** — สัดส่วนที่ใช้ได้หลังตัดแต่ง (แซลมอน 60 %)
- **ของกึ่งสำเร็จ (prepared)** — CK/HK/DK ที่ร้านทำเองจากวัตถุดิบดิบ มีสูตรและ yield ต่อ batch
- **ตะกร้า Tier** — เมนูทั้งหมดที่ลูกค้า Tier นั้นกินได้ (`min_tier ≤ T`)
- **Cover period** — ช่วงวันที่ของรอบสั่งหนึ่งต้องพอใช้จนของรอบถัดไปมาถึง
- **การใช้ตามทฤษฎี** — ยอดขาย × สูตร; **การใช้จริง** — ต้นงวด + รับเข้า − ปลายงวด; **ผลต่าง** — จริง − ทฤษฎี
- **ราคาซื้อจริงถัวเฉลี่ย** — Σมูลค่าที่ซื้อ ÷ Σปริมาณที่ซื้อ ต่อรหัสต่อเดือน จากรายงานซื้อของบัญชี; ใช้คิด BoM แทนราคาตามใบเสนอ (ซึ่งเก็บเป็นราคาอ้างอิง)
- **Sales Support** — ทีมส่วนกลางที่รับออเดอร์ที่สาขายืนยันแล้วไปดำเนินการต่อกับคลัง/ซัพพลายเออร์ (status processed)
