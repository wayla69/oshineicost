Executive summary

Phase D คืออะไร ในสามบรรทัด

ภาคต่อหลังจาก Phase A–C พิสูจน์ “คุณค่า” ของแอปแล้ว (buffet-leak guard, ROI ledger, food-cost benchmark, exec summary, targets). Phase D คือก้าวที่เปลี่ยน “ของที่ใช้ดี” ให้กลายเป็น “ของที่ขายต่อได้”.

The deal

  • 1
    หลายผู้เช่า (multi-tenant): ร้านอื่นสมัครเข้ามาใช้แดชบอร์ดเดียวกันได้ ข้อมูลของแต่ละเชนแยกขาด 100% — เห็นข้ามกันไม่ได้เด็ดขาด เพราะนี่คือ ข้อมูลต้นทุนและกำไร ที่ลับที่สุดของลูกค้า
  • 2
    สมัคร + นำเข้าข้อมูลได้เอง (self-serve onboarding): tenant ใหม่กรอกข้อมูล อัปโหลด Easy POS export / BoM Excel แล้วระบบ seed ค่าตั้งต้น + ผู้ใช้ + สิทธิ์ ให้อัตโนมัติ
  • 3
    เก็บเงินเป็นแพ็กเกจ (billing): แบ่ง plan ตามจำนวนสาขา / ประวัติข้อมูล / live-sync เป็น add-on — แอปกลายเป็นรายได้ประจำ (recurring revenue) ไม่ใช่ต้นทุน
📌
ตัดสินใจไว้แล้วว่า “ยังไม่ทำตอนนี้” — เจ้าของเลือกแยก Phase D เป็นโปรเจกต์ของมันเอง ไม่มัดรวมกับ A–C เพราะมันคือการ rewrite ขนาดใหญ่ (62 ตาราง / ~167 endpoint). เอกสารหน้านี้คือ design doc ที่ roadmap กำหนดให้ทำก่อน แล้วค่อยเคาะ go / no-go.

The shift

จากวันนี้ → ปลายทาง Phase D

  • SQLite ไฟล์เดียว /data/oshinei.db เก็บข้อมูลของ Oshinei รายเดียว

  • ~167 endpoint query ตรงไปที่ตาราง โดยไม่มีแนวคิด “เจ้าของข้อมูล”
  • นำเข้าข้อมูลด้วยมือผ่าน .bat / CLI (operator รัน)
  • Live sync ผูกกับ MSSQL HQ ของ Oshinei โดยเฉพาะ
  • ไม่มีการเก็บเงิน / ไม่มี plan / ไม่มี onboarding
→

🎯 ปลายทาง — Multi-tenant SaaS

  • ทุกตารางมี tenant_id; ข้อมูลแต่ละเชนแยกขาด (เชิงกายภาพหรือเชิง schema)
  • Auth รู้จัก tenant — session ผูก tenant_id; ข้ามเช่ากันไม่ได้
  • ทุก query ถูก scope ด้วย tenant อัตโนมัติผ่าน accessor กลาง
  • tenant สมัคร + อัปโหลดข้อมูลเองผ่าน onboarding wizard
  • Live sync เป็น add-on ต่อ tenant (creds แยกต่อราย)
  • Plan / subscription / metering + super-admin console
Architecture · การตัดสินใจที่ใหญ่ที่สุด

โมเดลการแยกข้อมูล (isolation model)

นี่คือการเลือกที่กำหนดทุกอย่างหลังจากนั้น เพราะข้อมูลคือ ต้นทุน/กำไรที่อ่อนไหวสูง — การรั่วข้ามเช่าหนึ่งครั้ง = จบเกมความน่าเชื่อถือ. มีสามทางหลัก:

ทางเลือกการแยกข้อดีข้อเสียเหมาะกับ
DB-per-tenant
แนะนำ v1
SQLite ไฟล์ละ tenant		 เชิงกายภาพ — คนละไฟล์ รั่วข้ามกันแทบเป็นไปไม่ได้ ใกล้เคียงโค้ดเดิมที่สุด (เปิดไฟล์ตาม tenant), backup/restore ต่อรายง่าย, ปลอดภัยที่สุด query ข้าม tenant (analytics รวม) ทำยาก, จำนวนไฟล์เยอะเมื่อ scale มาก 10–200 tenants
Shared schema + tenant_id
SQLite ไฟล์เดียว		 เชิงตรรกะ — ทุกแถวมี tenant_id, ทุก query ต้อง WHERE โครงสร้างเดียว ดูแลง่าย, รายงานรวมข้าม tenant ทำได้ทันที เสี่ยงรั่ว ลืม WHERE แถวเดียว = leak; SQLite เขียนพร้อมกันหลาย tenant คอขวด prototype
Postgres + RLS
Row-Level Security		 เชิงตรรกะ + บังคับที่ DB — policy กรอง tenant ให้เองทุก query scale + concurrency จริงจัง, RLS เป็นตาข่ายนิรภัยระดับ DB, มาตรฐาน SaaS ต้อง ย้ายจาก SQLite (rewrite query บางส่วน + ops ใหม่), ลงทุนสูงสุด scale 100+ / ระยะยาว
🧩
คำแนะนำเชิงกลยุทธ์: เริ่ม v1 ด้วย DB-per-tenant (SQLite) — ได้ความปลอดภัยสูงสุดโดยแตะโค้ดเดิมน้อยที่สุด (โค้ดทุกวันนี้ก็ทำงานกับ SQLite ไฟล์เดียวอยู่แล้ว แค่เปลี่ยนเป็น “เลือกไฟล์ตาม tenant”). วาง abstraction การเชื่อมต่อ DB ให้สลับไป Postgres + RLS ได้ภายหลังเมื่อจำนวน tenant โตจนคุ้มค่าย้าย. การ query รวมข้ามเช่า (เช่น industry benchmark) ทำเป็น aggregation นอกเส้น request.

Workstreams D1 – D7

D1

Tenant data model & การแยกข้อมูล

XL

รากฐานของทุกอย่าง — เพิ่มมิติ “เจ้าของข้อมูล” เข้าไปทั้งสคีมา.

  • เพิ่มตาราง tenant (id, slug/subdomain, name, plan, status, settings JSON, created_at)
  • เติม tenant_id FK ลงทั้ง 62 ตาราง (branches, skus, sku_cost, sales_sku_monthly, sales_transaction, sales_month_summary, branch_targets, app_settings, bom_ingredients, cost_scenario, app_user, sale_bill_item, *_archive ฯลฯ)
  • เปลี่ยน natural key ให้เป็น composite — เช่น receipt_no ที่ไม่ unique ทั่วระบบอยู่แล้ว → (tenant_id, receipt_no)
  • เลือก isolation model (จากหัวข้อด้านบน) แล้วเขียน migration backfill ข้อมูลเดิมเป็น tenant_id = 1 (Oshinei)
แตะ: backend/main.py (init_db/schema)migration script ใหม่ทุกตารางใน oshinei.db
D2

Auth & request scoping ที่รู้จัก tenant

L

ต่อยอดจาก RBAC ที่มีแล้ว — เพิ่มมิติ tenant เหนือมิติ role.

  • resolve tenant จาก subdomain (acme.oshinei.app) หรือจาก login → ฝัง tenant_id ใน session cookie (HMAC-signed อยู่แล้ว, 12h)
  • ขยาย backend/auth.py: path_allowed() + middleware enforce_auth ให้บังคับ tenant boundary — ปฏิเสธ request ที่ข้าม tenant ทันที
  • ทำ accessor กลาง tdb(tenant_id) — ทุก handler ดึง connection/scope จากตรงนี้ ไม่ใช่ต่อ DB ตรง ๆ
  • เพิ่ม role super-admin ข้าม tenant + เส้นทาง impersonation สำหรับซัพพอร์ต
แตะ: backend/auth.pyenforce_auth middlewarerequire_write_token
D3

Refactor endpoint ~167 ตัว

XL

งานหนักที่สุดเชิงปริมาณ — ทุก endpoint ต้องถูก scope และพิสูจน์ว่าแยกจริง.

  • ทำ inventory endpoint ทั้งหมด แล้วจัดกลุ่ม: data-read / mutation / export / admin
  • ฉีด tenant scope ผ่าน accessor กลาง (D2) — อย่าแก้ทีละ handler เพราะลืมตัวเดียว = รั่ว
  • เขียน isolation test matrix: สร้าง 2 tenant แล้วยืนยันทุก endpoint ว่า tenant A เห็นข้อมูล tenant B ไม่ได้
  • ผูก write-token / RBAC module gate เข้ากับมิติ tenant ด้วย
แตะ: backend/main.py (~8.5K บรรทัด)test_auth.py → test_tenant_isolation.py
D4

Self-serve onboarding & data import

L

เปลี่ยนการนำเข้าข้อมูลจาก “operator รัน .bat” → “ลูกค้าทำเองได้”.

  • signup flow → provision tenant + seed ค่าตั้งต้น (categories, app_settings, default users + RBAC roles)
  • import wizard: reuse upload_data.py (ตัวอัปโหลด canonical ตัวเดียว) + parser Easy POS export + BoM Excel + sku_cost mapping — ทำให้ tenant-scoped และมีไกด์
  • ใช้ coverage guard เดิม (missing last-day, VAT column quirks, sku_cost-is-price) ซ้ำได้เลย — ทุก tenant เจอ quirk แบบเดียวกัน
  • Live MSSQL sync (sync_mssql.py) = add-on ระดับพรีเมียมต่อ tenant (creds แยกราย); v1 onboarding เป็น file-upload ก่อน
แตะ: backend/upload_data.pysync_mssql.pyonboarding UI ใหม่

D6

Infra, data store & ops

L

รันคู่ขนานกับ D1 — เพราะการเลือก store กำหนดทุกอย่าง.

  • ตัดสินใจ store: SQLite-per-tenant บน Fly volume (ใกล้เคียงโค้ดเดิม) vs Postgres (managed, concurrency, RLS)
  • automation การ provision tenant + backup/restore ต่อราย (ปัจจุบัน backup = คัดลอกไฟล์เดียว)

Risks · ความเสี่ยงและการรับมือ

ความเสี่ยงหลัก

High ข้อมูลรั่วข้ามเช่า (cross-tenant leak)

นี่คือข้อมูล ต้นทุน/กำไร ที่ลับที่สุด — รั่วครั้งเดียวจบ. ลืม WHERE tenant_id แถวเดียวใน 167 endpoint ก็พอ.

รับมือ: เลือก DB-per-tenant (แยกเชิงกายภาพ) สำหรับ v1 + accessor กลางบังคับ scope + isolation test matrix ครบทุก endpoint + default-deny.

High พื้นผิว ~167 endpoint กว้างเกินจะตรวจด้วยตา

main.py ~8.5K บรรทัด — แก้ทีละ handler แล้วพลาดเป็นเรื่องปกติ.

รับมือ: ฉีด tenant scope ที่ accessor กลางจุดเดียว ไม่ใช่ 167 จุด; เขียนเทสต์ที่ fail ถ้ามี endpoint ใดยังไม่ถูก scope.

Med SQLite เขียนพร้อมกันหลาย tenant

หลาย tenant sync/upload พร้อมกัน → SQLite ล็อกทั้งไฟล์ถ้าใช้ shared schema.

รับมือ: DB-per-tenant ทำให้การเขียนแยกไฟล์ (ไม่ชนกัน); ถ้าโตมากค่อยย้าย Postgres ตาม abstraction ที่วางไว้.

Med ไฟล์ใหญ่ก้อนเดียว + parallel-session edit

index.html ~13.3K บรรทัด + main.py ~8.5K บรรทัด, blast radius กว้าง; เคยมี session คู่ขนานสวีปโค้ดของกันมาแล้ว.

รับมือ: feature-branch วินัย, stage เป็น hunk (อย่า git-add ทั้งไฟล์), ตรวจ insertion count ทุกครั้ง.

Med คุณภาพข้อมูล onboarding ของ tenant ใหม่

ทุก tenant จะเจอ quirk แบบเดียวกับ Easy (วันสุดท้ายหาย, คอลัมน์ VAT, sku_cost=ราคาขาย).

รับมือ: reuse parser + coverage guard ที่ผ่านการ harden แล้วใน upload_data.py; แสดง coverage report ให้ tenant เห็นก่อน confirm.

High Scope creep / โปรเจกต์ไม่จบ

multi-tenant + billing + admin เป็นหลุมที่ทำได้ไม่รู้จบ.

รับมือ: go/no-go gate ที่ชัด + นิยาม MVP ที่ตัดออกเยอะ + ส่งเป็นเฟส ไม่ big-bang.
