# การดึงข้อมูลจาก POS บนคลาวด์ (Cloud Sync)

เครื่องบน Fly ดึงยอดขายจาก Easy POS (MSSQL) เองตามเวลา ไม่ต้องเปิดคอมพิวเตอร์สำนักงานค้างไว้
ค่าเริ่มต้น **ปิด** การ deploy เวอร์ชันนี้ไม่เปลี่ยนการทำงานใด ๆ จนกว่าเจ้าของจะเปิด

## อะไรทำงานที่ไหน

| งาน | เดิม (คอมพิวเตอร์สำนักงาน) | ใหม่ (เครื่อง Fly) |
|---|---|---|
| 06:00 ดึงใหม่ทั้งหมด | `Oshinei Auto Sync` | รอบแรกของวัน |
| 12:00 และ 16:00 ดึง 45 วันล่าสุด | `Oshinei Sync Live (Fly)` | รอบที่ 2 และ 3 |
| ตรวจเทียบก่อนใช้ข้อมูล | `sync_mssql.py` | `sync_mssql.py` ตัวเดียวกัน |
| ใช้ข้อมูลที่ดึงมา | ส่งขึ้น Fly แล้วสลับ | สลับในเครื่องเดียวกัน (hot-swap เดิม) |

- เวลาเป็นเวลาประเทศไทย ตั้งเปลี่ยนได้ที่ `OSHINEI_CLOUD_SYNC_TIMES` (ค่าเริ่มต้น `06:00,12:00,16:00`) รอบแรกของวันเป็นรอบดึงใหม่ทั้งหมดเสมอ
- รอบ 45 วันดึงใหม่ทั้งหมดซ้ำทุก 7 วัน (`--window-days 45 --full-every-days 7` เหมือนเดิม)
- ถ้าเครื่องเริ่มใหม่ข้ามรอบ ระบบดึงให้ **หนึ่งครั้ง** หลังเริ่มเครื่อง
- งานรันเป็นโปรเซสลูก (`nice -n 10`) แยกจากเว็บ ใช้หน่วยความจำสูงสุดประมาณ 250 MB (รอบดึงใหม่ทั้งหมด) และ 210 MB (รอบ 45 วัน) ที่วัดบนอิมเมจ Linux ด้วยข้อมูลจำลองขนาดเท่าของจริง ค่าจริงของแต่ละรอบแสดงที่หน้า "ข้อมูลจาก POS" (หน่วยความจำสูงสุด)
- ระหว่างรันใช้พื้นที่ดิสก์เพิ่มประมาณ 2 เท่าของไฟล์ฐานข้อมูล (ไฟล์สำเนาที่กำลังสร้าง และไฟล์ WAL ตอน VACUUM) ระบบจึงตรวจก่อนเริ่มว่ามีที่ว่างอย่างน้อย 2.5 เท่า
- ข้อมูลที่ดึงสร้างเป็นไฟล์ส่วนตัว แล้วเผยแพร่เป็น `oshinei.db.incoming` เมื่อผ่านการตรวจเทียบแล้วเท่านั้น ระบบสลับข้อมูลเดิมจึงไม่เห็นไฟล์ที่สร้างไม่เสร็จ

### เงื่อนไขที่ข้ามรอบ (ข้อมูลที่ใช้อยู่ไม่ถูกแตะต้อง)

| ผล | ความหมาย | สิ่งที่ต้องทำ |
|---|---|---|
| `ok` สำเร็จ | ดึงและสลับข้อมูลแล้ว | ไม่ต้องทำ |
| `failed` ไม่สำเร็จ | โปรเซสลูกจบด้วยรหัสอื่นที่ไม่ใช่ 0 หรือ 3 | ดู "บันทึกล่าสุด" ในหน้าตั้งค่า |
| `reconcile_failed` ไม่ผ่านการตรวจเทียบ | ยอดเดือนที่ปิดแล้วไม่ตรงข้อมูลเดิม (รหัส 3) | ตรวจข้อมูลต้นทาง วันแรกของเดือนอาจพบได้ครั้งเดียว |
| `locked` ข้ามรอบ | มีงานซิงก์อื่นถือล็อกอยู่ | ไม่ต้องทำ รอบถัดไปรันเอง |
| `no_space` พื้นที่ไม่พอ | พื้นที่ว่างน้อยกว่า 2.5 เท่าของไฟล์ฐานข้อมูล | ขยายดิสก์ (ขั้นตอนที่ 1 ด้านล่าง) |
| `creds_missing` ยังไม่ตั้งรหัส | ไม่พบ `OSH_SVR`, `OSH_PORT`, `OSH_USER`, `OSH_PWD` หรือ `OSH_DB` | ตั้งรหัสที่ Fly (ขั้นตอนที่ 2) |

ผลล้มเหลว (`failed`, `no_space`, `creds_missing`) และ `reconcile_failed` สองรอบติดกัน ส่งแจ้งเตือนเข้ามือถือผู้บริหารผ่านการแจ้งเตือน "ข้อมูลขายไม่เข้า" เดิม วันละหนึ่งครั้งต่อผล

## วิธีเปิดใช้ (เจ้าของ)

1. ขยายดิสก์เป็น 10 GB
   ```
   flyctl volumes list -a oshinei-dashboard
   flyctl volumes extend <VOLUME_ID> -s 10 -a oshinei-dashboard
   ```
2. ส่งรหัสเชื่อมต่อ POS ขึ้น Fly (รันจากโฟลเดอร์ `backend/` รหัสไม่ผ่านหน้าจอและไม่เข้า git)
   ```
   grep -E '^OSH_(SVR|PORT|USER|PWD|DB)=' .env | flyctl secrets import -a oshinei-dashboard --stage
   ```
3. เปิดการดึงข้อมูล (คำสั่งนี้เริ่มเครื่องใหม่ และใช้รหัสที่เตรียมไว้ในขั้นตอนที่ 2 ไปพร้อมกัน)
   ```
   flyctl secrets set OSHINEI_CLOUD_SYNC=1 -a oshinei-dashboard
   ```
4. เปิด **ตั้งค่า > ข้อมูลจาก POS** ตรวจว่า "สถานะ" เป็น เปิดใช้ และ "รหัสเชื่อมต่อ POS" เป็น ตั้งแล้ว กด **ดึงข้อมูลตอนนี้** หนึ่งครั้งเพื่อทดสอบ (รอบ 45 วันใช้เวลาหลายนาที หน้านี้รีเฟรชเองระหว่างรอ)

## วิธีตรวจสถานะ

- หน้า **ตั้งค่า > ข้อมูลจาก POS** (เฉพาะ Management): ผลรอบล่าสุด เวลาเริ่ม/จบ จำนวนบิลหลังดึง รอบถัดไป พื้นที่ว่าง หน่วยความจำสูงสุด และบันทึก 40 บรรทัดสุดท้าย
- `GET /api/admin/cloud-sync/status` ให้ข้อมูลชุดเดียวกันเป็น JSON
- บันทึกเต็ม: `/data/logs/cloud_sync.log` เก็บ 14 วัน (`flyctl ssh console -a oshinei-dashboard -C "tail -n 200 /data/logs/cloud_sync.log"`)
- ปุ่ม **ดึงข้อมูลตอนนี้** (`POST /api/admin/cloud-sync/run` ต้องใช้รหัสปลดล็อกเหมือนการบันทึกอื่น) ไม่ทำงานซ้อนกับรอบที่กำลังรัน

## กลับไปใช้คอมพิวเตอร์สำนักงาน

```
flyctl secrets unset OSHINEI_CLOUD_SYNC -a oshinei-dashboard
```

เครื่องเริ่มใหม่และหยุดดึงข้อมูลทันที จากนั้นเปิด task `Oshinei Auto Sync` และ `Oshinei Sync Live (Fly)` บนคอมพิวเตอร์สำนักงานอีกครั้ง (ถ้าปิดไว้) ไม่มีข้อมูลที่ต้องย้ายกลับ ทั้งสองทางเขียนฐานข้อมูลชุดเดียวกัน

## แผนย้ายงาน (cut-over)

1. **วันที่ 0** เปิดตามหัวข้อ "วิธีเปิดใช้" ปล่อยให้คอมพิวเตอร์สำนักงานรันตามเดิม
2. **วันที่ 1-3 (รันคู่กัน 2-3 วัน)** ทุกรอบตรวจสองข้อ
   - ผลรอบของ Fly เป็น `ok` ทุกรอบ ไม่มี `reconcile_failed`
   - "จำนวนบิลหลังดึง" ของ Fly กับบรรทัด `inserted N transactions` ใน `backend/logs/auto_sync_local.log` / `sync_live_fly.log` ของรอบเดียวกันต่างกันไม่เกิน 0.1% (ต่างได้เล็กน้อยจากบิลที่ POS ส่งมาช้า)
3. **เมื่อผ่านครบ** ปิด task ทั้งสองบนคอมพิวเตอร์สำนักงาน (ตัวเฝ้าระวังงานข้าม task ที่ปิดอยู่)
   ```
   schtasks /Change /TN "Oshinei Auto Sync" /DISABLE
   schtasks /Change /TN "Oshinei Sync Live (Fly)" /DISABLE
   ```
4. ดูต่ออีกสัปดาห์ แล้วจึงถือว่าย้ายเสร็จ

## ข้อควรรู้

- งานที่ยังต้องใช้คอมพิวเตอร์สำนักงานเหมือนเดิม: สำรองข้อมูลออกนอกเครื่อง (`pull_fly_state`), ดึงรีวิว (`Fetch Feedback`), `Push Invisible`, ตัวเฝ้าระวังงาน (`Task Watchdog`) เอกสารนี้ย้ายเฉพาะการดึงยอดขาย
- ขณะรันคู่กัน ถ้าคอมพิวเตอร์สำนักงานส่งข้อมูลขึ้น Fly ระหว่างที่ Fly กำลังดึง ผลที่ถูกใช้คือไฟล์ที่เผยแพร่ทีหลัง ทั้งสองมาจาก POS สดเหมือนกัน
- ข้อมูลที่ผู้ใช้พิมพ์บนเว็บ (ผู้ใช้ เป้าหมาย การตั้งค่า สูตร ใบสั่งซื้อ รีวิว ผลกระทบกระทบยอด) อยู่ในตารางที่การสลับข้อมูลรักษาไว้เสมอ รวมถึงสถานะของการดึงข้อมูลนี้ (`app_settings`)
- ไม่มีการเก็บรหัสเชื่อมต่อ POS ในโค้ดหรือบันทึก ข้อความที่มีที่อยู่เซิร์ฟเวอร์หรือชื่อผู้ใช้ถูกแทนด้วย `***` ก่อนเก็บ

# สำรองข้อมูล (Cloud Backup)

เครื่องบน Fly สำรองฐานข้อมูล `/data/oshinei.db` เองทุกวัน ไปเก็บในที่เก็บไฟล์ภายนอก (Fly Tigris ที่เข้ากันได้กับ S3) เพราะการดึงข้อมูลจาก POS ย้ายขึ้น Fly แล้ว ฐานข้อมูลในคอมพิวเตอร์สำนักงานจึงไม่เป็นข้อมูลล่าสุดอีก
ค่าเริ่มต้น **ปิด** การ deploy เวอร์ชันนี้ไม่เปลี่ยนการทำงานใด ๆ จนกว่าเจ้าของจะเปิด

สแนปช็อตดิสก์รายวันของ Fly (เก็บ 5 วัน) ยังมีอยู่ แต่อยู่ผู้ให้บริการเดียวกัน จึงไม่นับเป็นสำเนานอกสถานที่

## ทำอะไรบ้างในแต่ละรอบ

| ขั้น | รายละเอียด |
|---|---|
| เวลา | 07:30 เวลาประเทศไทย (ตั้งเปลี่ยนได้ที่ `OSHINEI_CLOUD_BACKUP_TIME`) หลังการดึงข้อมูลรอบ 06:00 ถ้าเครื่องเริ่มใหม่ข้ามรอบ ระบบสำรองให้ **หนึ่งครั้ง** หลังเริ่มเครื่อง |
| รอการดึงข้อมูล | ถ้าการดึงข้อมูลจาก POS กำลังทำงาน (ล็อกเดียวกัน `sync_lock.py`) รอได้ไม่เกิน 90 นาที เกินนั้นข้ามรอบเป็น `locked` |
| ตรวจพื้นที่ | ต้องมีที่ว่างอย่างน้อย 1.5 เท่าของไฟล์ฐานข้อมูล ไม่พอเป็น `no_space` |
| สำเนา | ใช้ SQLite online backup (ไม่คัดลอกไฟล์ตรง ๆ ขณะฐานข้อมูลเปิดอยู่) บีบเป็น gzip พร้อมรายการตรวจ (จำนวนแถว, sha256) เขียนที่ `/data/backups/tmp` |
| ทดสอบกู้คืน | แตกไฟล์ที่เพิ่งเขียนเป็นไฟล์ชั่วคราว ตรวจ sha256 ตรงรายการตรวจ, `PRAGMA quick_check` เป็น ok, จำนวนแถวตรงรายการตรวจ ไม่ผ่านคือ `verify_failed` และไม่อัปโหลด |
| อัปโหลด | `oshinei_<YYYY-MM-DD_HHMM>.db.gz` และ `.manifest.json` ไปที่ `s3://<BUCKET_NAME>/db/` แล้วตรวจขนาดกับ sha256 ของไฟล์ที่เก็บ |
| เก็บย้อนหลัง | เก็บ 7 วันล่าสุด และสำเนาแรกของแต่ละเดือนย้อนหลัง 6 เดือน (กฎเดียวกับ `Backup DB.bat`) ลบสำเนาที่เกินหลังอัปโหลดรอบใหม่ผ่านการตรวจเท่านั้น ถ้าอัปโหลดไม่สำเร็จจะไม่ลบอะไร |
| เก็บกวาด | ลบไฟล์ชั่วคราวทั้งหมด |

งานรันเป็นโปรเซสลูก (`nice -n 10`) แยกจากเว็บ ผลรอบล่าสุดเก็บใน `app_settings` (`cloud_backup_status` คงอยู่ข้ามการสลับข้อมูล) บันทึกเต็มอยู่ที่ `/data/logs/cloud_backup.log` เก็บ 14 วัน

| ผล | ความหมาย | สิ่งที่ต้องทำ |
|---|---|---|
| `ok` สำเร็จ | สำรอง ทดสอบกู้คืน และอัปโหลดครบ | ไม่ต้องทำ |
| `failed` ไม่สำเร็จ | ขั้นใดขั้นหนึ่งผิดพลาด (เช่น เชื่อมต่อที่เก็บไฟล์ไม่ได้) | ดู "บันทึกล่าสุด" ในหน้าตั้งค่า |
| `verify_failed` ทดสอบกู้คืนไม่ผ่าน | สำเนาที่เพิ่งสร้างไม่ตรงรายการตรวจ ไม่มีอะไรถูกอัปโหลด | แจ้งผู้ดูแล ตรวจฐานข้อมูลก่อน |
| `locked` ข้ามรอบ | การดึงข้อมูลจาก POS ถือล็อกเกิน 90 นาที | ไม่ต้องทำ รอบถัดไปรันเอง |
| `no_space` พื้นที่ไม่พอ | ที่ว่างน้อยกว่า 1.5 เท่าของไฟล์ฐานข้อมูล | ขยายดิสก์ |
| `creds_missing` ยังไม่ตั้งรหัส | ไม่พบ `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_ENDPOINT_URL_S3` หรือ `BUCKET_NAME` | สร้างที่เก็บไฟล์ (ขั้นตอนที่ 1) |

ผล `failed`, `verify_failed`, `no_space`, `creds_missing` ส่งแจ้งเตือนเข้ามือถือผู้บริหาร (ชุดเดียวกับแจ้งเตือนการดึงข้อมูล) วันละหนึ่งครั้งต่อผล

## วิธีเปิดใช้ (เจ้าของ)

1. สร้างที่เก็บไฟล์ ระบบตั้ง `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_ENDPOINT_URL_S3`, `AWS_REGION`, `BUCKET_NAME` ให้ที่แอปเอง
   ```
   flyctl storage create -a oshinei-dashboard -n oshinei-backups
   ```
2. เปิดการสำรองข้อมูล (คำสั่งนี้เริ่มเครื่องใหม่ และสำรองให้หนึ่งครั้งหลังเริ่มเครื่อง)
   ```
   flyctl secrets set OSHINEI_CLOUD_BACKUP=1 -a oshinei-dashboard
   ```
3. เปิด **ตั้งค่า > สำรองข้อมูล** ตรวจว่า "สถานะ" เป็น เปิดใช้ และ "รหัสที่เก็บข้อมูลสำรอง" เป็น ตั้งแล้ว รอผลรอบแรกหรือกด **สำรองข้อมูลตอนนี้** ผลที่ถูกต้องคือ "ผลรอบล่าสุด" สำเร็จ และ "ทดสอบกู้คืน" เป็น PASS

## วิธีดูสำเนาที่เก็บไว้

- หน้า **ตั้งค่า > สำรองข้อมูล** (เฉพาะ Management): ผลรอบล่าสุด ทดสอบกู้คืน ขนาด จำนวนสำเนา รอบถัดไป รายการสำเนาในที่เก็บไฟล์ (ใหม่ไปเก่า) และบันทึก 40 บรรทัดสุดท้าย
- `GET /api/admin/cloud-backup/status` ให้ข้อมูลชุดเดียวกันเป็น JSON ปุ่ม **สำรองข้อมูลตอนนี้** คือ `POST /api/admin/cloud-backup/run` (ต้องใช้รหัสปลดล็อกเหมือนการบันทึกอื่น)
- จากเครื่องที่ตั้งรหัสที่เก็บไฟล์แล้ว: `python backend/cloud_backup.py list`

## วิธีกู้คืน

ทำบนเครื่อง Fly ซึ่งมีรหัสที่เก็บไฟล์อยู่แล้ว ข้อมูลที่ผู้ใช้พิมพ์บนเว็บหลังเวลาของสำเนาที่เลือกจะหายไป ส่วนยอดขายจะกลับมาเมื่อการดึงข้อมูลรอบ 06:00 ถัดไปทำงาน

1. หยุดการดึงข้อมูลจาก POS ชั่วคราว (ถ้าเปิดอยู่) เพื่อไม่ให้มีการสลับข้อมูลระหว่างกู้คืน
   ```
   flyctl secrets unset OSHINEI_CLOUD_SYNC -a oshinei-dashboard
   ```
2. เข้าเครื่อง ดาวน์โหลดสำเนาที่ต้องการ แล้วตรวจ
   ```
   flyctl ssh console -a oshinei-dashboard
   python /app/backend/cloud_backup.py list
   python /app/backend/cloud_backup.py download --key db/oshinei_2026-10-22_0730.db.gz --out /data/restore/oshinei_2026-10-22_0730.db.gz
   python /app/backend/db_backup.py verify --backup /data/restore/oshinei_2026-10-22_0730.db.gz
   ```
   คำสั่ง `download` ตรวจ sha256 เทียบกับค่าที่เก็บไว้กับไฟล์ ไม่ตรงจะไม่บันทึกไฟล์ คำสั่ง `verify` ต้องได้ `RESULT: PASS` (อาจใช้ได้ที่เครื่องของตนเองเช่นกัน ถ้าตั้ง `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_ENDPOINT_URL_S3`, `BUCKET_NAME` ไว้)
3. แตกไฟล์ข้าง ๆ ไฟล์จริง ยังไม่แตะไฟล์ที่ใช้งานอยู่ (ใช้พื้นที่เท่าไฟล์ฐานข้อมูลหนึ่งชุด)
   ```
   gunzip -c /data/restore/oshinei_2026-10-22_0730.db.gz > /data/oshinei.db.restored
   ```
4. สลับไฟล์ แล้วออกจากเครื่อง
   ```
   mv /data/oshinei.db /data/oshinei.db.before-restore
   mv /data/oshinei.db.restored /data/oshinei.db
   rm -f /data/oshinei.db-wal /data/oshinei.db-shm
   exit
   ```
5. เริ่มแอปใหม่ให้เปิดไฟล์ที่กู้คืน (ดูรหัสเครื่องจาก `flyctl machine list -a oshinei-dashboard`)
   ```
   flyctl machine restart <MACHINE_ID> -a oshinei-dashboard
   ```
6. ตรวจหน้าแรกและจำนวนบิลล่าสุด เมื่อแน่ใจแล้วเปิดการดึงข้อมูลกลับ และลบไฟล์ที่เหลือ
   ```
   flyctl secrets set OSHINEI_CLOUD_SYNC=1 -a oshinei-dashboard
   flyctl ssh console -a oshinei-dashboard -C "rm -rf /data/oshinei.db.before-restore /data/restore"
   ```

ถ้าขั้นตอนที่ 6 พบว่าสำเนาไม่ถูกต้อง ให้ย้าย `/data/oshinei.db.before-restore` กลับเป็น `/data/oshinei.db` แล้วเริ่มแอปใหม่

## สำเนาในคอมพิวเตอร์สำนักงาน

task `Oshinei DB Backup` (07:30, `Backup DB.bat`) สำรองไฟล์ `backend\oshinei.db` ของคอมพิวเตอร์สำนักงาน ซึ่งจะไม่เป็นข้อมูลล่าสุดเมื่อการดึงข้อมูลย้ายขึ้น Fly
- เมื่อการสำรองบนคลาวด์ทำงานผ่านแล้ว 2-3 วัน (ผลรอบเป็นสำเร็จ และทดสอบกู้คืน PASS ทุกวัน) ปิด task นี้ได้
  ```
  schtasks /Change /TN "Oshinei DB Backup" /DISABLE
  ```
- ถ้าต้องการสำเนาที่สองไว้ก่อน และคอมพิวเตอร์สำนักงานยังดึงข้อมูลรอบ 06:00 อยู่ จะเก็บ task นี้ไว้ต่อก็ได้ ทั้งสองทางไม่กระทบกัน
- หลักฐานการทดสอบกู้คืนสำหรับผู้ตรวจ (AUD-2) ย้ายไปอยู่ที่ "ทดสอบกู้คืน" ของหน้า สำรองข้อมูล และบันทึก `/data/logs/cloud_backup.log` (บรรทัด `restore test: quick_check ok`)

## ปิดการสำรองข้อมูลบนคลาวด์

```
flyctl secrets unset OSHINEI_CLOUD_BACKUP -a oshinei-dashboard
```

สำเนาที่เก็บไว้ในที่เก็บไฟล์ไม่ถูกลบ
