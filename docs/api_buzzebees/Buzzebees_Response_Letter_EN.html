2.2 Load profile

2.5 How a bill is identified

In September 2026 the 49,665 finalised bills had 49,665 unique branch + SaleNum pairs, but only 33,542 distinct SaleId values. SaleId therefore repeats across branches and cannot identify a bill on its own. SaleNum embeds the business date and a daily sequence, and return documents carry an RE prefix.

Figure 2. Bill identifier in Easy POS. We propose that the bill key is sent in every earn and redeem call (R1).

2.6 When bills are voided

Between January and September 2026, 2,482 finalised bills were voided. 2,446 (98.5%) were voided on the day of sale, but 36 were voided on a later day, up to 19 days after the sale. Under the current rule that points can be reversed only within the day (sheet "Refund point"), every one of these 36 bills would leave points on a member account for a sale that no longer exists.

Figure 3. Voids made after the day of sale, by delay in days. Total 36; the longest delay was 19 days.

No return documents (IsReturn) were recorded in the period, so all reversals today are voids. If points are introduced, partial returns may appear; the cancel API must then support reversing a bill and earning again on the reduced amount (R2).

5. Checkout sequence on the CRM PLUS API

How one bill would run on your endpoints. The POS calls at most five times; coupon redemption must succeed before the bill closes, and earning happens after payment so the receipt can print the points.

Figure 5. Checkout sequence mapped to CRM PLUS endpoints. Red marks show where the current API leaves customer value unprotected.
  1. The cashier scans the member QR or enters a phone number; the POS calls /pos/profile and shows the masked name, point balance and usable coupons.
  2. The customer picks a coupon; the POS calls /wallet/pay with to_use=false to check it without using it.
  3. On payment the POS calls /wallet/pay with amount=0 and a unique refId to redeem the coupon, and records the result in PromotionByCRM.
  4. After payment the POS calls /pos/earn with the paid amount and the bill key, then prints the points earned on the receipt.
  5. If a call times out, the POS queries the status before deciding; if the bill is later voided, the POS reverses both the earn and the coupon.

6. Requests to Buzzebees (R1–R10)

Each request states the current behaviour in your specification, the problem it causes, our evidence, and the change we ask for.

R1 — Unique reference and receipt number on earn Blocking

CurrentSheets "Earn", "Earn via user id" and "Earn Direct point": fields are code / contactNumber or userId, terminalId, amount, remark, remark2 (or description). There is no unique request reference and no receipt number. /wallet/pay already has refId.
ProblemWhen a call times out after Buzzebees has credited the points, the POS cannot tell success from failure. A retry credits the points a second time.
EvidenceUp to 452 bills an hour in peak trading (section 2.2), mostly on branch internet links. Even a small timeout rate produces duplicate credits every week.
RequestAdd refId (unique per request, generated by the POS) and receiptNo (branch code + SaleNum, section 2.5) to all earn endpoints. A repeated refId must return the original result without crediting again; a repeated receiptNo must be rejected with a specific error id.
Figure 6. Duplicate credit on retry, and the effect of an idempotency reference.

R2 — Point reversal after the day of sale Blocking

CurrentSheet "Refund point": /earn/cancel with transactionId and terminalId; "Able to refund stamp only transaction within the day."
ProblemBills voided after the day of sale keep their points; partial returns cannot be corrected.
Evidence36 of 2,482 voids in Jan–Sep 2026 happened on a later day, up to 19 days after the sale (section 2.6, Figure 3).
RequestAllow reversal for at least 30 days after the sale. Accept refId or receiptNo as well as transactionId. If the member has already spent the points, define whether the balance may go negative or the shortfall is deducted from the next earn (Oshinei to decide, D4). A repeated cancel must return "already reversed" (your error 4027) without side effects.

R3 — Reversal of a redeemed coupon Blocking

CurrentSheets "Redeem" and "Check code": /wallet/pay redeems a code; there is no endpoint to reverse a redemption.
ProblemIf a bill is cancelled after the coupon is used, for example when payment fails or the bill is voided, the customer loses the coupon although no discount was given.
EvidenceVoids run at about 250–340 bills a month (section 2.1). Each void of a coupon bill would need a manual correction in your back office.
RequestAn endpoint that reverses a redemption by transactionId or refId, restores the code to unused, and is idempotent. The same 30-day window as R2.

R4 — Minimal profile for the POS Blocking

CurrentSheet "Profile": /pos/profile returns the full member record, including name, gender, birth date, age, contact number, e-mail, addresses, NationalIdCard, Passport, DriverLicenseNumber, credit-card fields, marketing consents and income.
ProblemA cashier screen needs only enough to confirm the customer and apply benefits. Receiving the rest on 33–35 shop terminals conflicts with data minimisation under the Personal Data Protection Act B.E. 2562, and Easy would store it in CallAPILog.
RequestA POS profile (or a field filter) that returns only: userId, masked display name (e.g. "Som***"), member level, point balance, points expiring within 30 days, and the list of coupons usable at the calling branch. No identity documents, address, birth date or payment data.

R5 — Transaction status API Before pilot

CurrentSheet "Redeem": status "unknown" requires calling {url}/api/wallet/query every 5 seconds, but the endpoint is not specified.
RequestFull specification (URL, parameters, response, terminal states) and coverage of earn and cancel as well as pay. The POS will query by refId. Please state the maximum time a transaction can stay "unknown".

R6 — Daily reconciliation report Before pilot

CurrentNo report or export is specified.
RequestA daily file or API, available by 06:00 for the previous day, one row per transaction: transactionId, refId, type (earn, cancel, redeem, coupon reversal), branchId, terminalId, receiptNo, userId, amount, points, coupon code, status, timestamp. Oshinei's accounting team will match it to Easy sales every day; mismatches to be corrected within 3 business days.

R7 — Burning points as a bill discount Before pilot

Current/wallet/pay with amount greater than 0 is described as "payment" and returns a balance. It is not clear whether this debits points or a stored-value wallet.
RequestConfirm the endpoint and parameters for using points as a discount, the conversion rate, minimum and maximum per bill, and how the POS learns these values (ideally in the R4 profile).

R8 — Earning through the receipt QR Before pilot

CurrentNot covered. Easy POS already has a receipt-QR feature assigned to 35 branches (inactive) with fields for a pattern and public/secret keys (section 2.4).
RequestConfirm whether the LINE Official Account can read a signed QR from the receipt (branch code, SaleNum, date, amount, signature) and credit points once per bill key. If yes, agree the format with Easy; if not, members must be identified at the counter on every bill.

R9 — Credentials and environments Before pilot

CurrentOne merchant token per merchant; production URL "TBC" in every sheet; sheet "url" lists new staging and production hosts from June 2024.
RequestIssue Oshinei UAT and production credentials, one per branch (or one token plus server-side branch binding); confirm the production base URLs; confirm the branchId, brandId and terminalId values for each Oshinei branch and how a new branch is added; state the token lifetime and rotation procedure (your error 1905 "token expired").
