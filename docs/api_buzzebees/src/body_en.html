1. Definitions

The following terms carry the same meaning throughout this document.

2. Scope and roles

The system shall allow cashiers to look up members, record point earning, apply coupons, burn points and void transactions at the point of sale of every branch running Easy POS (approximately 35 branches). Member sign-up takes place only in the Buzzebees LINE Official Account; the POS does not support sign-up.

PartyRoleResponsibilities
BuzzebeesDeveloper and system operatorDevelop APIs B0–B9 to the HO_CRM specification; decode the receipt QR; provide the sandbox and test accounts; deliver the daily reconciliation report; configure the LINE Official Account, earn rules and coupons
Easy POSSpecification owner and POS configuratorDeliver the HO_CRM specification and receipt QR format to Buzzebees; configure per-branch URLs and API keys in the POS; enable the receipt QR per branch; map coupons to Easy discount codes; take part in testing
OshineiProject owner, decision maker and acceptance authoritySet earn and coupon rules; select pilot branches; train cashiers; perform daily reconciliation; accept the work

Out of scope: replacing the POS with B-POS; online ordering and delivery; member sign-up at the POS; marketing campaigns (handled inside Buzzebees with no API impact).

4. API overview and integration map

Provider-side developer: Buzzebees · Callers: Easy POS (B0–B8), Easy HQ (B7), Oshinei reporting system (B9)

Every API is called by a consumer towards Buzzebees. Buzzebees never calls the POS, because POS terminals sit inside the branch network and cannot accept inbound connections.

5. Call sequence per bill

POS-side developer (call order and failure handling): Easy · Provider-side developer: Buzzebees

A bill makes at most five API calls (B1–B5), all initiated by Easy POS. Coupon redemption and point burning (B3, B4) must succeed before the bill closes. Point earning (B5) is called after payment succeeds and before the receipt prints, so the receipt can show points earned and the balance.

{{SVG_SEQ}}
API call sequence per bill: five steps and two exceptions
  1. The cashier scans the member QR from LINE or enters a phone number → B1 member lookup. The POS shows the name, point balance and available coupons.
  2. The customer selects a coupon → B2 validate coupon (no deduction yet). The POS applies the discount returned.
  3. The customer asks to burn points → the POS computes the discount from point_balance × point_value_thb returned by B1, with no API call.
  4. Payment is confirmed → B3 redeem coupon and B4 burn points, one at a time. If either fails, the POS reverses the successful one with B6 and informs the cashier.
  5. Payment succeeds → B5 earn points → the receipt prints with points earned, balance and the receipt QR. If B5 does not answer in time, the receipt prints "Points will be credited within 24 hours" and the POS places the request in the retry queue.
  6. Bill cancelled before closing after B3/B4 succeeded → B6 immediately with the transaction_refs to restore the coupon and points.
  7. Void or return after closing → B6 restores the coupon and burned points and deducts earned points. For a partial return, call B6 for the whole bill, then call B5 again with the post-return amount.

When B3, B4 or B5 times out: the POS calls B8 transaction status with the same request_id. completed → use that result; not_found → treat as not deducted and give no discount; B8 also unanswered → give no discount and close the bill at full price. Any deduction that may have happened appears in the reconciliation report, and Buzzebees restores it to the customer.

8. Receipt QR

QR format: Easy (technical team) · Decoding and point award: Buzzebees · Per-branch activation: Easy

Every receipt carries a QR code. Customers who did not identify as members at payment can scan it in the LINE Official Account to claim points later; new customers can sign up first and then claim. No POS API call is involved. (Easy already has the QrDataReceipt setting, currently disabled in all branches.)

QR contentDescription
branch_code, receipt_no, sale_date, sale_timeBill key; must match the values sent in B5
net_amount_inc_vat, earn_base_amountNet amount, and the earn base agreed for point calculation
signatureHMAC-SHA256 digital signature over the fields above, using a secret key issued by Buzzebees (QRDataSecretKey in Easy), to prevent tampering with the amount (proposed)

The data layout inside the QR (separator, field order, encoding) shall follow what the Easy QRDataReceiptSetting supports. Easy will send the specification to Buzzebees.

Rules

  • One receipt can claim points once, within 7 days of sale_date (proposed).
  • For a bill already earned through B5, scanning the QR returns "Points have already been awarded for this bill" and awards nothing (checked by bill key).
  • Receipt-QR transactions are recorded with channel = receipt_qr and carry a transaction_ref like any other.
  • If a bill is voided after the customer scanned it, points are deducted through B6 (Buzzebees finds the transaction by bill key even when the POS holds no transaction_ref).
  • A QR with an invalid signature is rejected and logged by Buzzebees in the reconciliation report.

9. General requirements

Compliance owners: Buzzebees (provider side and operations) · Easy (POS side: timeouts, retry queue, logging)

Security

  • HTTPS with TLS 1.2 or higher on every API.
  • One API key per branch, sent only in headers, never in the URL. A branch key cannot be used with another branch_code.
  • Keys can be revoked per branch and rotated without downtime (old and new keys both valid for 7 days).
  • Head-office keys for B7 and B9 should be restricted by source IP (IP allowlist) where possible.
  • The only personal data passing through the API is member_id, the masked name, and the phone number in the B1 request.

Idempotency and duplicate prevention

  • Same request_id + same body → the original result (HTTP 200), with no second execution.
  • Same request_id + different body → HTTP 409.
  • A bill key can earn (B5) only once, whether the request comes from the POS or the receipt QR.
  • Retry queue for B5 and B6: retry after 1, 5 and 15 minutes, then hourly until 24 hours have passed; the item is then reported as outstanding in the reconciliation report.

Timeouts and Buzzebees unavailability

  • The POS applies the timeouts in the API overview table; exceeding them counts as failure.
  • The bill can always be closed; a membership outage must never block a sale.
  • Coupons and point burning (B2–B4) are unavailable while offline; the cashier sees "Membership system unavailable" from B0.
  • Points are credited later through the retry queue or when the customer scans the receipt QR; both use the same bill key, so nothing is duplicated.

Logging, time and currency

  • Easy logs every request and response in CallAPILog and keeps them for 90 days; phone numbers in logs are masked as 08x-xxx-1234.
  • All timestamps use ISO 8601 in Thailand time (+07:00).
  • sale_date is the POS business date (SaleDate in Easy); bills after midnight but before the day is closed belong to the same business date.
  • Amounts are in baht with 2 decimals, always split into VAT-inclusive and VAT-exclusive; points are integers.

10. Daily reconciliation

Reconciler: Oshinei (accounting) · Report provider and corrections: Buzzebees · POS-side data: Easy

Every day at 06:00 Oshinei pulls the previous day's transactions through B9 and compares them with Easy on three points: (1) every Buzzebees transaction has a matching bill in Easy; (2) every Easy bill with points or coupons has a Buzzebees transaction; (3) discount amounts and points agree on both sides.

ColumnDescription
transaction_ref, request_idReferences on both sides
typeearn, burn, coupon or void
channelpos or receipt_qr
branch_code, sale_date, receipt_noBill key
member_idMember ID
pointsPositive = earned, negative = burned or deducted
discount_amount, coupon_codeDiscount in baht and coupon code (if any)
statuscompleted, reversed or rejected
created_atTime recorded by Buzzebees
  • Mismatches (present on one side only, or amounts differ) shall be resolved within 3 business days, with Buzzebees adjusting points to match the bill in Easy.
  • Coupon and point discounts must be separable from other Easy discounts through PromotionByCRM, so the store's discount reporting stays clean.
  • Items left in the retry queue beyond 24 hours are sent by Easy to Oshinei every morning for follow-up.

11. Acceptance test cases

Testing runs in the sandbox first, then again at one pilot branch with live bills. Every case must pass, and the reconciliation report for the test day must match Easy for every transaction.

Test groupTesterAcceptance
Normal checkout, coupons and points, voidsBuzzebees with Easy (technical team)Oshinei (project owner)
Network and retriesEasy (technical team)Buzzebees confirms provider side; Oshinei accepts
Receipt QR, master data and reportingBuzzebeesOshinei (accounting reviews the report)
Pilot-branch retestEasy (field team) with BuzzebeesOshinei (branch operations)

Normal checkout

  • B0: disconnect → the POS shows "Membership system unavailable" and recovers automatically when the connection returns.
  • B1: lookup by QR and by phone returns the correct masked name, balance and branch coupons; expired QR → QR_EXPIRED.
  • B5: a normal bill earns per the rules, the receipt prints points earned and balance, and Sale.EarnPoint matches Buzzebees.
  • B5: a bill with discounts, service charge and split payment earns on the agreed base.
  • B5: a delivery bill earns or does not earn, as agreed.

Coupons and points

  • B2/B3: bill-level, item-level and free-item coupons apply and are recorded in PromotionByCRM with the correct easy_promotion_code.
  • B2: used, expired, wrong-branch, below-minimum and other-member coupons → the error codes in the table.
  • B3: the same coupon cannot be redeemed at another branch at the same time.
  • B4: normal burn, burn above balance and burn outside min/max → the last two are rejected.
  • B4: mismatched expected_discount → AMOUNT_MISMATCH with no deduction.

Voids

  • B6: cancel before closing after B3/B4 succeeded → coupon usable again and points restored immediately.
  • B6: void a bill with a coupon, a burn and an earn → all three are reversed.
  • B6: void a bill whose earned points were already spent → balance goes negative as agreed.
  • B6 + B5: partial return → net points match the post-return amount.
  • B6: repeated void → already_reversed, no double reversal.

Network and retries

  • Internet cut at bill closing → the bill closes, the receipt prints "Points will be credited within 24 hours", and points arrive once the connection returns, without duplicates.
  • Resend the same request (same request_id and body) → same result, no duplicate.
  • Same request_id with a different body → HTTP 409.
  • B8: B3 times out after Buzzebees redeemed → B8 returns completed and the POS closes with that result; timeout before reaching Buzzebees → not_found.
  • Branch A key used with branch B code → HTTP 401.

Receipt QR, master data and reporting

  • Scan a normal receipt QR → points awarded; scan again → nothing; bill already earned through B5 → nothing; tampered QR → rejected.
  • B7: full branch and menu snapshot → all received, and item-level coupons can reference item_code.
  • B9: the test-day reconciliation report matches Easy for every transaction, including voids and receipt-QR claims.

12. Items requiring agreement

The following items must be settled before development starts, grouped by owner.

Before development Owners: Easy and Buzzebees

  • Easy: deliver the HO_CRM specification and receipt QR format so Buzzebees can align field names and endpoints, and confirm the Easy columns used (Sale.CustomerId / CustRefNum, PromotionByCRM).
  • Easy: confirm that HO_CRM supports all calls B0–B8, and whether any unsupported call requires additional development cost.
  • Buzzebees: confirm support for receipt-QR scanning from a third-party POS, and the availability of a sandbox.

Business rules Decision owner: Oshinei (project owner)

  • Earn base: amount after discount, with or without VAT and service charge, and the earn rate per baht.
  • Value of one point when burned, minimum and maximum per bill, and point expiry.
  • Whether delivery bills (Grab, LINE MAN) earn points.
  • Whether coupons combine with other discounts on the same bill, how many per bill, and whether a coupon and a point burn can be used together.
  • When a bill is voided after its earned points were spent: allow a negative balance, or deduct from the next earn.
  • Who sets the receipt footer message (receipt_message) and how often it may change.

Configuration and operations Owners: Buzzebees and Easy; approval: Oshinei

  • Easy: mapping each coupon type to an Easy discount code (easy_promotion_code), and who maintains that mapping.
  • Buzzebees: issuing per-branch API keys (Buzzebees issues, Easy configures), and the rotation procedure for new branches or a leaked key.
  • Oshinei and Buzzebees: the Data Processing Agreement (DPA), data residency and retention period.
