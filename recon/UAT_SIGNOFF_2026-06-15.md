## 3. สิ่งที่ต้องเตรียมก่อนทดสอบ (Prerequisites)

1. **รหัสเข้าใช้ (token):**
   - **รหัสบันทึกข้อมูล (admin/write):** ใช้กับการอัปโหลด/บันทึก — กรอกครั้งเดียวผ่านปุ่ม **🔑 รหัส**
   - **รหัสผู้จัดการ (manager):** ใช้กับ ปิดเดือน + เปิดงวดใหม่ + แก้รหัสสเตทเมนต์ — ระบบถามครั้งแรกที่กดงานผู้จัดการ
   - *(ขอรับรหัสจากเจ้าของระบบ — อย่าเผยแพร่)*
2. **เอกสารตัวอย่างของเดือนที่ทดสอบ** (อย่างน้อยอย่างละ 1 ไฟล์): สเตทเมนต์ธนาคาร KTB/KBANK, สรุปยอดบัตรเครดิต, รายงาน Grab/Line Man, สลิปนำฝากเงินสด
3. **เบราว์เซอร์** Chrome/Edge รุ่นใหม่ + เครื่องพิมพ์หรือ "Save as PDF"
4. ข้อมูล POS ของเดือนนั้นต้องถูกซิงก์เข้าระบบแล้ว (ถ้าเปิดสาขาแล้วไม่มียอด = ยังไม่ซิงก์)

## 4. ภาพรวมขั้นตอนการกระทบยอด 1 เดือน (Happy Path — อ่านก่อนเริ่มทดสอบ)

> **เรื่องเล่า:** ระบบนี้เปรียบ "ยอดที่ POS บันทึก" กับ "เงินที่เข้าบัญชี/เอกสารจริง" ของแต่ละ **ช่องทางรับเงิน**
> (เงินสด, QR พร้อมเพย์, เงินโอน, บัตรเครดิต, Grab, Line Man, คูปอง) **ไล่เป็นรายวันทั้งเดือน** เพื่อให้มั่นใจว่า
> เงินที่ขายได้เข้าบัญชีครบจริง ไม่มีตกหล่นหรือบันทึกผิดช่อง

ลำดับงานปกติของหนึ่งเดือน:

1. **เปิดหน้าแรก** → เห็นทุกสาขาเป็น "กล่องงาน" ว่าสาขาไหนเหลือกี่เรื่อง
2. **เข้าสาขา** → ระบบโชว์ช่องทางที่ "ยังไม่ตรง" ขึ้นก่อน + บอกว่าขาดเอกสารอะไร
3. **อัปโหลดเอกสาร** ที่ขาด (กดที่ป้ายเอกสารสีแดง หรือเลือกหลายไฟล์/ทั้งโฟลเดอร์)
4. ระบบ **จับคู่อัตโนมัติ** ทันที (ไม่มีปุ่ม "Run Match" — คำนวณสด)
5. ถ้ามี **"เงินอาจถูกบันทึกผิดช่อง"** ระบบขึ้นการ์ดเล่าเป็นเรื่อง → ยืนยันด้วยปุ่มเดียว
6. ถ้ามี **ผลต่างที่อธิบายได้** → กด "รับทราบผลต่าง" พร้อมใส่เหตุผล
7. เมื่อเรียบร้อย เจ้าหน้าที่กด **"ส่งตรวจ"** → ผู้จัดการ **"ปิดเดือน"** (ล็อกตัวเลขถาวร)
8. **ออกรายงาน** เพื่อเก็บหลักฐาน/ให้สาขาเซ็นรับทราบ/ตรวจการจับคู่

### TC-01 · หน้าแรก — กล่องงานทุกสาขา + แบนเนอร์เตือนรูปแบบน่าสงสัย
**บทบาท:** ทุกคน

**📖 การใช้งาน (narrative):** หน้าแรกคือ "อินบ็อกซ์" รวมทุกสาขา — เรียงสาขาที่ยังมีงานค้างขึ้นก่อน บอกชัดว่า
"เหลือกี่เรื่อง" และมีแถบ "รอฉันตรวจ" สำหรับผู้จัดการ ถ้าระบบจับได้ว่าการ์ดเงินผิดช่องมี **รูปแบบซ้ำผิดปกติ**
(อาจเกิดจากรหัสในสเตทเมนต์ตั้งผิด ไม่ใช่คนกดผิด) จะมีแบนเนอร์ 🔎 เตือนผู้จัดการให้ไปตรวจพจนานุกรมรหัสก่อน

**ขั้นตอนทดสอบ:**
1. เปิด `/app/` เลือกเดือนที่ทดสอบ (ช่องเลือกเดือนมุมขวาบน)
2. ดูรายการสาขา — สาขาที่มีงานค้างต้องขึ้นก่อน สาขาที่เรียบร้อยยุบอยู่ใน "เรียบร้อยแล้ว"
3. สังเกตแถบสรุปด้านบน (ความคืบหน้าทั้งเครือ / จำนวนเงินที่อาจผิดช่อง)

**ผลที่คาดหวัง:** เห็นรายการสาขาพร้อม "เหลือ N เรื่อง", กดสาขาแล้วเข้าหน้าสาขาได้, (ถ้ามี) แบนเนอร์เตือนแสดงพร้อมลิงก์ไปพจนานุกรมรหัส

**ผลการทดสอบ:** ☐ ผ่าน ☐ ไม่ผ่าน | ผู้ทดสอบ: __________ วันที่: ________ | หมายเหตุ: ________________

### TC-02 · หน้าสาขา — ช่องทางรับเงิน + อัปโหลดเอกสาร
**บทบาท:** เจ้าหน้าที่กระทบยอด

**📖 การใช้งาน (narrative):** เข้าสาขาแล้วระบบแยกช่องทางเป็น "ต้องทำ" (สีส้ม/แดง), "เศษเหรียญ ≤฿100" (รวบกดทีเดียว),
"รอเงินเข้าตามรอบ" (ปกติ ไม่ใช่ปัญหา) และ "เรียบร้อยแล้ว" (ยุบไว้) แถบ **เอกสาร** ด้านบนบอกว่าอัปครบหรือยัง —
ป้ายสีแดง = ยังขาด กดที่ป้ายเพื่ออัปโหลดได้เลย หรือใช้ "⬆ หลายไฟล์ / 📁 ทั้งโฟลเดอร์" ให้ระบบแยกประเภทไฟล์เอง

**ขั้นตอนทดสอบ:**
1. กดเข้าสาขาที่ทดสอบ
2. ที่แถบ "เอกสาร" กดป้ายเอกสารที่ยังขาด (สีแดง) แล้วเลือกไฟล์จริงของเดือนนั้น
3. รอระบบประมวลผล — ป้ายควรเปลี่ยนเป็น ✓ และช่องทางที่เกี่ยวข้องอัปเดตสถานะทันที
4. ลองกด "⬆ หลายไฟล์" เลือกหลายไฟล์พร้อมกัน

**ผลที่คาดหวัง:** อัปโหลดสำเร็จ (ขึ้นข้อความยืนยัน), ป้ายเอกสารเป็น ✓ พร้อมช่วงวันที่ครอบคลุม, ช่องทางที่ตรงแล้วเลื่อนไป "เรียบร้อย", ระบบแยกประเภทไฟล์ได้ถูกต้อง (สเตทเมนต์/บัตร/Grab/LM)

**ผลการทดสอบ:** ☐ ผ่าน ☐ ไม่ผ่าน | ผู้ทดสอบ: __________ วันที่: ________ | หมายเหตุ: ________________

### TC-03 · การ์ด "เงินอาจถูกบันทึกผิดช่อง" (จับคู่ข้ามช่องทาง)
**บทบาท:** เจ้าหน้าที่กระทบยอด

**📖 การใช้งาน (narrative):** เมื่อระบบเจอว่าช่องทางหนึ่ง "เกินมา" และอีกช่องทาง "ขาดไป" เป็นยอดเท่ากันในวันใกล้กัน
(เช่น เงินสดเกิน แต่ QR ขาด) จะขึ้นการ์ดเล่าเป็นเรื่องว่า *"น่าจะเป็นเงินก้อนเดียวกัน — ในเครื่อง POS กดเป็นเงินสด
แต่จริง ๆ เข้าเป็น QR"* ถ้ามั่นใจกด **"✅ ใช่ เป็นเงินก้อนเดียวกัน"** ระบบย้ายเข้าช่องที่ถูกให้ (ยอดรวมไม่หาย เป็นแค่
ย้ายช่อง) ถ้าไม่แน่ใจกด **"🔍 ขอดูรายการ"** เพื่อดูบรรทัดจริงก่อน

**ขั้นตอนทดสอบ:**
1. ในหน้าสาขา หาการ์ด "⇄ เงินอาจถูกบันทึกผิดช่อง" (ถ้ามี)
2. กด "🔍 ขอดูรายการ" → ตรวจว่าบรรทัด POS กับบรรทัดเอกสารเป็นเงินก้อนเดียวกันจริง
3. ถ้าใช่ กด "✅ ใช่ เป็นเงินก้อนเดียวกัน"
4. ตรวจว่ายอดย้ายเข้าช่องที่ถูก และการ์ดหายไป

**ผลที่คาดหวัง:** เห็นรายละเอียดเมื่อขอดู, ยืนยันแล้วยอดย้ายช่องถูกต้อง ยอดรวมของวันไม่เปลี่ยน, รายการถูกบันทึกเป็น "การจับคู่ด้วยมือ"

**ผลการทดสอบ:** ☐ ผ่าน ☐ ไม่ผ่าน | ผู้ทดสอบ: __________ วันที่: ________ | หมายเหตุ: ________________

### TC-04 · รับทราบผลต่าง (Accept Variance) พร้อมเหตุผล
**บทบาท:** เจ้าหน้าที่กระทบยอด

**📖 การใช้งาน (narrative):** บางช่องทางมีผลต่างที่ "อธิบายได้ด้วยสาเหตุจริง" (เช่น ผลต่างจากค่าธรรมเนียม/ปัดเศษที่กระทบยอดแล้ว) —
กด "รับทราบผลต่าง" แล้ว **เลือกเหตุผล** (หรือพิมพ์เอง อย่างน้อย 10 ตัวอักษร — ต้องระบุสาเหตุจริง ไม่ใช่ "ยอดเล็กไม่คุ้ม")
ระบบจะเคลียร์งานนั้นออกจากรายการค้างโดย **ไม่แก้ตัวเลข** และเก็บไว้เป็นหลักฐานว่าใครรับทราบ เพราะอะไร เมื่อไร — ใช้ตรวจสอบย้อนหลังได้

**ขั้นตอนทดสอบ:**
1. หาช่องทางที่มีผลต่างที่อธิบายสาเหตุได้
2. กด "รับทราบผลต่าง" → เลือก/พิมพ์เหตุผลที่ระบุสาเหตุจริง → ยืนยัน
3. ตรวจว่างานนั้นถูกเคลียร์ และมีบันทึกผู้รับทราบ + เวลา

**ผลที่คาดหวัง:** ใส่เหตุผลสั้นเกินไป (<10 ตัว) ระบบเตือน, ใส่เหตุผลครบแล้วเคลียร์งานได้, ตัวเลขยอดไม่เปลี่ยน, มีบันทึกหลักฐาน

**ผลการทดสอบ:** ☐ ผ่าน ☐ ไม่ผ่าน | ผู้ทดสอบ: __________ วันที่: ________ | หมายเหตุ: ________________

### TC-05 · ส่งตรวจ → ปิดเดือน (สองชั้น + รหัสผู้จัดการ)
**บทบาท:** เจ้าหน้าที่ (ส่งตรวจ) + ผู้จัดการ (ปิดเดือน)

**📖 การใช้งาน (narrative):** เพื่อความรอบคอบ การปิดเดือนแยกเป็นสองชั้น — เจ้าหน้าที่กด **"ส่งตรวจ"** เมื่อทำครบ
จากนั้น **ผู้จัดการ** ตรวจสรุปแล้วกด **"ปิดเดือน"** (ต้องใส่ **รหัสผู้จัดการ**) เมื่อปิดแล้วตัวเลขถูกล็อกถาวร แก้ไม่ได้
(ถ้าต้องเปิดใหม่ ผู้จัดการกด **"เปิดงวดใหม่ (ผู้จัดการ)"** + เหตุผล — ดู TC-36; "ส่งกลับแก้" ใช้ก่อนปิด ตอนรอผู้จัดการตรวจ)
— ป้องกันการแก้ย้อนหลังโดยไม่มีการอนุมัติ

**ขั้นตอนทดสอบ:**
1. ทำสาขาให้เรียบร้อย แล้วกด **"ส่งตรวจ"** → สถานะเปลี่ยนเป็น "รอผู้จัดการตรวจ"
2. (ผู้จัดการ) เปิดสาขา เห็นสรุปสำหรับผู้จัดการ → กด **"ปิดเดือน"**
3. ระบบถาม **รหัสผู้จัดการ** → ใส่รหัสผิดต้องไม่ผ่าน, ใส่ถูกต้องปิดได้
4. ลองแก้ข้อมูลหลังปิด — ต้องแก้ไม่ได้ (ล็อก)

**ผลที่คาดหวัง:** ส่งตรวจได้, ปิดเดือนต้องใช้รหัสผู้จัดการ (ผิด=ไม่ผ่าน), ปิดแล้วล็อกแก้ไม่ได้, แสดงผู้ปิด + เวลา

**ผลการทดสอบ:** ☐ ผ่าน ☐ ไม่ผ่าน | ผู้ทดสอบ: __________ วันที่: ________ | หมายเหตุ: ________________

### TC-06 · รายงานเงินบันทึกผิดช่อง + ใบเซ็นรับทราบ + แนวทางพัฒนาสาขา
**บทบาท:** ฝ่ายบัญชี / ผู้จัดการ

**📖 การใช้งาน (narrative):** รายการที่ยืนยันว่า "กดผิดช่อง" (จาก TC-03) จะถูกเก็บเป็น log และออกเป็น **รายงานให้สาขา
เซ็นรับทราบ + แก้ไข** ในรายงานยังมี **ส่วนช่วยสาขาพัฒนาตัวเอง**: กราฟแนวโน้มรายเดือน (ดีขึ้น/แย่ลง) + เป้าหมายเดือนหน้า,
ช่องทางที่สับสนบ่อย, และคำแนะนำเฉพาะจุด — ใช้ประเมิน/โค้ชแคชเชียร์ได้อย่างสร้างสรรค์ (ยอดเงินไม่หาย เป็นการลงผิดช่อง)

**ขั้นตอนทดสอบ:**
1. เมนู **⋯ เพิ่มเติม** → **"⇄ รายงานเงินบันทึกผิดช่อง"**

5. ลองพิมพ์เฉพาะสาขา (ลิงก์ "พิมพ์เฉพาะสาขานี้")

**ผลที่คาดหวัง:** รายงานแสดงรายการจริง, ใบพิมพ์ครบ 3 ส่วน + ช่องเซ็น, Excel โหลดได้, พิมพ์ PDF ได้

### TC-07 · พจนานุกรมรหัสในสเตทเมนต์ + ผู้จัดการแก้รหัสเอง
**บทบาท:** ฝ่ายบัญชี (ตรวจ) + ผู้จัดการ (แก้)

**📖 การใช้งาน (narrative):** สเตทเมนต์ธนาคารมี "รหัสย่อ" ที่ระบบใช้แยกประเภทอัตโนมัติ (เช่น SDCH, IORSDT) — บางรหัส
อาจถูกตีความผิด รายงานพจนานุกรมให้ทีมตรวจว่าทุกรหัสแปลถูกไหม (รหัสที่ยังไม่ยืนยันขึ้นสีเหลือง "⚠ รอตรวจ") ถ้าพบว่าผิด
**ผู้จัดการแก้เองได้ในหน้าตั้งค่า** โดยเลือกช่องทางที่ถูกต้อง (รวมตัวเลือก "ไม่นับ/ไม่ใช่รายได้") — มีผลทันทีกับข้อมูลเดิม
และไฟล์ที่อัปใหม่ ไม่ต้องรอทีมพัฒนา

**ขั้นตอนทดสอบ:**
1. 📊 รายงาน → **"📖 พจนานุกรมรหัสในสเตทเมนต์"** → ตรวจความหมาย/ช่องทางของแต่ละรหัส (พิมพ์ใบให้ทีมตรวจได้)
2. ⚙️ Admin → **#setup → ส่วน ⑤ "รหัสในสเตทเมนต์ → ช่องทาง"**
3. เลือกรหัสหนึ่ง (เช่น SDCH) เปลี่ยนช่องทางใน dropdown แล้วกด **"บันทึก"** → ระบบถามรหัสผู้จัดการ
4. ตรวจว่าหลังบันทึกขึ้น "✏️ ทีมแก้แล้ว" + แสดงจำนวนบรรทัดที่ปรับ
5. กด **"คืนค่าเดิม"** → กลับเป็นค่าระบบ

**ผลที่คาดหวัง:** ดูพจนานุกรมได้, แก้รหัสต้องใช้รหัสผู้จัดการ, แก้แล้วมีผล + นับบรรทัดที่ปรับ, คืนค่าเดิมได้

**ผลการทดสอบ:** ☐ ผ่าน ☐ ไม่ผ่าน | ผู้ทดสอบ: __________ วันที่: ________ | หมายเหตุ: ________________

### TC-08 · รายงานการจับคู่รายวันทั้งเดือน (ตรวจการจับคู่ + พิมพ์ PDF)
**บทบาท:** ฝ่ายบัญชี / ผู้ตรวจสอบ

**📖 การใช้งาน (narrative):** เพื่อ "มั่นใจว่าจับคู่ถูกครบทั้งเดือน" รายงานนี้ไล่ **ทุกวัน × ทุกช่องทาง** ในใบเดียว แสดง
ยอด POS เทียบเอกสาร, ผลต่าง, และสถานะการจับคู่ (✓ ตรง / ✗ ต่าง / ขาดเอกสาร / รอเอกสารตามรอบ) — แถวที่ต้องตรวจ
ขึ้นสีแดง ทำให้สายตาไปหาจุดที่ยังไม่ตรงได้ทันที ด้านบนมีสรุป "จับคู่ตรง X/Y" และถ้าครบมีแบนเนอร์ "✓ ทุกช่องทางจับคู่ครบ"
**ท้ายใบยังมี "💰 สรุปการรับเงินทั้งเดือน + ค่าธรรมเนียม/VAT" และ "📒 ร่างการบันทึกบัญชี (Dr/Cr)"** + ช่องเซ็น 3 คน ·
ปุ่ม **"📑 ฉบับตรวจสอบ (ละเอียด)"** เพิ่มหลักฐานระดับบรรทัดสำหรับ auditor (รหัส POS, ยอดบัตรราย acquirer, ทุกบรรทัดเงินเข้า, ค่าธรรมเนียม, การจับคู่ด้วยมือ) ·
มี **"📆 ช่องเลือกวัน (filter by date)"** บนหัวรายงาน — เลือกวันเดียวแล้วรายงาน **ย่อเหลือเฉพาะวันนั้น** พร้อม **ร่างบันทึกบัญชี (Dr/Cr) ของวันนั้นโดยตรง** สำหรับนำไปลงบัญชีรายวัน

**ขั้นตอนทดสอบ:**
1. **หน้าสาขา** → กดปุ่ม **"🖨️ ตรวจการจับคู่รายวัน"** (รายงานของสาขานั้น เดือนที่เลือก)
2. ตรวจ KPI ด้านบน (จับคู่ตรง / ต้องตรวจ / รอเอกสาร / POS รวม / เอกสารรวม / ผลต่างสะสม)
3. ไล่ตาราง — วันที่ที่ "ต่าง/ขาดเอกสาร" ขึ้นสีแดง, "รอเอกสารตามรอบ" สีเหลือง, ตรงแล้วเป็น ✓
4. เลื่อนลงดู **"💰 สรุปการรับเงิน + ค่าธรรมเนียม/VAT"** และ **"📒 ร่างบันทึกบัญชี"** → ตรวจว่ายอดถูก + เดบิตรวม = เครดิตรวม
5. เลือกวันเดียวที่ **"📆 ช่องเลือกวัน"** → รายงานเหลือเฉพาะวันนั้น + ร่างบันทึกบัญชี (Dr/Cr) ของวันนั้น แล้วกด **"↺ ทั้งเดือน"** เพื่อกลับ
6. กดปุ่ม **"📑 ฉบับตรวจสอบ (ละเอียด)"** → ตรวจหลักฐานระดับบรรทัด (รหัส POS, ยอดบัตรราย acquirer KBANK/KTC, ทุกบรรทัดเงินเข้า)
7. กด **"🖨️ พิมพ์ / บันทึก PDF"** → บันทึกเป็น PDF · ลองเมนู ⋯ → **"รายงานการจับคู่รายวัน (ทุกสาขา)"** → แพ็กหน้าละสาขา

**ผลที่คาดหวัง:** ทุกวัน × ช่องทางสถานะถูกต้อง, KPI ตรงข้อมูล, **สรุปรับเงิน/ค่าธรรมเนียม/VAT ถูก + ร่างบัญชี Dr=Cr**, **เลือกวันแล้วย่อเหลือวันเดียว + ร่างบัญชีของวันนั้นถูกต้อง**, ฉบับละเอียดมีหลักฐานครบทุกบรรทัด, พิมพ์ PDF ได้, แพ็กทุกสาขาแยกหน้าได้

**ผลการทดสอบ:** ☐ ผ่าน ☐ ไม่ผ่าน | ผู้ทดสอบ: __________ วันที่: ________ | หมายเหตุ: ________________

### TC-12 · รูปแบบไฟล์ที่รองรับ — KTB (Excel/PDF/OCR) + Line Man Balance-Report
**บทบาท:** เจ้าหน้าที่กระทบยอด

**📖 การใช้งาน (narrative):** สเตทเมนต์ KTB อัปได้ทั้ง **Excel/CSV** (แม่นที่สุด), **PDF ที่มีตัวอักษร**, หรือ
**PDF ที่ไม่มีตัวอักษร** (ไฟล์สแกน หรือไฟล์ที่ได้จาก "Print to PDF" ซึ่งแปลงตัวเลขเป็นรูป) — กรณีหลังระบบจะอ่านด้วย
**OCR** แล้ว **"ตรวจยอดคงเหลือ" อัตโนมัติ** (ยอดก่อนหน้า ± จำนวนเงิน = ยอดคงเหลือ) ถ้า OCR อ่านเลขผิดแม้ตัวเดียว
ห่วงโซ่ยอดจะพังและระบบ **ปฏิเสธ** ไม่บันทึกเลขที่ผิด · รายงาน **Line Man แบบ Balance-Report** (ไฟล์ Excel หัวคอลัมน์
อังกฤษ) ก็รองรับเป็นรายงาน settlement ที่ถูกต้องแล้ว (เดิมเคยถูกปฏิเสธ)

**ขั้นตอนทดสอบ:**
1. อัป KTB เป็น Excel/CSV (ถ้ามี) → ตรวจจำนวนรายการ/ยอดถูกต้อง
2. อัป KTB เป็น PDF ที่ไม่มีตัวอักษร (เช่นไฟล์จาก Print to PDF) → ระบบขึ้น chip "🔍 อ่านด้วย OCR — โปรดตรวจยอดก่อนยืนยัน"
3. เทียบยอดรวมในตัวอย่างกับยอดสรุปท้ายสเตทเมนต์ว่าตรงกัน ก่อนกดยืนยัน
4. อัปไฟล์ Line Man "Balance-Report-*.xlsx" ในช่อง Line Man → ต้องอ่านได้ ไม่ถูกปฏิเสธ

**ผลที่คาดหวัง:** KTB Excel/PDF อ่านได้ถูกต้อง, PDF ไม่มีตัวอักษรอ่านด้วย OCR + ขึ้น chip เตือน + ยอดผ่านการตรวจยอดคงเหลือ
(ถ้าเลขเพี้ยนจะถูกปฏิเสธพร้อมข้อความแนะนำให้ใช้ Excel/CSV), Line Man Balance-Report อัปได้

**ผลการทดสอบ:** ☐ ผ่าน ☐ ไม่ผ่าน | ผู้ทดสอบ: __________ วันที่: ________ | หมายเหตุ: ________________

### TC-13 · Line Man — จ่ายตามยอดสะสม ฿500 + เดือนยอดน้อยตกไปวันที่ 1 เดือนถัดไป
**บทบาท:** เจ้าหน้าที่กระทบยอด / ฝ่ายบัญชี

**📖 การใช้งาน (narrative):** LINE MAN **ไม่ได้โอนรายวันแบบ Grab** — เงินสุทธิจะ **"สะสม" จนเกิน ฿500** แล้วจึงโอน
เข้าบัญชี (วันเล็ก ๆ ต่ำกว่า ฿50 ก็ถูกนับสะสมด้วย) ถ้าทั้งเดือนยอดยัง **ไม่ถึง ฿500** LINE MAN จะโอนยอดทั้งเดือนใน
**"วันที่ 1 ของเดือนถัดไป"** ระบบจะจับคู่เงินก้อนนั้น **กลับมาให้เดือนที่เป็นเจ้าของยอดโดยอัตโนมัติ** (payout trace ขึ้น
✓ ตรง ไม่ค้างเป็น "รอเงินเข้า" ตลอด) และจะ **ไม่นับเงินก้อนเดิมซ้ำ** ในเดือนถัดไป (ไม่เกิดยอดเกินปลอม)

**ขั้นตอนทดสอบ:**
1. เลือกสาขา/เดือนที่ยอด LINE MAN ทั้งเดือนน้อย (< ฿500) — กางการ์ด LINEMAN ดู payout trace
2. อัปสเตทเมนต์ KBANK ของ "เดือนถัดไป" ด้วย (เงินโอน LINE MAN จะอยู่ราววันที่ 1)
3. ตรวจว่าเดือนนั้น payout trace ขึ้น ✓ ตรง ผูกกับเงินโอนวันที่ 1 ของเดือนถัดไป (ไม่ค้าง "รอเงินเข้า")
4. เปิดเดือนถัดไป — ตรวจว่าเงินก้อนวันที่ 1 ไม่ถูกนับเป็นยอดเกิน/รายได้ของเดือนใหม่

**ผลที่คาดหวัง:** ยอดสะสม (รวมวันเล็ก ๆ) จับคู่กับเงินโอนก้อนเดียว, เดือนยอดน้อยผูกกับเงินโอนวันที่ 1 เดือนถัดไป = ✓ ตรง
(ไม่ค้างรอเงินเข้า), เดือนถัดไปไม่เกิดยอดเกินปลอมจากเงินก้อนเดิม

**ผลการทดสอบ:** ☐ ผ่าน ☐ ไม่ผ่าน | ผู้ทดสอบ: __________ วันที่: ________ | หมายเหตุ: ________________

### TC-14 · ตรวจผลต่างรายวัน — รับทราบทีละวัน (กระทบยอดตามวันที่)
**บทบาท:** เจ้าหน้าที่กระทบยอด

**📖 การใช้งาน (narrative):** ผลต่างของช่องทาง (เช่น เงินสด / Line Man) ต้องกระทบยอด **"ตามวันที่"** ไม่ใช่ยอดรวมทั้งก้อน ·
กางช่องทางที่ต่างจะมีตาราง **"ตรวจผลต่างรายวัน"** โชว์ทุกวันที่ต่าง กดปุ่ม **"รับทราบวันนี้"** ใส่เหตุผลแยกราย วัน
(อย่างน้อย 10 ตัวอักษร) เมื่อรับทราบครบทุกวัน ช่องทางนั้นจะเคลียร์ออกจาก "เหลือ N เรื่อง" เอง · เหตุผลรายวันติดไปในไฟล์ Excel ปิดเดือน

**ขั้นตอนทดสอบ:**
1. เปิดสาขาที่มีผลต่าง กดการ์ดช่องทางที่ขึ้น "ตรวจผลต่าง..."
2. ดูตาราง "ตรวจผลต่างรายวัน" — แต่ละวันที่ต่างมีปุ่ม "รับทราบวันนี้"
3. กดรับทราบทีละวัน ใส่เหตุผล (สั้นกว่า 10 ตัวอักษรต้องถูกปฏิเสธ)
4. เมื่อครบทุกวัน ตรวจว่าช่องทางหายจาก "เหลือ N เรื่อง" และวันที่รับทราบขึ้น ✓

**ผลที่คาดหวัง:** รับทราบแยกรายวันได้, เหตุผล <10 ตัวถูกปฏิเสธ, ครบทุกวัน → ช่องทางเคลียร์ปิดเดือนได้,
เหตุผลรายวันอยู่ในไฟล์ Excel ปิดเดือน (ชีต Daily acknowledged variances)

**ผลการทดสอบ:** ☐ ผ่าน ☐ ไม่ผ่าน | ผู้ทดสอบ: __________ วันที่: ________ | หมายเหตุ: ________________

### TC-15 · รายงานการจับคู่รายวัน — สรุปบัญชีรายวัน (ยอดเต็ม/ส่วนลดแยก + รหัสบัญชี)
**บทบาท:** ฝ่ายบัญชี

**📖 การใช้งาน (narrative):** รายงานการจับคู่รายวันมี **"📅 สรุปบัญชีรายวัน"** ไล่ทุกวัน × ช่องทาง บันทึกเป็น **"ยอดเต็ม (gross)"**
โดยแยกบรรทัด ส่วนลด / ค่าธรรมเนียม / VAT / สุทธิ — ใช้ลงบัญชีรายวันได้ · มีคอลัมน์ **รหัสบัญชี / ชื่อบัญชี** (เว้นว่างก่อน
เติมภายหลังผ่าน `/api/account-map`) · ส่วน **"💰 สรุปการรับเงินทั้งเดือน"** (ยอดเต็ม·ส่วนลด·ค่าธรรมเนียม·VAT·สุทธิ +
ร่างบันทึกบัญชี Dr/Cr) ยังอยู่ครบเป็นสรุปทั้งเดือน · บรรทัด **"ส่วนลด"** รวม **ส่วนลดบนบิล (เด็ก/ผู้สูงอายุ/วันเกิด ฯลฯ)**
จาก `pos_coupon_day` ด้วย — ไม่ใช่แค่ส่วนลดที่จ่ายผ่านคูปอง (แต้ม KTC/BAY ไม่นับซ้ำ)

**ขั้นตอนทดสอบ:**
1. เปิด ⋯ เพิ่มเติม → รายงานการจับคู่รายวัน (หรือหน้าสาขา → 🖨️)
2. ตรวจส่วน "📅 สรุปบัญชีรายวัน" — มีคอลัมน์ ยอดเต็ม / ส่วนลด แยกกัน + รหัสบัญชี/ชื่อบัญชี
3. สาขาที่ใช้คูปองเด็ก/ผู้สูงอายุเยอะ (เช่น อุดรธานี): ตรวจว่าบรรทัด "ส่วนลด" มียอด **ไม่ใช่ 0**
4. (ผู้จัดการ) ตั้งรหัสบัญชีผ่าน `/api/account-map` แล้วรีเฟรช — รหัส/ชื่อบัญชีต้องขึ้นในรายงาน
5. ตรวจ "💰 สรุปการรับเงินทั้งเดือน" ว่ามีคอลัมน์ส่วนลด และร่างบัญชี Dr=Cr

**ผลที่คาดหวัง:** มีสรุปบัญชีรายวัน (gross + ส่วนลดแยก), **ส่วนลดบนบิล (เด็ก/ผู้สูงอายุ) ปรากฏในบรรทัดส่วนลด (ไม่เป็น 0 ผิดปกติ)**,
คอลัมน์รหัส/ชื่อบัญชีว่างจนกว่าจะตั้งค่า แล้วขึ้นตามที่ตั้ง, สรุปทั้งเดือนยังครบ + ร่างบัญชีสมดุล

**ผลการทดสอบ:** ☐ ผ่าน ☐ ไม่ผ่าน | ผู้ทดสอบ: __________ วันที่: ________ | หมายเหตุ: ________________

### TC-16 · รายงานข้อผิดพลาดประจำเดือน (ทุกประเภท ไม่ใช่แค่บันทึกผิดช่อง)
**บทบาท:** ฝ่ายบัญชี / ผู้จัดการ

**📖 การใช้งาน (narrative):** รายงานเดิม "เงินบันทึกผิดช่อง" ขยายเป็น **"ข้อผิดพลาดประจำเดือน"** รวมข้อผิดพลาดทุกชนิดของเดือน:
ยอดต่าง, เงินเข้าเกิน (ไม่มี POS), ขาดเอกสาร, เงินโอนเข้าไม่ครบ/ช้า, รหัสยังไม่ตั้งธนาคาร และบันทึกผิดช่อง — แต่ละแถวมี
ประเภท + สถานะ (ค้าง/รับทราบแล้ว/แก้ไขแล้ว) + เหตุผล · รายละเอียดบันทึกผิดช่อง + ใบเซ็นยังอยู่ครบเป็นส่วนท้าย

**ขั้นตอนทดสอบ:**

2. ตรวจตาราง "ข้อผิดพลาดทั้งหมด" — มีหลายประเภท ไม่ใช่แค่บันทึกผิดช่อง + สถานะ ค้าง/รับทราบ/แก้ไข

4. กด ⬇ Excel (แผ่นแรก "ข้อผิดพลาดทั้งหมด") และ 🖨️ พิมพ์/PDF

**ผลที่คาดหวัง:** เห็นข้อผิดพลาดทุกประเภทของเดือน + สถานะ + เหตุผล, กรองรายสาขาได้, Excel/พิมพ์ออกได้
(แผ่น/หัวข้อ "ข้อผิดพลาดทั้งหมด"), รายละเอียดบันทึกผิดช่องยังอยู่ครบ

**ผลการทดสอบ:** ☐ ผ่าน ☐ ไม่ผ่าน | ผู้ทดสอบ: __________ วันที่: ________ | หมายเหตุ: ________________

### TC-17 · สรุปบัญชีรายวัน (รายใบ) — แต่ละวัน = 1 การ์ด + เลือกสาขา + พิมพ์ PDF
**บทบาท:** ฝ่ายบัญชี

**📖 การใช้งาน (narrative):** ส่วน **"📅 สรุปบัญชีรายวัน"** (ยอดเต็ม/ส่วนลดแยกบรรทัด) ถูกดึงออกมาเป็น **"หน้าแยกของตัวเอง"**
และแสดงเป็น **"การ์ดรายวัน — 1 วัน = 1 ใบบันทึกบัญชี"** ดูทีละสาขา (เลือกจากดรอปดาวน์) · ด้านบนมีแถบสรุปทั้งเดือน
(ยอดเต็มรวม·ส่วนลด·ค่าธรรมเนียม·VAT·สุทธิ·จำนวนใบ) · แต่ละการ์ดไล่ทุกช่องทางของวันนั้นเป็นยอดเต็ม แยกบรรทัดส่วนลด/ค่าธรรมเนียม/VAT
→ สุทธิ + "รวมวันนี้" · รหัสบัญชีมาจากที่ตั้งใน ตั้งค่าระบบ · **แต่ละการ์ดมีปุ่มพับ "📒 ร่างบันทึกบัญชีวันนี้ (Dr/Cr)"** กางออกดูคู่เดบิต/เครดิตของวันนั้น (มีในฉบับพิมพ์ PDF ด้วย) · ตัวเลขชุดเดียวกับ TC-15 (จอ ↔ กระดาษตรงกัน) มีปุ่มพิมพ์ PDF เป็นแผ่นการ์ด

**ขั้นตอนทดสอบ:**
1. เปิด ⋯ เพิ่มเติม → "📅 สรุปบัญชีรายวัน (รายใบ)"
2. เลือกสาขาจากดรอปดาวน์มุมขวา — การ์ดเปลี่ยนตามสาขา (สาขาที่ไม่มีรายการขึ้นข้อความว่าง)
3. ตรวจการ์ดวันหนึ่ง: มี ยอดเต็ม / ส่วนลด (แยกบรรทัด) / ค่าธรรมเนียม / VAT / สุทธิ + แถว "รวมวันนี้"
4. กางปุ่ม "📒 ร่างบันทึกบัญชีวันนี้ (Dr/Cr)" → เดบิต (เงินสด/ธนาคารสุทธิ·ส่วนลด·ค่าธรรมเนียม·VAT) = เครดิต (รายได้เต็มยอด)
5. เทียบยอดรวมทั้งเดือนด้านบนกับ §สรุปบัญชีรายวัน ในรายงานจับคู่ (TC-15) ว่าตรงกัน
6. กด "🖨️ พิมพ์/PDF" → ออกเป็นแผ่นการ์ดรายวัน (เลือกสาขาเดียว หรือเว้น = ทุกสาขา หน้าละสาขา) มีร่างบัญชี Dr/Cr ในทุกการ์ด

**ผลที่คาดหวัง:** หน้าแสดงการ์ด 1 วัน/ใบ ครบทุกวันที่มีรายการ, ยอดเต็ม/ส่วนลดแยกบรรทัดถูกต้อง + รวมวันนี้ + รวมทั้งเดือน,
**ร่างบันทึกบัญชี Dr/Cr ต่อวันสมดุล (Dr=Cr)**, เลือกสาขาได้, รหัสบัญชีขึ้นตามที่ตั้ง, ตัวเลขตรงกับ TC-15, พิมพ์ PDF เป็นการ์ดได้

**ผลการทดสอบ:** ☐ ผ่าน ☐ ไม่ผ่าน | ผู้ทดสอบ: __________ วันที่: ________ | หมายเหตุ: ________________

### TC-18 · บันทึกผิดช่อง (ย้ายช่อง) — กระทบสองยอดพร้อมกัน
**บทบาท:** เจ้าหน้าที่กระทบยอด / ผู้จัดการ

**📖 การใช้งาน (narrative):** ถ้ายอดถูกบันทึกผิดช่อง (เช่น ลูกค้าสแกน QR แต่พนักงานกดเป็นเงินสด) เจ้าหน้าที่ระบุ
"ย้ายจากช่องผิด → ช่องถูก + จำนวนเงิน" โปรแกรมจะ **ลดยอดช่องผิดและเพิ่มยอดช่องถูกพร้อมกันทันที** (กระทบสองยอด)
โดยไม่ต้องรันจับคู่ใหม่ · **ย้อนกลับได้** (↩ ยกเลิก) · ทุกการย้ายเข้าไปอยู่ในรายงานเงินบันทึกผิดช่อง (TC-06) ติดป้าย "ย้ายด้วยมือ"

**ขั้นตอนทดสอบ:**
1. หน้าสาขา → การ์ด "⇄ บันทึกผิดช่อง (ย้ายช่อง)" → "+ บันทึกผิดช่อง"
2. เลือก จากช่อง (ผิด) → ไปช่อง (ถูก) + ใส่จำนวนเงิน + เหตุผล → "บันทึกการย้าย"
3. ตรวจว่ายอดทั้งสองช่องเปลี่ยนพร้อมกันในตารางสรุป + รายงานจับคู่รายวัน + Dashboard
4. กด "↩ ยกเลิก" → ยอดกลับไปช่องเดิม
5. เปิด ⋯ → "⇄ รายงานเงินบันทึกผิดช่อง" ตรวจว่ารายการย้ายขึ้นพร้อมป้าย "ย้ายด้วยมือ"

**ผลที่คาดหวัง:** ย้ายแล้วช่องผิดลด+ช่องถูกเพิ่มเท่ากัน, รายวันตรงกับรายเดือน (ไม่ทำให้ผลต่างเพี้ยน), ยกเลิกคืนค่าได้,
เข้าช่องเดียวกัน/จำนวน≤0 ถูกปฏิเสธ, ขึ้นในรายงานพร้อมป้ายย้ายด้วยมือ

**ผลการทดสอบ:** ☐ ผ่าน ☐ ไม่ผ่าน | ผู้ทดสอบ: __________ วันที่: ________ | หมายเหตุ: ________________

### TC-19 · Dashboard รายได้ตามช่องทางรายวัน (ทุกสาขาในวันเดียว · เลือกวันปฏิทิน)
**บทบาท:** ผู้จัดการ / ฝ่ายบัญชี

**📖 การใช้งาน (narrative):** หน้า Dashboard ใหม่: เลือกวันจากปฏิทิน → เห็นรายได้แยกช่องทางของ "ทุกสาขา" ในวันนั้นพร้อมกัน
+ แถบยอดรวมทุกสาขา · มีปุ่มสลับ **3 โหมด**: (1) **เงินเข้าจริง (บัญชี)** — ยอดเต็ม/ส่วนลด/สุทธิ, แยกคูปอง KTC/BAY (แต้ม) =
เงินรับจริง; (2) **ยอด POS** — ยอดที่เครื่อง POS บันทึกแยกช่องทาง; (3) **ประกบ POS ↔ เงินเข้า** — แต่ละช่องทางแสดง
POS | เงินเข้าจริง | ต่าง (เงินเข้า = ยอดเข้าบัญชี/ค่ายบัตรตาม statement·settlement). สลับโหมดไม่ต้องโหลดใหม่

**ขั้นตอนทดสอบ:**
1. เปิด ⋯ เพิ่มเติม → "📊 รายได้ตามช่องทาง รายวัน (Dashboard)"
2. เลือกวันจากปฏิทินมุมขวา — การ์ดทุกสาขาปรับตามวันนั้น
3. โหมด "เงินเข้าจริง (บัญชี)": ตรวจ ช่องทาง/ยอดเต็ม/ส่วนลด/สุทธิ + แถว "รวมสาขา" + แถบยอดรวม
4. กดปุ่ม "ยอด POS": เห็นยอดที่ POS บันทึกแยกช่องทาง
5. กดปุ่ม "ประกบ POS ↔ เงินเข้า": เห็น POS | เงินเข้า | ต่าง (ช่องที่ยังไม่อัปเอกสาร เงินเข้า = 0 → ต่างติดลบเท่ายอด POS)
6. ลองเลือกวันที่ไม่มีข้อมูล → ขึ้นข้อความว่าง ไม่ error

**ผลที่คาดหวัง:** เลือกวันได้, สลับ 3 โหมดได้ไม่โหลดใหม่, ทุกสาขา (เฉพาะ master) แสดงแยกการ์ด, ยอดรวมเปลี่ยนตามโหมด, COUPON = แต้มเท่านั้น + บรรทัดส่วนลดแยก, ประกบ POS↔เงินเข้า + ผลต่างถูกต้อง, วันไม่มีข้อมูลไม่ค้าง

### TC-20 · บัญชีรายได้ — ยอดเต็มก่อนหักส่วนลด + ส่วนลดจากคูปอง (ไม่รวม KTC/BAY)
**บทบาท:** ฝ่ายบัญชี

**📖 การใช้งาน (narrative):** การบันทึกบัญชีลง "ยอดเต็มก่อนหักคูปองส่วนลด" แล้วแยกบรรทัด "ส่วนลด" เป็นยอดหัก ·
ส่วนลดมาจากคูปองส่วนลด (ผู้สูงอายุ/เด็ก/อื่น ๆ) เท่านั้น — คูปอง KTC/BAY ที่ใช้แต้มถือเป็น "เงินรับจริง" (ค่ายบัตรจ่ายคืน) ไม่ใช่ส่วนลด ·
เห็นได้ทั้งในสรุปบัญชีรายวัน (TC-17), รายงานจับคู่รายวัน (§สรุปการรับเงิน + ร่างบัญชี), และ Dashboard (TC-19)

**ขั้นตอนทดสอบ:**
1. เปิด "📅 สรุปบัญชีรายวัน (รายใบ)" ของสาขาที่มีคูปอง
2. ตรวจว่าช่อง COUPON = เฉพาะแต้ม KTC/BAY (เงินรับจริง) + มีบรรทัด "ส่วนลด (คูปอง)" แยก = ยอดหัก
3. ตรวจว่า ยอดเต็ม (gross) = ยอดก่อนหักส่วนลด, สุทธิ = ยอดเต็ม − ส่วนลด − ค่าธรรมเนียม − VAT
4. เปิดรายงานจับคู่รายวัน → §"💰 สรุปการรับเงิน" + "📒 ร่างบันทึกบัญชี": รายได้ (Cr) = ยอดเต็ม, ส่วนลด (Dr) รวมคูปองส่วนลด, Dr = Cr

**ผลที่คาดหวัง:** ยอดเต็มไม่หักส่วนลด, ส่วนลดแยกบรรทัดมาจากคูปองส่วนลด (ไม่รวม KTC/BAY), KTC/BAY อยู่ในเงินรับจริง, สุทธิถูกต้อง, ร่างบัญชี Dr = Cr

**ผลการทดสอบ:** ☐ ผ่าน ☐ ไม่ผ่าน | ผู้ทดสอบ: __________ วันที่: ________ | หมายเหตุ: ________________

### TC-24 · Bank Coverage (#bankcov) — สถานะครอบคลุมสเตทเมนต์ธนาคาร (session-scoped)
**บทบาท:** ฝ่ายบัญชี / ผู้ตรวจสอบ

**ขั้นตอนทดสอบ:**
1. เปิด ⋯ เพิ่มเติม → "วินิจฉัย" → "🏦 Bank Coverage"

### TC-26 · โอนภายใน — รหัส IORSDT/NBSDT ถูกแนะนำให้ตัดออกทุกยอด และ "ตัดออกทั้งหมด" ส่งคำขอเดียว
**บทบาท:** พนักงานสาขา / ผู้จัดการ

**📖 การใช้งาน (narrative):** เงินเข้าที่มีรหัสโอนระหว่างบัญชี/ระหว่างธนาคารของ KTB (IORSDT, NBSDT) ไม่ใช่ยอดขาย — สาขาไม่มีรหัสรับโอนใน POS เดิมระบบแนะนำให้ตัดออกเฉพาะยอดก้อนใหญ่เลขกลม ยอดเล็กต้องหาเอง ตอนนี้ทุกบรรทัดที่มีรหัสนี้ขึ้นในการ์ดโอนภายในพร้อมป้าย "รหัสโอนภายใน" และปุ่มตัดออกทั้งหมดส่งคำขอเดียว (`POST /api/bank-lines/bulk-ignore`) บรรทัดที่เปลี่ยนไม่ได้จะถูกข้ามพร้อมเหตุผล

**ขั้นตอนทดสอบ:**
1. อัปโหลดสเตทเมนต์ที่มีบรรทัด IORSDT ยอดต่ำกว่า 100,000 และบรรทัดก้อนใหญ่เลขกลม
2. เปิดหน้าแรกของสาขา/เดือนนั้น → การ์ด "พบยอดโอนเข้าที่น่าจะเป็นการโอนกันเอง" มีทั้งสองบรรทัด บรรทัด IORSDT ติดป้าย "รหัสโอนภายใน" อีกบรรทัดติดป้าย "ก้อนใหญ่เลขกลม"
3. กด "ตัดออกทั้งหมด" → toast แจ้งจำนวนที่ตัดออก (และจำนวนที่ข้าม ถ้ามี) ทั้งสองบรรทัดหายจากช่องรอ
4. จับคู่บรรทัดหนึ่งด้วยมือก่อน แล้วกดตัดออกทั้งหมด → บรรทัดนั้นถูกข้ามพร้อมเหตุผล "manually matched" บรรทัดอื่นยังถูกตัดออกตามปกติ
5. เปิด ⋯ เพิ่มเติม → ประวัติการแก้ไข → ทุกบรรทัดที่ตัดออกมีรายการ audit ของตัวเองพร้อม note

**ผลที่คาดหวัง:** ยอดที่มีรหัส IORSDT/NBSDT ถูกแนะนำทุกขนาด; ตัดออกทั้งหมด = คำขอเดียว commit เดียว; บรรทัดที่เปลี่ยนไม่ได้ถูกข้ามพร้อมเหตุผล ไม่ทำให้ทั้งชุดล้ม; ย้อนกลับได้ (`ignored=false`)

### TC-35 · บัตรเครดิต ขั้น 2 — เงินเข้าต้นเดือนที่เดือนก่อนจับคู่ไปแล้ว ต้องไม่ถูกนับเป็น settlement ของเดือนนี้ซ้ำ
**บทบาท:** ผู้จัดการ / ผู้สอบบัญชี

**📖 การใช้งาน (narrative):** เงินสดฝาก T+1 ของวันสิ้นเดือน และ payout ของ Grab/LINE MAN/บัตร ที่เข้าบัญชีวันที่ 1–7 เป็นเงินของเดือนก่อน (ตัวจับคู่เงินสด/payout มองข้ามเดือนได้) แต่ตัวจับคู่บัตรเครดิตมองเฉพาะในเดือน เดิมจึงเห็นบรรทัดนั้นเป็นผู้สมัครใหม่ — ถ้ายอดสุทธิ settlement ของเดือนนี้บังเอิญเท่ากันภายในค่าเผื่อ จะจับเป็นเงินเข้าของบัตรเดือนนี้ (ขั้น 2 ขึ้น "ตรงกัน" ทั้งที่เงินยังไม่เข้า) ตั้งแต่ 2026-09-05 ตัวจับคู่บัตรตัดบรรทัดที่เดือนก่อนจับไปแล้ว และบรรทัดที่เงินสดเดือนนี้จับไปแล้ว ออกทุกเส้นทาง (หน้าเดือน `reconcile_month`, รายงาน coverage statement)

**ขั้นตอนทดสอบ:**
1. เดือน M: POS เงินสดวันสิ้นเดือน + สเตทเมนต์มีเงินเข้าวันที่ 1 ของเดือน M+1 ยอดเท่ากัน → ช่อง CASH เดือน M ตรงกัน
2. เดือน M+1: อัปโหลดสรุปบัตรที่มี settlement สุทธิยอดเท่ากันในวันที่ 1 → กางแถว CREDIT ค่ายบัตรนั้น
3. ขั้น 2 ต้องขึ้น "รอเงินเข้า" (bank_credit = 0) ไม่ใช่ "ตรงกัน" และรายงาน coverage statement ระบุบรรทัดวันที่ 1 เป็นของเดือนก่อน
4. สเตทเมนต์มีเงินเข้าจริงของบัตรในวันถัดไป → ขั้น 2 ขึ้น "ตรงกัน" ด้วยบรรทัดนั้น
5. ยืนยัน recon tests เขียว (`test_credit_three_way_excludes_credit_carried_from_prev_month`)

**ผลที่คาดหวัง:** บรรทัดเงินเข้าที่เดือนก่อนจับคู่ไปแล้วไม่ถูกนับซ้ำในเดือนใหม่ ทั้งช่องเงินสด/payout/บัตร; ขั้น 2 ของบัตรจับเฉพาะเงินเข้าของเดือนนั้นจริง; ผลเท่ากันทุกหน้าที่คำนวณ

### TC-36 · เปิดงวดใหม่ (ผู้จัดการ) — เปิดเดือนที่ปิดแล้วด้วยรหัสผู้จัดการ + เหตุผล
**บทบาท:** ผู้จัดการ

**📖 การใช้งาน (narrative):** เดือนที่ปิดแล้ว (approved/closed) ถูกล็อกทั้งหมด ถ้าปิดแล้วพบว่าผิด ผู้จัดการกดปุ่ม “เปิดงวดใหม่ (ผู้จัดการ)” บนแถบ “เดือนนี้ปิดแล้ว” ของหน้าสาขา ต้องใส่เหตุผลอย่างน้อย 10 ตัวอักษร + รหัสผู้จัดการ ระบบบันทึกเหตุผลลงประวัติการแก้ไข แล้วสถานะกลับเป็น “กำลังทำ” · “ส่งกลับแก้” ใช้เฉพาะตอนรอผู้จัดการตรวจ (ก่อนปิด) · สถานะ “ปิดงวดแล้ว (closed)” ตั้งได้หลังอนุมัติแล้วเท่านั้น และการกดปิดเดือนซ้ำในเดือนที่ปิดแล้วถูกปฏิเสธ (เพิ่ม 2026-10)

**ขั้นตอนทดสอบ:**
1. ผู้จัดการเข้าหน้าสาขาที่ “ปิดเดือนแล้ว” → แถบ “เดือนนี้ปิดแล้ว” มีปุ่ม “เปิดงวดใหม่ (ผู้จัดการ)”
2. กดปุ่ม ใส่เหตุผลน้อยกว่า 10 ตัวอักษร → ระบบเตือน เปิดไม่ได้
3. ใส่เหตุผลครบ แต่รหัสผู้จัดการผิด → เปิดไม่ได้ สถานะยังเป็น “ปิดเดือนแล้ว”
4. ใส่เหตุผลครบ + รหัสถูก → สถานะกลับเป็น “กำลังทำ” · เปิด “ประวัติการแก้ไข” (#auditlog) เห็นการเปลี่ยนสถานะพร้อมเหตุผลที่เปิดงวด
5. ส่งตรวจ → ปิดเดือนอีกครั้ง → ได้หลักฐานแช่แข็งชุดใหม่ · (ถ้าเปิดค้างไว้สองแท็บ) กดปิดเดือนในแท็บที่สองหลังปิดไปแล้ว → ระบบปฏิเสธ ผู้อนุมัติเดิมไม่ถูกเปลี่ยน

**ผลที่คาดหวัง:** เหตุผล <10 ตัวอักษรหรือรหัสผิด → เปิดไม่ได้; ครบ + ถูก → กลับเป็น “กำลังทำ” พร้อมบันทึกเหตุผล/ผู้เปิด/เวลา; ปิดใหม่ได้หลักฐานชุดใหม่; อนุมัติซ้ำถูกปฏิเสธ; ตั้ง closed โดยข้ามขั้นอนุมัติไม่ได้

**ผลการทดสอบ:** ☐ ผ่าน ☐ ไม่ผ่าน | ผู้ทดสอบ: __________ วันที่: ________ | หมายเหตุ: ________________

### TC-37 · กดซ้ำ / ดับเบิลคลิก — บันทึกครั้งเดียว
**บทบาท:** เจ้าหน้าที่กระทบยอด

**📖 การใช้งาน (narrative):** ปุ่มบันทึกสำคัญกันการกดซ้ำแล้ว — ระหว่างรอผล ปุ่มเป็นสีจางกดไม่ได้ และฝั่งเซิร์ฟเวอร์กันการจับคู่ซ้ำ/ย้ายช่องซ้ำอีกชั้น (ย้ายช่องยอดเดียวกันซ้ำภายใน 10 วินาทีถูกปฏิเสธ) — ป้องกันยอดถูกบันทึกสองครั้ง

**ขั้นตอนทดสอบ:**
1. ดับเบิลคลิก “ใช่ เป็นเงินก้อนเดียวกัน” ในการ์ดเงินผิดช่อง → ปุ่มจางระหว่างรอ บันทึกครั้งเดียว (ยอดย้ายครั้งเดียว)
2. ใน “จับคู่ละเอียด” ติ๊กรายการแล้วดับเบิลคลิก “จับคู่” → เกิดคู่เดียว
3. รับทราบผลต่าง / รับทราบวันนี้ แล้วดับเบิลคลิก “บันทึกรับทราบ” → มีบันทึกเดียว
4. ดับเบิลคลิก “ส่งตรวจ” → เปลี่ยนสถานะครั้งเดียว ไม่มีข้อความผิดพลาด
5. บันทึกผิดช่อง (ย้ายช่อง) ยอดเดียวกันซ้ำภายใน 10 วินาที → ข้อความ “บันทึกการย้ายช่องนี้ไปแล้วเมื่อสักครู่ (กดซ้ำ?)”
6. เปิดประวัติการแก้ไข → แต่ละการกระทำมีรายการเดียว

**ผลที่คาดหวัง:** ทุกปุ่มบันทึกครั้งเดียว, ปุ่มจางระหว่างรอ, ยอด/คู่/การรับทราบไม่ซ้ำ, ย้ายช่องซ้ำภายใน 10 วินาทีถูกปฏิเสธ

**ผลการทดสอบ:** ☐ ผ่าน ☐ ไม่ผ่าน | ผู้ทดสอบ: __________ วันที่: ________ | หมายเหตุ: ________________

### TC-38 · ด่านอัปโหลด — เดือนที่ปิดแล้ว / เลือกเดือนผิด / ไฟล์ซ้ำ
**บทบาท:** เจ้าหน้าที่กระทบยอด

**📖 การใช้งาน (narrative):** ตัวจับคู่อ่านแต่ละบรรทัดตามวันที่ของบรรทัดเอง ไม่ใช่เดือนที่เลือกตอนอัป จึงมีด่านกัน: (1) เอกสารที่มีรายการของเดือนที่ปิด/อนุมัติแล้วถูกปฏิเสธ; (2) สเตทเมนต์ธนาคาร / Grab / LINE MAN ที่ไม่มีรายการในเดือนที่เลือกเลยถูกปฏิเสธ — ให้เลือกเดือนให้ตรง (สรุปยอดบัตรเครดิตยกเว้น เพราะยอดขายสิ้นเดือนจ่ายวันที่ 1 เดือนถัดไป); (3) ไฟล์เดิมที่เคยอัปให้สาขานี้แล้ว (เดือนไหนก็ตาม) ถูกปฏิเสธ

**ขั้นตอนทดสอบ:**
1. ใช้เดือน M ที่ปิดแล้วของสาขาทดสอบ → อัปสเตทเมนต์ที่มีรายการของเดือน M (แม้เลือกเดือน M+1) → ปฏิเสธ “เอกสารนี้มีรายการของเดือน M ซึ่งปิด/อนุมัติแล้ว”
2. อัปสเตทเมนต์ของเดือนอื่นทั้งฉบับ โดยเลือกเดือนที่ไม่ตรง → ปฏิเสธ “รายการในเอกสารนี้เป็นของเดือน … ไม่ใช่เดือนที่เลือก” · เลือกเดือนให้ตรงแล้วอัปได้
3. อัปไฟล์เดิมซ้ำ (เดือนเดิมหรือเดือนอื่นของสาขาเดียวกัน) → ปฏิเสธ “ไฟล์นี้อัปโหลดไปแล้วสำหรับสาขานี้ (เดือน …)”
4. อัปสรุปยอดบัตรที่วันจ่ายเป็นวันที่ 1 ของเดือนถัดไป ในเดือนที่ขาย → อัปได้ตามปกติ
5. อัป PDF ที่ตั้งรหัสเฉพาะสิทธิ์เจ้าของ (เปิดอ่านได้โดยไม่ใส่รหัส) → อ่านได้โดยไม่ต้องใส่รหัส

**ผลที่คาดหวัง:** ทั้งสามกรณีถูกปฏิเสธพร้อมข้อความบอกเหตุผล ไม่มีรายการใดถูกบันทึก, สรุปยอดบัตรข้ามเดือนอัปได้, PDF สิทธิ์เจ้าของอ่านได้, ตัวเลขของเดือนที่ปิดแล้วไม่เปลี่ยน

**ผลการทดสอบ:** ☐ ผ่าน ☐ ไม่ผ่าน | ผู้ทดสอบ: __________ วันที่: ________ | หมายเหตุ: ________________

### TC-39 · สเตทเมนต์ดาวน์โหลดซ้ำ — ข้ามบรรทัดที่บันทึกไว้แล้ว
**บทบาท:** เจ้าหน้าที่กระทบยอด

**📖 การใช้งาน (narrative):** สเตทเมนต์ที่ดาวน์โหลดจากธนาคารใหม่ (เช่น ช่วงวันที่ทับกับไฟล์เดิม) เป็นไฟล์คนละไฟล์แต่มีบรรทัดเดิมซ้ำ — ระบบข้ามบรรทัดที่บันทึกไว้แล้ว (วันที่/ยอด/ยอดคงเหลือเดียวกัน) บันทึกเฉพาะบรรทัดใหม่ และบอกจำนวนที่ข้าม ถ้าซ้ำทั้งฉบับระบบปฏิเสธ — เงินเข้าจึงไม่ถูกนับสองเท่า

**ขั้นตอนทดสอบ:**
1. อัปสเตทเมนต์วันที่ 1–15 ของเดือนแล้วยืนยัน
2. ดาวน์โหลดสเตทเมนต์วันที่ 1–31 (ทับช่วงเดิม) แล้วอัป → ตัวอย่างขึ้น “ซ้ำกับที่มีอยู่ N รายการ (จะข้าม)”
3. ยืนยัน → ข้อความ “บันทึกแล้ว X รายการ · ข้ามรายการซ้ำ N” · เงินเข้าวันที่ 1–15 ไม่เพิ่มเป็นสองเท่า
4. อัปไฟล์ดาวน์โหลดใหม่ที่ซ้ำทั้งฉบับ → ปฏิเสธ “ทุกรายการในเอกสารนี้ (N รายการ) อัปโหลดไว้แล้วจากไฟล์อื่น — ไม่บันทึกซ้ำ”
5. อัปหลายไฟล์พร้อมกันที่มีบรรทัดซ้ำ → สรุปผลขึ้น “ข้ามบรรทัดซ้ำ N”

**ผลที่คาดหวัง:** บรรทัดซ้ำถูกข้ามและแสดงจำนวน, บรรทัดใหม่บันทึกครบ, เงินเข้าไม่ซ้ำ, ไฟล์ที่ซ้ำทั้งฉบับถูกปฏิเสธ

**ผลการทดสอบ:** ☐ ผ่าน ☐ ไม่ผ่าน | ผู้ทดสอบ: __________ วันที่: ________ | หมายเหตุ: ________________

### TC-40 · รับทราบรายวันแล้วยอดเปลี่ยน — วันกลับมาเป็นผลต่าง (“ยอดเปลี่ยนหลังรับทราบ”)
**บทบาท:** เจ้าหน้าที่กระทบยอด

**📖 การใช้งาน (narrative):** ตอนกด “รับทราบวันนี้” ระบบเก็บผลต่างจริงของวันนั้นตามที่หน้าสาขาแสดง (ไม่ใช่ตัวเลขที่หน้าจอส่ง) ถ้าภายหลังยอดของวันนั้นเปลี่ยนเกิน ฿50 (เช่น อัปเอกสารเพิ่ม) การรับทราบเดิมไม่ครอบคลุมแล้ว วันนั้นกลับมาเป็นผลต่างพร้อมป้าย “ยอดเปลี่ยนหลังรับทราบ” และช่องทางกลับเข้า “เหลือ N เรื่อง” จนกว่าจะรับทราบใหม่

**ขั้นตอนทดสอบ:**
1. เลือกช่องทางที่มีวันต่าง → “รับทราบวันนี้” ใส่เหตุผล → วันนั้นขึ้น ✓ รับทราบ
2. อัปเอกสารเพิ่มที่ทำให้ยอดของวันนั้นเปลี่ยนเกิน ฿50
3. กลับหน้าสาขา → เซลล์วันนั้นมีป้าย “ยอดเปลี่ยนหลังรับทราบ” · ตาราง “ตรวจผลต่างรายวัน” บอกยอดที่เคยรับทราบไว้ · รายละเอียดช่องทางขึ้น “ยอดเปลี่ยนหลังรับทราบ N วัน”
4. กด “รับทราบวันนี้” อีกครั้งพร้อมเหตุผลใหม่ → ป้ายหาย วันนั้นเป็น ✓
5. เทียบ: ถ้ายอดเปลี่ยนไม่เกิน ฿50 → การรับทราบเดิมยังใช้ได้

**ผลที่คาดหวัง:** การรับทราบเก็บผลต่างจริง ณ ตอนนั้น, ยอดเปลี่ยน >฿50 → วันกลับมาเป็นผลต่างพร้อมป้ายและต้องรับทราบใหม่, ≤฿50 ไม่กระทบ, สรุปผลต่างที่รับทราบ (#accepted) แสดงยอดปัจจุบัน (และยอดตอนรับทราบถ้าต่างกัน)

**ผลการทดสอบ:** ☐ ผ่าน ☐ ไม่ผ่าน | ผู้ทดสอบ: __________ วันที่: ________ | หมายเหตุ: ________________

### TC-41 · ปิดเดือนหลังจัดการข้อแตกต่างแล้ว — ปิดได้ ไม่เด้งกลับ
**บทบาท:** ผู้จัดการ

**📖 การใช้งาน (narrative):** ตอนกด “ปิดเดือน” ระบบจับคู่ใหม่อีกรอบ เดิมข้อแตกต่างที่ resolve/รับทราบแล้วถูกสร้างกลับเป็น “รอแก้ไข” ทำให้ปิดไม่ได้ ตอนนี้ข้อแตกต่างที่จัดการแล้ว (ยอดไม่เปลี่ยน) ไม่ถูกเปิดกลับ ช่องทางที่รับทราบครบทุกวันถือว่าเรียบร้อย และคูปองที่ไม่มีข้อมูลแต้มเป็นข้อมูลประกอบ — หน้าสาขาขึ้นว่าพร้อมปิด = ปิดได้ (ข้อจำกัดที่ยังเหลือ: ผลต่างระดับรอบโอนของ Grab/LINE MAN/บัตร บางครั้งยังต้อง resolve หนึ่งครั้งใน #discrepancies)

**ขั้นตอนทดสอบ:**
1. เลือกสาขาที่มีข้อแตกต่าง → resolve (ยอมรับ/ปรับแล้ว) ใน #discrepancies และรับทราบผลต่างที่เหลือ จนหน้าสาขาไม่เหลืองาน
2. ส่งตรวจ → (ผู้จัดการ) กด “ปิดเดือน” + รหัสผู้จัดการ → ปิดสำเร็จ
3. เปิด #discrepancies ของเดือนนั้น (กรองทุกสถานะ) → รายการที่ resolve ไว้ยังเป็นสถานะเดิม ไม่มีรายการ “รอแก้ไข” ใหม่ของยอดเดิม
4. (ถ้ามี) สาขาที่คูปองไม่มีข้อมูลแต้ม → ไม่ขวางการปิดเดือน
5. ถ้ากดปิดแล้วยังขึ้นว่ามีข้อแตกต่างค้าง (ระดับรอบโอน) → resolve รายการนั้นใน #discrepancies หนึ่งครั้ง แล้วปิดอีกครั้ง → สำเร็จ

### TC-42 · จับคู่ด้วยมือ — กันบรรทัดที่ใช้ไม่ได้ + ใช้ยอดจริงของสเตทเมนต์
**บทบาท:** เจ้าหน้าที่กระทบยอด

**📖 การใช้งาน (narrative):** ใน “จับคู่ละเอียด” ระบบตรวจทุกบรรทัดฝั่งเซิร์ฟเวอร์: บรรทัดที่จับคู่ด้วยมือไปแล้ว, ถูกตัดออก (ไม่ใช่รายได้), หรือเป็นของสาขาอื่น/เดือนอื่น ติ๊กไม่ได้พร้อมข้อความบอกเหตุผล และยอดฝั่งเอกสารของคู่ = ยอดจริงของบรรทัดในสเตทเมนต์เสมอ

### TC-50 · เปิดดูเดือนเก่า — ตัวเลขสดอาจเปลี่ยน หลักฐานแช่แข็งไม่เปลี่ยน
**บทบาท:** ผู้จัดการ / ผู้สอบบัญชี

**📖 การใช้งาน (narrative):** รอบ ต.ค. 2569 แก้ตัวจับคู่ (เงินช่วงรอยต่อเดือนไม่นับซ้ำสองเดือน, settlement บัตรที่เข้าวันที่ 1 นับให้เดือนก่อน, KTC Point อยู่ในก้อน KTC ที่ธนาคาร, สรุปบัญชีรายวันช่องบัตรไม่รวมแต้ม KTC/BAY, เงินเข้าหนึ่งบรรทัดนับให้ผู้ให้บริการเดียว, เงินโอน/QR ไม่นับบรรทัดที่เป็น settlement/payout แล้ว) — ตัวเลขสดของเดือนเก่าอาจเปลี่ยน แต่หลักฐานแช่แข็งที่ปิดไว้ไม่เปลี่ยน (คู่มือ §9.16)

**ขั้นตอนทดสอบ:**
1. เลือกเดือนที่ปิดแล้วก่อน ต.ค. 2569 → เปิดหน้าสาขา (ตัวเลขสด) และดาวน์โหลดหลักฐานแช่แข็ง / Excel ปิดเดือน
2. เทียบ: หลักฐานแช่แข็งตรงกับที่ปิดไว้เดิมทุกบาท
3. ถ้าตัวเลขสดต่าง → ตรวจว่าต่างในช่องที่ระบุใน §9.16 (บัตร / Grab / LINE MAN / เงินโอน / QR ช่วงรอยต่อเดือน, KTC Point)
4. ถ้าจำเป็นต้องแก้ → ใช้ “เปิดงวดใหม่ (ผู้จัดการ)” (TC-36) แล้วปิดใหม่

**ผลที่คาดหวัง:** หลักฐานแช่แข็งไม่เปลี่ยน, ความต่างของตัวเลขสดอธิบายได้ตาม §9.16, ไม่มีเงินเข้าก้อนเดียวถูกนับสองเดือน/สองค่าย

**ผลการทดสอบ:** ☐ ผ่าน ☐ ไม่ผ่าน | ผู้ทดสอบ: __________ วันที่: ________ | หมายเหตุ: ________________

### TC-51 · ยอดโอนจากผู้ให้บริการไม่ตรงรายงาน — แสดงบนหน้าสาขา รับทราบได้ในที่เดียว
**บทบาท:** Staff (บัญชี) / ผู้จัดการ

**📖 การใช้งาน (narrative):** ยอดสุทธิในรายงาน Grab / Line Man / บัตรเครดิต ที่ไม่ตรงกับเงินที่โอนเข้าธนาคาร เดิมอยู่แค่ในหน้าข้อแตกต่าง ทำให้หน้าสาขาบอก “พร้อมปิด” แต่กดปิดเดือนไม่ได้ — ตอนนี้แสดงเป็นการ์ดบนหน้าสาขาและนับเป็นเรื่องค้าง (คู่มือ §3.3, §7)

**ขั้นตอนทดสอบ:**
1. เลือกสาขา/เดือนที่รายงาน Grab (หรือ Line Man / บัตร) ยอดสุทธิไม่ตรงกับเงินโอนเข้าธนาคาร → หน้าสาขาขึ้นการ์ดแดง “ยอดโอนจากผู้ให้บริการไม่ตรงรายงาน” แสดงรายงานสุทธิ · เงินเข้า · ต่าง และรายการนี้อยู่ใน “เหลือ N เรื่องก่อนปิดเดือน”
2. กด “ดูรายการโอนรายวัน” → ไปหน้าเงินเข้าธนาคาร (#payout) ของสาขานี้
3. กลับหน้าสาขา → กด “✓ รับทราบ + เหตุผล” ใส่เหตุผลสั้นกว่า 10 ตัวอักษร → ระบบเตือน · ใส่เหตุผลครบ → แถวขึ้น “รับทราบแล้ว” พร้อมเหตุผล และหายจากเรื่องค้าง
4. ส่งตรวจ → ผู้จัดการเห็นแถว “ยอดโอน …” ในตารางสรุปก่อนปิด → ปิดเดือน → ปิดได้ (ไม่ขึ้นข้อแตกต่างค้าง)
5. (ทดสอบย้อน) เปิดงวดใหม่ → กด “เลิกรับทราบ” → แถวกลับมาค้าง · อัปรายงานเพิ่มจนยอดต่างเปลี่ยนเกิน ฿100 → แถวที่รับทราบไว้กลับมาค้างอีกครั้ง

**ผลที่คาดหวัง:** ยอดโอนที่ไม่ตรงเห็นบนหน้าสาขาและนับเป็นเรื่องค้าง, รับทราบ/เลิกรับทราบได้ในการ์ด (บันทึกใน ประวัติการแก้ไข), หน้าสาขาที่ขึ้นว่าพร้อมปิด = กดปิดเดือนได้จริง

**ผลการทดสอบ:** ☐ ผ่าน ☐ ไม่ผ่าน | ผู้ทดสอบ: __________ วันที่: ________ | หมายเหตุ: ________________

### TC-52 · หน้าตาใหม่ + โหมดมืด
**บทบาท:** Staff (บัญชี) / ผู้จัดการ

**📖 การใช้งาน (narrative):** หน้ากระทบยอดใช้ชุดสี ขอบมน และเงาการ์ดเดียวกับแดชบอร์ดหลัก มีปุ่มสลับโหมดมืด/สว่างที่หัวหน้า และแถบสีกลุ่ม “เงิน” ใต้แถบเมนู — ตำแหน่งปุ่ม ขั้นตอน และตัวเลขทุกอย่างเหมือนเดิม (คู่มือ §3.1)

**ขั้นตอนทดสอบ:**
1. เปิด /app/ → หน้าภาพรวมแสดงครบเหมือนเดิม (รายการสาขา แถบความคืบหน้า เมนู 4 โซน) · การ์ดมุมมนมีเงาอ่อน และมีแถบสีแดงใต้แถบเมนู (มือถือ: ขอบบนของเมนูล่าง)
2. กดปุ่มพระจันทร์มุมบนขวา → ทั้งหน้าเป็นโหมดมืด ปุ่มเปลี่ยนเป็นดวงอาทิตย์ ตัวอักษรอ่านชัดทุกกล่อง ไม่มีกล่องพื้นขาวค้าง
3. เปิดหน้าสาขา → กด “ดูรายการ” ของช่องทาง, เปิดดูวัน, กด “✓ รับทราบ + เหตุผล” แล้วกดยกเลิก, เปิด/ปิด “เรียบร้อยแล้ว” → ทำงานเหมือนเดิมในโหมดมืด
4. เปิดหน้าอื่น (รายงาน, สรุปบัญชีรายวัน, ตั้งค่าระบบ, ข้อแตกต่าง, คู่มือ) → ยังเป็นโหมดมืด · กด F5 → ยังเป็นโหมดที่เลือกไว้
5. กดปุ่มอีกครั้ง → กลับโหมดสว่าง · (ทดสอบย้อน) เปิดในหน้าต่างส่วนตัว (ยังไม่เคยเลือก) → หน้าตามธีมของเครื่อง/มือถือ
6. กดแป้น Tab ไล่ปุ่มและแถว → เห็นกรอบโฟกัสสีน้ำเงินรอบปุ่ม/แถวที่เลือกชัดเจน

**ผลที่คาดหวัง:** ตำแหน่งปุ่ม ขั้นตอน และตัวเลขเหมือนเดิมทุกหน้า, โหมดมืดอ่านชัดไม่มีกล่องขาวค้าง, จำค่าข้ามหน้าและหลังรีเฟรช, ยังไม่เคยเลือก = ตามเครื่อง, กรอบโฟกัสเห็นชัด

**ผลการทดสอบ:** ☐ ผ่าน ☐ ไม่ผ่าน | ผู้ทดสอบ: __________ วันที่: ________ | หมายเหตุ: ________________

### TC-59 · เข้าสู่ระบบ — ตั้งรหัสผ่านครั้งแรก, ออกจากระบบ, ล็อกเมื่อใส่ผิด 5 ครั้ง
**บทบาท:** ทุกบทบาท

**📖 การใช้งาน (narrative):** ระบบกระทบยอดมีบัญชีผู้ใช้ของตัวเอง แยกจากแดชบอร์ด (คู่มือ §9.7) · เปิด /app/ แล้วต้องเข้าสู่ระบบก่อน · เข้าครั้งแรกหรือหลังผู้จัดการตั้งรหัสใหม่ให้ ต้องตั้งรหัสผ่านของตัวเอง · ชื่อ + สิทธิ์แสดงมุมขวาบน กดเพื่อเปลี่ยนรหัสผ่าน/ออกจากระบบ · ใส่รหัสผิด 5 ครั้งติดกัน บัญชีถูกล็อก 15 นาที

**ขั้นตอนทดสอบ:**
1. เปิด /app/ (ยังไม่เข้าสู่ระบบ) → ขึ้นหน้า “กระทบยอด — Oshinei” มีช่องชื่อผู้ใช้ รหัสผ่าน ปุ่ม “เข้าสู่ระบบ” (ลองทั้งโหมดสว่าง/มืด และบนมือถือ)
2. ใส่รหัสผิด → ขึ้นข้อความเดียว “ชื่อผู้ใช้หรือรหัสผ่านไม่ถูกต้อง …” (ไม่บอกว่าผิดที่ชื่อหรือรหัส) · ใส่ชื่อที่ไม่มีอยู่ → ข้อความเดียวกัน
3. เข้าด้วยรหัสชั่วคราวที่ผู้จัดการให้ → ระบบให้ตั้งรหัสผ่านใหม่ก่อน (ใส่รหัสเดิม + รหัสใหม่ 2 ครั้ง, สั้นกว่า 8 ตัวไม่ได้) → เข้าหน้าหลักได้
4. มุมขวาบนเห็นชื่อ · สิทธิ์ และไม่มีปุ่ม “รหัส” · กดชื่อ → “ออกจากระบบ” → กลับหน้าเข้าสู่ระบบ · กดย้อนกลับ/รีเฟรชก็ยังต้องเข้าใหม่
5. ใส่รหัสผิด 5 ครั้งติดกัน → ครั้งที่ 6 แม้รหัสถูกก็ยังเข้าไม่ได้ (ล็อก 15 นาที) → ผู้จัดการกด “ตั้งรหัสใหม่” ให้ → เข้าได้ทันที
6. ผู้จัดการเปิด #auditlog / ประวัติการแก้ไข → เห็นรายการเข้า/ออก/เข้าไม่สำเร็จ พร้อมชื่อผู้ใช้และเวลา

**ผลที่คาดหวัง:** ทุกหน้าต้องเข้าสู่ระบบก่อน, ข้อความผิดพลาดไม่บอกใบ้, บังคับตั้งรหัสเองครั้งแรก, ล็อก 15 นาทีหลังผิด 5 ครั้ง, ออกจากระบบได้, ทุกการเข้าออกถูกบันทึก

**ผลการทดสอบ:** ☐ ผ่าน ☐ ไม่ผ่าน | ผู้ทดสอบ: __________ วันที่: ________ | หมายเหตุ: ________________

### TC-60 · ผู้จัดการจัดการผู้ใช้ — เพิ่ม, เปลี่ยนสิทธิ์, ปิดบัญชี, ตั้งรหัสใหม่
**บทบาท:** ผู้จัดการ

**📖 การใช้งาน (narrative):** Admin → ตั้งค่าระบบ → ⑥ ผู้ใช้งานระบบ (เห็นเฉพาะผู้จัดการ) · เพิ่มผู้ใช้ด้วยรหัสชั่วคราว, เปลี่ยนสิทธิ์มีผลทันที, ปิดบัญชีแล้วผู้ใช้หลุดออกทุกเครื่อง, ตั้งรหัสใหม่ปลดล็อก + บังคับตั้งรหัสเองอีกครั้ง · ปิดหรือลดสิทธิ์ผู้จัดการคนสุดท้ายไม่ได้

**ขั้นตอนทดสอบ:**
1. เข้าเป็นผู้จัดการ → Admin → ตั้งค่าระบบ → เลื่อนลงถึง “⑥ ผู้ใช้งานระบบ” → เห็นตาราง ชื่อ / ชื่อผู้ใช้ / สิทธิ์ / สถานะ / เข้าใช้ล่าสุด
2. กด “เพิ่มผู้ใช้” → เพิ่มพนักงานบัญชี 1 คน (สิทธิ์ บัญชี) และ 1 คนสิทธิ์ ดูอย่างเดียว ด้วยรหัสชั่วคราว → แถวใหม่ขึ้น “รอตั้งรหัสใหม่” · ลองชื่อผู้ใช้ซ้ำ/มีเว้นวรรค/รหัสสั้น → ระบบปฏิเสธพร้อมเหตุผล
3. เปลี่ยนสิทธิ์ของคนดูอย่างเดียวเป็น บัญชี → ผู้ใช้คนนั้นรีเฟรชแล้วทำงานได้ทันที · เปลี่ยนกลับ
4. กด “ปิดบัญชี” ผู้ใช้ที่กำลังใช้งานอยู่อีกเครื่อง → เครื่องนั้นกลับไปหน้าเข้าสู่ระบบและเข้าไม่ได้ · กด “เปิดใช้” → เข้าได้อีก
5. กด “ตั้งรหัสใหม่” → ผู้ใช้หลุดจากระบบทุกเครื่อง, เข้าด้วยรหัสชั่วคราวแล้วต้องตั้งรหัสเอง
6. (ทดสอบย้อน) เมื่อมีผู้จัดการคนเดียว ลองเปลี่ยนตัวเองเป็น บัญชี หรือปิดบัญชีตัวเอง → ระบบปฏิเสธ “ต้องมีผู้จัดการที่ใช้งานได้อย่างน้อย 1 คน”
7. #auditlog → เห็นการเพิ่ม/เปลี่ยนสิทธิ์ (ค่าเดิม → ค่าใหม่)/ปิดบัญชี/ตั้งรหัสใหม่ พร้อมชื่อผู้จัดการที่ทำ

**ผลที่คาดหวัง:** ผู้จัดการจัดการบัญชีได้ครบในหน้าเดียว, การเปลี่ยนสิทธิ์/ปิดบัญชี/ตั้งรหัสใหม่มีผลทันที, ไม่มีทางทำให้ระบบไม่มีผู้จัดการ, ทุกการแก้ไขถูกบันทึก

**ผลการทดสอบ:** ☐ ผ่าน ☐ ไม่ผ่าน | ผู้ทดสอบ: __________ วันที่: ________ | หมายเหตุ: ________________

### TC-61 · สิทธิ์ “บัญชี” — ทำงานกระทบยอดได้ แต่ปิดเดือน/เปิดงวด/ตั้งค่าขั้นสูง/จัดการผู้ใช้ไม่ได้
**บทบาท:** Staff (บัญชี)

**📖 การใช้งาน (narrative):** พนักงานบัญชีทำงานประจำได้ทุกอย่าง (อัปโหลด จับคู่ ย้ายช่อง รับทราบ ส่งตรวจ) โดยไม่ต้องใช้ปุ่ม “รหัส” · ปุ่มปิดเดือน/เปิดงวดใหม่/ตั้งค่าขั้นสูงไม่แสดง และถ้าส่งคำสั่งตรงเข้าเซิร์ฟเวอร์ก็ถูกปฏิเสธ · ทุกงานบันทึกชื่อผู้ใช้จริง (คู่มือ §9.7)

**ขั้นตอนทดสอบ:**
1. เข้าเป็นพนักงานบัญชี → เปิดหน้าสาขา → อัปโหลดเอกสาร 1 ไฟล์, จับคู่ด้วยมือ 1 คู่, รับทราบผลต่าง 1 วันพร้อมเหตุผล → ทำได้ทุกอย่างโดยไม่ถามรหัส
2. กด “ส่งตรวจ” → สถานะ “รอผู้จัดการตรวจ” · มีปุ่ม “ส่งกลับแก้” แต่ไม่มีปุ่ม “ปิดเดือน (ผู้จัดการ)”
3. เปิด Admin → ตั้งค่าระบบ → แก้ธนาคารของรหัสรับเงินได้ · ไม่มีปุ่มแก้ lane/พารามิเตอร์ และไม่มีปุ่มบันทึกรหัสสเตทเมนต์ · ไม่มีส่วน “⑥ ผู้ใช้งานระบบ”
4. เปิดเดือนที่ปิดแล้ว → ไม่มีปุ่ม “เปิดงวดใหม่ (ผู้จัดการ)”
5. #auditlog (ผู้จัดการเปิดดู) → งานข้างบนทั้งหมดบันทึกเป็นชื่อผู้ใช้ของพนักงานคนนั้น ไม่ใช่ “staff”

**ผลที่คาดหวัง:** บัญชีทำงานประจำครบ, ปุ่มงานผู้จัดการไม่แสดงและเซิร์ฟเวอร์ปฏิเสธ (“เฉพาะผู้จัดการ”), audit ระบุตัวคนจริง

### TC-62 · สิทธิ์ “ดูอย่างเดียว” — เปิดดูทุกหน้าได้ บันทึกอะไรไม่ได้
**บทบาท:** ผู้บริหาร / ผู้สอบบัญชี (ดูอย่างเดียว)

**📖 การใช้งาน (narrative):** บัญชีดูอย่างเดียวเห็นทุกหน้าและดาวน์โหลดรายงานได้ แต่ปุ่มที่บันทึกข้อมูลทั้งหมดไม่แสดง (อัปโหลด รับทราบ จับคู่ ย้ายช่อง ส่งตรวจ/ปิดเดือน/เปิดงวด บันทึกการตั้งค่า) · เซิร์ฟเวอร์ปฏิเสธทุกคำสั่งบันทึกด้วย “สิทธิ์ดูอย่างเดียว” · เปลี่ยนรหัสผ่านของตัวเองได้

**ขั้นตอนทดสอบ:**
1. เข้าเป็นผู้ใช้ดูอย่างเดียว → หน้าภาพรวม, หน้าสาขา, รายงาน, สรุปบัญชีรายวัน เปิดได้ทุกหน้า ตัวเลขเหมือนที่ผู้จัดการเห็น
2. หน้าสาขา → ไม่มีปุ่มอัปโหลด/หลายไฟล์/ทั้งโฟลเดอร์, “รับทราบ + เหตุผล”, “รับทราบวันนี้”, จับคู่, บันทึกผิดช่อง, ส่งตรวจ
3. Admin → ตั้งค่าระบบ → ดูได้ แต่ช่องเลือก/ปุ่มบันทึกกดไม่ได้หรือไม่แสดง
4. ดาวน์โหลด Excel / ใบรับรอง / รายงานการควบคุมภายใน → ได้
5. กดชื่อมุมขวาบน → เปลี่ยนรหัสผ่านของตัวเอง → ได้

**ผลที่คาดหวัง:** ดูได้ครบ ดาวน์โหลดได้, ไม่มีปุ่มบันทึกใด ๆ, ถ้าส่งคำสั่งบันทึกเซิร์ฟเวอร์ตอบ “สิทธิ์ดูอย่างเดียว”, เปลี่ยนรหัสผ่านตัวเองได้

**ผลการทดสอบ:** ☐ ผ่าน ☐ ไม่ผ่าน | ผู้ทดสอบ: __________ วันที่: ________ | หมายเหตุ: ________________

### TC-63 · ผู้จัดการปิดเดือน/เปิดงวดใหม่ด้วยสิทธิ์ (ไม่ต้องใช้รหัส) + ผู้จัดทำอนุมัติงานตัวเองไม่ได้ + สคริปต์ bulk upload ยังทำงาน
**บทบาท:** ผู้จัดการ (2 คน) / Staff (บัญชี) / ผู้ดูแลระบบ

**📖 การใช้งาน (narrative):** เมื่อเปิดล็อกอิน การปิดเดือน เปิดงวดใหม่ และตั้งค่าขั้นสูงตรวจจาก “สิทธิ์ผู้จัดการ” ของผู้ที่เข้าสู่ระบบ ไม่ถามรหัสผู้จัดการและไม่ต้องพิมพ์ชื่อผู้อนุมัติ · แบ่งแยกหน้าที่ (SoD) เทียบตัวตนจริง: คนที่สร้างงวดอนุมัติงวดนั้นเองไม่ได้ · รหัสบันทึก (write token) เหลือไว้ให้สคริปต์อัปโหลดหลายไฟล์เท่านั้น

**ขั้นตอนทดสอบ:**
1. พนักงานบัญชีส่งตรวจเดือนหนึ่ง → ผู้จัดการเข้าหน้าสาขา → กด “ปิดเดือน (ผู้จัดการ)” → ยืนยัน → ปิดได้ทันที ไม่ถามรหัส/ชื่อ · หัวการ์ดขึ้น “โดย <ชื่อผู้ใช้ผู้จัดการ>”
2. ผู้จัดการกด “เปิดงวดใหม่ (ผู้จัดการ)” + เหตุผล ≥10 ตัวอักษร → เปิดได้โดยไม่ถามรหัส · #auditlog มีเหตุผล + ชื่อผู้จัดการ
3. ผู้จัดการ A สร้างงวดของสาขาหนึ่งเอง (เช่น กดส่งตรวจในเดือนที่ยังไม่มีงวด) แล้วกดปิดเดือนเอง → ระบบปฏิเสธ “แบ่งแยกหน้าที่ (SoD)” → ผู้จัดการ B เข้าสู่ระบบแล้วปิดเดือนนั้น → สำเร็จ
4. ผู้ดูแลรันสคริปต์ bulk_recon_upload.py ด้วย write token (--no-login) → อัปโหลดสำเร็จ · audit บันทึกผู้ทำเป็น token · ใช้ write token อนุมัติ/ปิดเดือนไม่ได้
5. (ทดสอบย้อน) เปิดหน้าเว็บในเบราว์เซอร์ที่เคยใส่ปุ่ม “รหัส” ไว้ แต่ยังไม่เข้าสู่ระบบ → ยังต้องเข้าสู่ระบบก่อน (หน้าเว็บไม่ส่ง write token แทนการล็อกอิน)

**ผลที่คาดหวัง:** ผู้จัดการปิด/เปิดงวดด้วยสิทธิ์โดยไม่ใช้รหัสร่วม, ชื่อผู้อนุมัติมาจากผู้ที่เข้าสู่ระบบ, SoD ใช้ตัวตนจริง, สคริปต์ bulk upload ทำงานต่อด้วย write token แต่ทำงานผู้จัดการไม่ได้
